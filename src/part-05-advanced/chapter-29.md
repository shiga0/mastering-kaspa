# Chapter 29 — GHOSTDAG Security & DAGKnight（GHOSTDAGのセキュリティとDAGKnight）

> **原稿ステータス：v0.1（技術レビュー前）**  
> 本章は研究・実装理解のための解説であり、特定の攻撃に対する無条件の安全性や、DAGKnightの本番導入状況を保証するものではない。プロトコルの採用状況とパラメータは、参照時点のKIP・公式実装・リリース情報で確認する。

## 29.1 本章の目的

これまでにBlockDAG、GHOSTDAG、コンセンサス順序、Virtual State、Rust実装を学んだ。本章では、それらが**敵対的なネットワーク環境でなぜ、どの条件で安全と考えられるのか**を検討する。

学習目標は次のとおり。

1. 安全性（Safety）と活性（Liveness）を区別する。
2. ネットワーク遅延、攻撃者のハッシュレート、ブロック生成率が与える影響を説明する。
3. GHOSTDAGの`k`が表す役割と、固定パラメータのトレードオフを理解する。
4. DAGKnightが目指す改善を、既存GHOSTDAGとの関係で整理する。
5. 小規模シミュレーションで仮説を検証し、結果の限界を明記できる。

> **重要：** BlockDAGはブロック間の参照関係を表すデータ構造であり、GHOSTDAGとDAGKnightは、そのDAGから合意に必要な順序・選択を導くためのプロトコルである。

## 29.2 なぜコンセンサスにセキュリティモデルが必要か

正常なノードが同じ順序でブロックを受け取るとは限らない。ネットワークには遅延、パケット損失、分断、再接続がある。さらに、攻撃者がブロックを秘密裏に生成し、特定の時点で公開する可能性もある。

```text
          honest miner A                 honest miner B
                │                              │
          block X を生成                block Y を生成
                │                              │
                └────── network delay ────────┘
                              │
                       X と Y が並行
                              │
                         BlockDAG
                              │
                      ordering / state
```

並行ブロックの存在そのものは不正ではない。重要なのは、各ノードが最終的に互換性のある合意結果へ収束できるかどうかである。

## 29.3 安全性・活性・収束

| 性質 | 問い | 例 |
|---|---|---|
| Safety（安全性） | 正常ノードが互いに矛盾する確定結果を採用しないか | 二重支払いの防止 |
| Liveness（活性） | 正常なトランザクションが十分な条件下で処理され続けるか | 検閲や停止への耐性 |
| Convergence（収束） | ネットワークが回復した後、正常ノードが共通の見方に近づくか | 一時的なDAG差分の解消 |

これらは独立ではない。例えば極端に保守的な承認ルールは安全性を高める方向に働いても、トランザクションの利用可能性や確認時間を犠牲にし得る。

**不変条件の例**

- 無効なブロックが、検証を経ずに合意状態へ組み込まれない。
- 同じUTXOが同一の受理済み状態で二度消費されない。
- 合意順序が同じなら、決定的な状態遷移は同じ結果を返す。
- 再編成時にも、UTXO状態と合意順序の整合性が維持される。

これらは**実装上の検証対象**であり、単にGHOSTDAGを採用するだけで自動的に保証されるわけではない。

## 29.4 脅威モデルを明示する

安全性を議論するときは、少なくとも次を明示する。

| 前提・変数 | 意味 | 検証すべき点 |
|---|---|---|
| 攻撃者のハッシュレート比率 | 全計算資源に占める攻撃者の割合 | どの閾値・仮定で議論するか |
| ネットワーク遅延 | ブロック伝播にかかる時間 | 平均だけでなく分布・外れ値 |
| ブロック生成率 | 単位時間あたりのブロック数 | 並行ブロックがどの程度増えるか |
| ネットワーク分断 | 一部ノード間の通信断 | 回復後の収束 |
| 攻撃者の戦略 | 秘匿、遅延公開、競合ブロック生成など | 攻撃者が何を観測・制御できるか |
| ノードの検証能力 | CPU・ストレージ・帯域 | リソース枯渇で活性が失われないか |

「攻撃者が過半数未満なら絶対安全」のような単純化は避ける。安全性はネットワーク仮定、確認ポリシー、攻撃モデルにも依存する。

## 29.5 ブロック生成率と伝播遅延

直感をつかむため、ブロック生成を平均レート `λ` のポアソン過程と**仮定**する。伝播時間を一定の `Δ` 秒とすると、その間に生成されるブロック数の期待値は

\[
E[N] = \lambda \Delta
\]

である。少なくとも1ブロックが生成される確率は

\[
P(N \ge 1) = 1 - e^{-\lambda\Delta}
\]

となる。これは**ネットワーク競合の直感を得るためのモデル**であり、Kaspaの実際の安全性を計算する公式ではない。

例えば `λ=1 block/s`、`Δ=0.2s` と仮定すると、期待生成数は `0.2`、追加ブロックが少なくとも1個生成される確率は約18.1%となる。

ブロック生成率を高めれば、伝播が終わる前に別のブロックが生成される場面は増えやすい。線形チェーンで「競合ブロックを捨てる」設計と、並行ブロックをDAGに保持する設計では、この状況への対応が異なる。

## 29.6 GHOSTDAGの基本構造を復習する

GHOSTDAGは、BlockDAG上で選択された親（selected parent）を基準に、並行ブロックを含む構造を評価し、合意に必要な情報を計算する。

```text
            Genesis
             /   \
            A     B
             \   /
               C
              / \
             D   E
              \ /
               F
```

ここで `A` と `B`、`D` と `E` は並行し得る。DAGはその事実を保存するが、**どのブロックをどの順序で評価するか**は別途コンセンサス規則が決める。

用語の整理：

- **Past**：対象ブロックから親参照をたどって到達できるブロック集合。
- **Future**：対象ブロックを祖先として参照するブロック集合。
- **Anticone**：対象ブロックのPastにもFutureにも属さない、比較不能なブロック集合。
- **Selected-parent chain**：各ブロックの選択親をたどる系列。
- **blue / red**：GHOSTDAGの規則に基づく分類。**有効／無効の分類ではない**。

## 29.7 `k` パラメータは何を意味するか

GHOSTDAGの `k` は、並行性を扱うための重要なパラメータである。直感的には、選択されるblue集合の「許容する並行性」の範囲に関係する。

ただし、**「k個までの並行ブロックを無条件に受理する」や「kが大きいほど常に安全」という理解は不正確**。実際のblue集合の判定は、GHOSTDAGの具体的な規則に従う。

`k` に関する設計上の問い：

1. 通常のネットワーク遅延で生じる並行性をどこまで吸収するか。
2. 攻撃者が作る不自然な並行構造をどう区別するか。
3. 高速なブロック生成と保守的な選択規則をどう両立させるか。
4. ノードの処理負荷と状態管理コストにどう影響するか。

**実際の値・ネットワーク別設定・変更履歴は、対象バージョンの公式実装を確認する。**

## 29.8 blue / redの誤解を避ける

blueとredは、ブロックの署名やPoWが正しいかを示すラベルではない。

```text
  block validity                  GHOSTDAG classification
  ──────────────                  ───────────────────────
  PoW / header / rules            DAG position / ordering rules
          │                                 │
          ▼                                 ▼
  valid or invalid                 blue or red (contextual)
```

有効なブロックでもredに分類され得る。また、あるブロックが合意の一部として考慮されることと、そのブロックに含まれる全トランザクションが最終的に受理されることも同じではない。

## 29.9 攻撃の種類と観察点

### 29.9.1 秘密マイニング・遅延公開

攻撃者が生成ブロックを一時的に秘匿し、後からまとめて公開する。検証対象は、DAGの形状、選択親の変化、合意順序の変化、既存トランザクションへの影響である。

### 29.9.2 二重支払い

同一UTXOを使う競合トランザクションを異なる場所へ伝播させる。検証対象は、最終的なUTXO状態に二重消費が存在しないことと、再編成時のトランザクション状態の変化である。

### 29.9.3 Eclipse攻撃

被害ノードの接続先を攻撃者が支配し、観測するDAGを偏らせる。これは合意アルゴリズムだけでなく、**P2Pのピア選択・接続管理・ネットワーク多様性**にも関係する。

### 29.9.4 ネットワーク分断

正常ノードが異なるブロック集合を観測する。通信回復後の同期・合意順序・Virtual Stateの収束を調べる。

### 29.9.5 リソース枯渇

大量のメッセージや複雑なDAG構造によって、CPU・メモリ・ストレージ・帯域を圧迫する。安全性に加えて活性の問題でもある。

> ここで挙げたものは脅威の分類であり、特定の攻撃が現行Kaspaに成功することを意味しない。

## 29.10 Finalityをどう捉えるか

PoW型の分散合意では、確認が進むにつれて覆されるリスクが小さくなるという**確率的な確定性**を議論することが多い。

確認数だけを取り出して「絶対に戻らない」と断定してはいけない。アプリケーション側では、トランザクション額、脅威モデル、再編成の可能性、使用するノードの同期状態に応じて受理ポリシーを定義する。

例：

```text
Transaction submitted
        │
        ▼
Mempool observed
        │
        ▼
Included in a block
        │
        ▼
Observed in consensus state
        │
        ▼
Application acceptance policy satisfied
```

各段階は同義ではない。特に、**Mempoolにあることと、合意状態で受理されたことは異なる**。

## 29.11 DAGKnightは何を改善しようとしているか

DAGKnightは、GHOSTDAG系の研究を発展させ、**ネットワーク遅延に対する固定的な前提への依存を減らし、観測されたネットワーク状況に適応する**ことを目指すコンセンサス研究である。

ここでの「適応」は、単純に「ブロック生成速度を自動で上げる」という意味ではない。合意の判断において、遅延・並行性・攻撃者に関する仮定をどう扱うかが中心となる。

| 観点 | GHOSTDAG | DAGKnightの研究上の方向性 |
|---|---|---|
| 並行ブロック | DAGとして扱う | DAGとして扱う |
| 合意規則 | `k` に依存する選択規則を用いる | 固定的な遅延前提への依存を減らすことを目指す |
| ネットワーク条件 | 想定条件・パラメータの設定が重要 | 観測された条件への適応が主要な研究課題 |
| 実装上の課題 | 選択・順序・状態更新の決定性 | 追加の判定ロジック、証明と実装の整合性 |
| 導入状況 | 対象ネットワークとバージョンを確認 | **提案・研究と本番稼働を区別して確認** |

**注意：** この表は理解のための概念比較であり、論文の定理・実装仕様を完全に再現したものではない。

## 29.12 DAGKnightの安全性を読むときの質問

研究論文を読むとき、アルゴリズムの概要だけでなく次を確認する。

1. **ネットワークモデル**：同期・部分同期・非同期のどれを仮定しているか。
2. **攻撃者モデル**：計算資源、ネットワーク操作能力、適応的行動の範囲は何か。
3. **安全性の主張**：どの事象の確率を、どの条件下で抑えるか。
4. **活性の主張**：どの条件が回復すると処理が進むか。
5. **確認・確定の規則**：何を観測したら受理するか。
6. **複雑度**：ブロック数増加時の計算量・メモリ量はどうなるか。
7. **実装可能性**：ノード間で決定的に同じ結果を計算できるか。

「適応的」「高速」「安全」という言葉だけでは、プロトコルの保証範囲は分からない。

## 29.15 最小実験：遅延中にブロックが増える確率

この実験は**GHOSTDAGやDAGKnightの安全性を証明しない**。ブロック生成率と伝播遅延の関係を理解するための導入である。

### 29.15.1 Rustプロジェクト

```bash
cargo new dag-delay-experiment
cd dag-delay-experiment
```

`src/main.rs`：

```rust
fn probability_at_least_one(lambda: f64, delay_seconds: f64) -> f64 {
    assert!(lambda >= 0.0);
    assert!(delay_seconds >= 0.0);
    1.0 - (-lambda * delay_seconds).exp()
}

fn main() {
    let rates = [0.1, 1.0, 10.0];
    let delays = [0.05, 0.2, 1.0];

    println!("rate(block/s), delay(s), P(N>=1)");
    for rate in rates {
        for delay in delays {
            println!("{rate:.2}, {delay:.2}, {:.4}",
                probability_at_least_one(rate, delay));
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn zero_rate_means_zero_probability() {
        assert_eq!(probability_at_least_one(0.0, 1.0), 0.0);
    }

    #[test]
    fn zero_delay_means_zero_probability() {
        assert_eq!(probability_at_least_one(10.0, 0.0), 0.0);
    }

    #[test]
    fn probability_increases_with_rate() {
        assert!(probability_at_least_one(10.0, 0.2)
            > probability_at_least_one(1.0, 0.2));
    }

    #[test]
    fn probability_increases_with_delay() {
        assert!(probability_at_least_one(1.0, 1.0)
            > probability_at_least_one(1.0, 0.1));
    }
}
```

```bash
cargo test
cargo run
```

### 29.15.2 観察と限界

期待される観察は、生成率と遅延が大きいほど、伝播中に別ブロックが生じやすくなること。ただし、ここでは伝播時間を固定値とし、ネットワークトポロジー、攻撃者、ブロックサイズ、相関、ノードの検証時間を省略している。

**次の実験では**遅延を確率分布に変更し、ノードごとの観測DAGの違いを記録する。

## 29.16 発展実験：攻撃者を含むDAGシミュレーター

実際のセキュリティ検証へ進むには、次のようなイベント駆動モデルを作る。

```text
Simulation State
 ├── nodes: [NodeState]
 ├── event_queue: PriorityQueue<Event>
 ├── network: DelayModel
 ├── miners: HashrateDistribution
 └── metrics: Measurements

Event
 ├── MineBlock { miner_id, timestamp }
 ├── DeliverBlock { from, to, block_id }
 ├── Disconnect { node_a, node_b }
 └── Reconnect { node_a, node_b }
```

**測定する指標**：

- ノード間のDAG差分
- ブロック伝播時間の分布
- 合意順序の再計算回数
- 状態再編成の回数・深さ
- トランザクション受理状態の変化
- CPU時間・メモリ使用量

GHOSTDAGを忠実に再現するには、選択親、merge set、blue/red判定、blue score/work、順序規則を**仕様に基づいて実装**する必要がある。単純なトポロジカルソートを代用して「GHOSTDAGの実験」と呼んではいけない。

## 29.17 テスト戦略：何を証明し、何を観測するか

| レベル | 例 | 得られる証拠 |
|---|---|---|
| 単体テスト | Past/Anticone計算 | 局所的な正しさ |
| プロパティテスト | DAGに閉路が生じない | 広い入力範囲の不変条件 |
| 差分テスト | 参照実装との出力比較 | 実装間の一致 |
| シミュレーション | 遅延・分断・攻撃者のモデル化 | モデル内の挙動 |
| Devnet統合テスト | 複数ノードの再接続・同期 | 実装間の動作確認 |
| 形式的検証・論文 | 定理と仮定に基づく議論 | 定義したモデル内の保証 |

**重要：** テストが全て成功しても、未知の攻撃に対する安全性の証明にはならない。逆に、論文上の定理があっても、実装バグや運用ミスは別途検証する必要がある。

## 29.18 C4・DDD・状態遷移で整理する

### C4：コンテナ／コンポーネントの責務

- **Network**：メッセージ受信・ピア管理・帯域制御。
- **Block Validation**：構文・PoW・文脈依存検証。
- **DAG Store**：祖先関係・索引・永続化。
- **Consensus**：選択親・分類・順序・仮想状態への入力。
- **UTXO State**：トランザクション適用・競合解決・再編成。
- **Observability**：再編成・同期・遅延・エラーの測定。

### DDD：言葉の境界

「ブロックが有効」「ブロックがblue」「トランザクションが受理済み」「アプリが確定扱い」は別のドメイン概念として名前を分ける。曖昧な`confirmed: bool`だけで全段階を表すと、セキュリティ上の誤解を生みやすい。

### 状態遷移

```text
Received → Validated → Indexed in DAG
                            │
                            ▼
                    Consensus evaluated
                            │
                            ▼
                     Virtual state updated
                            │
                            ▼
                     Application notified
```

通知と永続化の順序、再編成時の再通知・取り消しも設計対象となる。

3. 選択親と順序計算の責務。
4. Virtual StateとUTXO更新の境界。
5. 再編成時の処理とテスト。
6. ネットワーク別パラメータの定義と有効化条件。

本章執筆時点でのDAGKnightの採用状況を、ここでは断定しない。読者は次を区別して確認する。

- 対応するKIPや仕様が存在するか。

## 29.21 ケーススタディ：アプリケーションの確認ポリシー

決済アプリがトランザクションを「成功」と表示するまでを設計する。

**悪い例**：Mempoolで見えた時点で不可逆な決済として処理する。

**改善例**：

1. `submitted`：送信を受け付けた。
2. `observed`：ネットワーク上で観測した。
3. `accepted_by_consensus`：ノードの合意状態で受理を観測した。
4. `accepted_by_policy`：アプリ独自の確認ポリシーを満たした。
5. `reversed`：再編成などで状態が変わった。

これらをイベントとして記録し、重複通知や再編成に対して冪等に処理する。実際のRPCイベント名・確定性の意味は使用バージョンで確認する。

## 29.22 よくある誤解

| 誤解 | 正しい理解 |
|---|---|
| BlockDAGだから攻撃されない | データ構造だけで安全性は決まらない |
| blueは有効、redは無効 | blue/redはコンセンサス上の分類 |
| 高速なブロック生成は常に安全 | 遅延・攻撃者・パラメータに依存する |
| `k`は単なる同時ブロック数の上限 | GHOSTDAGの選択規則に関係するパラメータ |
| DAGKnightが提案された＝本番稼働済み | 論文・KIP・実装・有効化は別段階 |
| Devnetで成功した＝安全性が証明された | 統合テストは限定された証拠 |
| トランザクションが見えた＝不可逆に確定 | 観測・合意受理・アプリ承認は異なる |

### 課題B：遅延実験を拡張する

### 課題C：Rust実装の不変条件を特定する

Chapter 22のRPC連携を前提に、`submitted`から`accepted_by_policy`までの状態遷移と、再編成時の補償処理を設計する。

## 29.25 まとめ

本章の要点は次のとおり。

- **セキュリティはアルゴリズム名だけでは語れない。** ネットワーク・攻撃者・確認ポリシーの前提が必要。
- **BlockDAGは並行性を記録する構造**であり、GHOSTDAGは合意のための分類・順序付けを担う。
- **blue/redは有効/無効ではない。** ブロックとトランザクションの受理も分けて考える。
- **DAGKnightは固定的な遅延前提への依存を減らすことを目指す研究**として、論文の仮定から理解する。
- **論文、KIP、実装、ネットワーク有効化を混同しない。**
- **Rust実装では不変条件・決定性・再編成・障害復旧を検証する。**

次章 **Chapter 30 — Kaspa Improvement Proposals（Kaspa改善提案・KIP）** では、研究成果や変更案がどのように仕様・実装・ネットワーク運用へ結びつくかを扱う。
