## この章で学ぶこと

マイニングはブロックを生成する技術的な処理であると同時に、報酬と費用によって参加者の行動が決まる経済システムでもある。本章では、マイナーの収益構造、ネットワーク全体のハッシュレート、攻撃コスト、報酬の長期的な変化を結び付けて考える。**経済的に採算が取れることと、ネットワークが安全であることは同義ではない**点に注意する。

3. 攻撃者のハッシュパワーと攻撃成功確率・費用を混同せずに議論できる。
4. KaspaのBlockDAGに固有の評価事項を理解する。
5. Rustで簡易収益モデルを作り、前提条件を変えて感度分析できる。

## 19.1 マイニングは何に対して報酬を受け取るのか

Proof of Work（PoW）では、マイナーは計算資源を投入してブロック候補のPoW条件を満たそうとする。採掘に成功しても、ネットワークがそのブロックをプロトコル上適切に扱わなければ、期待した報酬を得られるとは限らない。

マイナーが得る収益の源泉は大きく二つある。

- **発行報酬（subsidy）**：プロトコルの発行スケジュールに従う新規発行分。
- **トランザクション手数料（fees）**：ネットワーク利用者が取引に支払う手数料。

報酬の実際の帰属や支払条件は、ブロックの扱い、Coinbaseの仕組み、マイニングプールの契約・配分方法に依存する。Bitcoinの「最長チェーンに採用されたブロック」という直感を、そのままKaspaのすべてのブロックに当てはめない。

### 経済的な因果関係

```text
KAS市場価格 ─────┐
発行報酬 ────────┼──> 期待売上 ──┐
手数料収入 ──────┘               │
                                 ├──> 利益・採掘継続判断
電力単価 ────────┐               │
機器効率 ────────┼──> 期待費用 ──┘
設備投資・運用 ───┘
             │
             ▼
     参加ハッシュレートの変化
             │
             ▼
      難易度調整と競争環境
```

これは単方向の確定的な予測モデルではない。価格、採掘競争、電力調達、設備市場、将来期待が相互に影響する。

## 19.2 収益・利益・キャッシュフローを分ける

日次の簡易モデルを次のように定義する。

- `H_m`：自分のハッシュレート
- `H_n`：ネットワークのハッシュレート
- `B`：ネットワーク全体の1日当たりの期待ブロック数
- `R`：1ブロック当たりの**平均的な期待受取報酬**（KAS、発行報酬と手数料を含む。採掘・報酬の実際のルールを簡略化）
- `P`：KAS価格（円/KAS）
- `W`：消費電力（W）
- `E`：電力単価（円/kWh）
- `C`：プール手数料率

ハッシュレートの比率を `s = H_m / H_n` とすると、極めて単純化した期待売上は以下となる。

```text
期待獲得KAS/日 ≈ B × R × s × (1 - C)
期待売上（円/日） ≈ 期待獲得KAS/日 × P
電力費（円/日） = W / 1000 × 24 × E
営業寄与（円/日） ≈ 期待売上 - 電力費 - その他日次運用費
```

**重要な制限**：この式は個々のKaspaブロックの実際の報酬配分を再現しない。`R` を「観測された平均的な有効受取報酬」として扱うための教育用モデルである。また、発行報酬・手数料・採掘条件は時期とネットワーク設定で変わる。

### 例：仮定した数値で計算する

次の数字は**市場の実測値ではなく例示用**である。

| 項目 | 仮定 |
|---|---:|
| 自分のハッシュレート比率 | 0.0001%（0.000001） |
| 1日当たり期待ブロック数 | 864,000 |
| 平均的な有効報酬 | 0.5 KAS/ブロック |
| KAS価格 | 10円/KAS |
| 消費電力 | 100 W |
| 電力単価 | 30円/kWh |
| プール手数料 | 1% |

```text
期待獲得量 = 864,000 × 0.5 × 0.000001 × 0.99
           = 0.42768 KAS/日
期待売上   = 4.2768 円/日
電力費     = 0.1 × 24 × 30 = 72 円/日
営業寄与   = -67.7232 円/日（その他費用を除く）
```

この例では採算が合わない。ただし、この結論は**仮定した条件にだけ**当てはまる。実際の採算は、その時点のハッシュレート、実報酬、機器性能、電気料金、価格、プール条件で再計算する必要がある。

## 19.3 初期投資と減価償却

日次の電力収支がプラスでも、ASICの購入費用を回収できるとは限らない。

```text
総投資額 = 機器購入費 + 送料 + 関税等 + 電源・配線・冷却設備
概算回収期間（日） = 総投資額 / 日次キャッシュ余剰
```

この回収期間は、日次余剰が正で一定と仮定した場合だけ意味を持つ。実際には、設備の劣化、故障、陳腐化、難易度上昇、価格変動、報酬低下、税務処理などがある。**回収期間の計算と会計上の減価償却は別**である。

### 追加で確認すべきコスト

| 費用 | 典型的な論点 |
|---|---|
| ASIC本体 | 初期費用・中古価格・故障率 |
| 電源装置 | 定格出力・効率・安全性 |
| 冷却 | ファン・空調・室温・騒音 |
| 通信 | 停電・回線障害・プール接続 |
| 電力 | 契約単価・時間帯料金・契約容量 |
| プール | 手数料・最低支払額・支払方式 |
| 保守 | ファームウェア・予備機・修理 |
| 税務 | 収入認識・費用計上・居住地の法令 |

## 19.4 ハッシュレート・難易度・生成間隔

ネットワーク全体の計算能力が増えると、難易度が一定ならPoW条件を満たす頻度は増える。しかしPoWネットワークには難易度調整があり、目標とするブロック生成ペースに近づけようとする。

```text
ネットワークハッシュレート ↑
            │
            ▼
難易度が一定なら期待生成頻度 ↑
            │
            ▼
難易度調整が追従
            │
            ▼
目標生成ペースに近づく
```

「ハッシュレートが2倍なら、いつまでもブロックが2倍生成される」という理解は誤りである。詳細は第13章を参照。

また、**ハッシュレートの単位（H/s、TH/s、PH/sなど）と消費電力（W）は別**であり、機器の効率（J/TH等）で結び付ける。

## 19.5 ハッシュ効率と電力単価

マイニング機器の性能は、ハッシュレートの大きさだけでは判断できない。

```text
効率（J/TH） = 消費電力（J/s） / ハッシュレート（TH/s）
```

同じハッシュレートで消費電力が少ないほど、一般に電力費は低い。ただし、ASICはアルゴリズム専用機であるため、**異なるPoWアルゴリズム向けのハッシュレート数値をそのまま比較してはいけない**。

## 19.6 ソロマイニングとプールマイニング

### ソロマイニング

自分で採掘を試み、成功したときの収入を得る方式。期待値がプラスでも、低いハッシュシェアでは報酬を得るまでの期間が非常に長くなる可能性がある。

### プールマイニング

複数の参加者がハッシュパワーを集め、プールの支払方式に従って報酬を分配する。収入の分散を抑えやすいが、手数料、支払条件、プール運営者への依存が生じる。

| 観点 | ソロ | プール |
|---|---|---|
| 報酬のばらつき | 大きい | 一般に小さい |
| 手数料 | プール手数料なし | 通常あり |
| 運用難度 | 高め | 相対的に低め |
| 運営者への依存 | 低い | あり |
| 検閲・集中化の論点 | 個別参加者に分散 | プール運営者の影響が大きくなり得る |

プールの「ハッシュレート比率」と、誰がブロックテンプレートを作るかという**意思決定権限**は区別して分析する。

## 19.7 報酬分布のばらつき

一定の短期間に採掘できるブロック数は確定値ではない。単純化した独立試行モデルでは、成功回数は確率変数になる。期待獲得数が少ないマイナーほど、実績と期待値が大きく乖離しやすい。

たとえば期待採掘数が1ブロック/日であっても、毎日必ず1ブロック得られるわけではない。ポアソン近似を用いると、1日でゼロ件の確率は約 `e^-1 ≈ 36.8%` となる。ただし、実際のネットワークと報酬配分には追加条件がある。

**期待値と確実性は異なる。**

## 19.8 PoWセキュリティの基本

PoWの重要な性質は、ネットワーク上の履歴を攻撃者に有利な形で作り直そうとすると、計算資源が必要になることである。

ただし、次の三つを混同しない。

1. **ハッシュパワーの比率**：攻撃者がどの程度の計算資源を持つか。
2. **攻撃成功確率**：攻撃モデル、ネットワーク状況、確認時間などに依存する。
3. **攻撃費用**：設備、電力、レンタル市場、機会費用、価格変動などに依存する。

「51%未満なら絶対安全」「51%以上なら必ずあらゆる攻撃が成功する」という二分法は正確ではない。攻撃の種類と前提を特定する必要がある。

## 19.9 攻撃モデルを分ける

| 攻撃・リスク | 狙い | 主な前提 |
|---|---|---|
| 二重支払い | 先に見せた支払いを後で覆す | 履歴競争・確認深度・計算資源 |
| 検閲 | 特定の取引を取り込まない | ブロック作成権限の集中など |
| Selfish mining | 公開タイミングを操作し利益を増やす | ネットワーク・競争条件 |
| Eclipse攻撃 | 特定ノードの接続先を支配 | P2P接続・ピア管理の弱点 |
| DoS | 参加者の処理・通信を妨害 | 帯域・計算・実装の弱点 |
| プール集中 | 少数主体にブロック構築権限が偏る | プール参加・運営構造 |

これらは必要資源も影響も異なる。PoWの計算コストだけでP2Pレイヤーの攻撃を防げるわけではない。

## 19.10 BitcoinとKaspaで攻撃分析が異なる理由

Bitcoinでは、競合するブロックの一部が主チェーンに含まれず、累積作業量によるチェーン選択が重要になる。一方KaspaはBlockDAGを用い、並行ブロックの関係をGHOSTDAGなどのルールで扱う。

したがって、Bitcoin向けの「確認ブロック数と逆転確率」の説明を、そのままKaspaの安全性の数式として再利用してはいけない。Kaspaの分析では少なくとも以下を確認する。

- 攻撃者と誠実な参加者のハッシュパワー比率
- ブロック生成率とネットワーク遅延
- GHOSTDAGのパラメータと前提
- 攻撃者のブロック公開戦略
- 対象とするファイナリティ・確認基準
- 実装バージョンおよびネットワークの設定

KaspaのBlockDAGは並行ブロックをより積極的に活用する設計だが、**すべての攻撃が不可能になるわけではない**。

## 19.11 ネットワーク遅延と公平性

ブロックの伝播速度は、マイナー間の競争条件を左右する。通信が速い参加者は、最新のブロック情報を早く把握し、古い情報を前提に採掘する時間を減らせる。

KaspaのBlockDAGは並行生成ブロックを扱うが、ネットワーク遅延が無視できるわけではない。高いブロック生成率を採用する際は、通信量、検証負荷、ノードの参加可能性を合わせて考える必要がある。

```text
高いブロック生成率
    ├── 確認体験・処理機会の改善可能性
    ├── 伝播・検証負荷の増加
    ├── 低性能ノードへの負担
    └── ネットワーク分断時の複雑性
```

「生成レートを上げれば安全性と分散性が自動的に改善する」という主張には追加の検証が必要である。

## 19.12 マイニング集中化の指標

単にマイナーの台数を数えるだけでは分散性を評価できない。

- ハッシュパワーの分布
- プール運営者の分布
- ブロックテンプレート作成権限の分布
- ASICメーカーへの依存
- 電力・地域・法制度への依存
- ネットワーク接続や中継インフラの集中

### HHI（集中度指標）

参加主体のシェアを百分率 `s_i` で表すと、HHIは `Σ s_i²` と定義できる。たとえば4主体がそれぞれ25%なら `4 × 25² = 2500`。1主体が100%なら `10000`。

これは**主体をどう定義するか**で結果が変わる。プールを1主体と数えるのか、実際のハッシュ所有者で分けるのかを明記すること。

## 19.13 発行報酬の減少と長期的な安全性

Kaspaは発行報酬が時間とともに減少する設計を採用している。長期的には新規発行に由来するマイナー収入が縮小し、手数料収入の相対的重要性が増す。

```text
初期：発行報酬が主な収入源
              │
              ▼
時間経過：発行報酬の減少
              │
              ▼
将来：手数料収入の重要性が増す
```

しかし「手数料が発行報酬を必ず補う」とは限らない。取引需要、手数料水準、ネットワーク容量、KAS価格、ASIC効率、電力価格などが関係する。

**安全性の持続可能性は、発行スケジュールだけでは判断できない。** 実際の発行量・報酬規則は、調査対象時点の公式仕様と実装で確認する。

## 19.14 セキュリティ予算（Security Budget）

PoWネットワークの「セキュリティ予算」は、通常、一定期間にマイナーへ支払われる経済的報酬の規模を指す説明概念として使われる。

```text
概念上の報酬予算 ≈ 新規発行価値 + 手数料価値
```

これは**攻撃に必要な最小費用を直接表す数値ではない**。マイナー報酬が高くても、ハッシュパワーの調達市場や攻撃者の保有設備、ネットワーク条件次第で攻撃コストは変わる。逆に攻撃コストは電力費だけでもない。

## 19.15 ゲーム理論：誠実な行動が合理的になる条件

PoWの設計目標の一つは、ルールに従って採掘することが、逸脱するより経済的に魅力的になる環境を作ることにある。

マイナーの選択肢を単純化すると、次のように整理できる。

| 行動 | 期待する利益 | 主なリスク |
|---|---|---|
| 誠実な採掘 | 継続的な報酬 | 価格・難易度・設備費 |
| ブロックの公開操作 | 相対的な報酬増 | 失敗時の報酬喪失・検出 |
| 二重支払い攻撃 | 不正な経済的利益 | 計算資源・失敗・法的リスク |
| 取引検閲 | 外部からの利益・戦略目的 | 評判・収益・競争の変化 |

実際の均衡はプロトコルと外部市場の条件に依存する。すべての参加者が金銭的利益のみを最大化するとも限らない。

## 19.16 Rustで作る最小マイニング収益モデル

次のコードは**Kaspaプロトコルを実装したものではない**。入力条件から期待売上・電力費を計算する、依存関係を限定した純粋関数の例である。

```rust
#[derive(Debug, Clone, Copy)]
struct MiningAssumptions {
    miner_hashrate: f64,
    network_hashrate: f64,
    expected_blocks_per_day: f64,
    average_effective_reward_kas: f64,
    kas_price_jpy: f64,
    pool_fee_rate: f64,
    power_watts: f64,
    electricity_jpy_per_kwh: f64,
    other_cost_jpy_per_day: f64,
}

#[derive(Debug, PartialEq)]
struct DailyEstimate {
    expected_kas: f64,
    revenue_jpy: f64,
    electricity_jpy: f64,
    operating_margin_jpy: f64,
}

fn estimate_daily(a: MiningAssumptions) -> Result<DailyEstimate, &'static str> {
    let values = [
        a.miner_hashrate, a.network_hashrate, a.expected_blocks_per_day,
        a.average_effective_reward_kas, a.kas_price_jpy,
        a.pool_fee_rate, a.power_watts, a.electricity_jpy_per_kwh,
        a.other_cost_jpy_per_day,
    ];
    if values.iter().any(|x| !x.is_finite() || *x < 0.0) {
        return Err("inputs must be finite and nonnegative");
    }
    if a.network_hashrate <= 0.0 || a.miner_hashrate > a.network_hashrate {
        return Err("invalid hashrate assumptions");
    }
    if a.pool_fee_rate > 1.0 {
        return Err("pool fee must be <= 1");
    }

    let share = a.miner_hashrate / a.network_hashrate;
    let expected_kas = a.expected_blocks_per_day
        * a.average_effective_reward_kas * share * (1.0 - a.pool_fee_rate);
    let revenue_jpy = expected_kas * a.kas_price_jpy;
    let electricity_jpy = a.power_watts / 1000.0 * 24.0
        * a.electricity_jpy_per_kwh;
    Ok(DailyEstimate {
        expected_kas,
        revenue_jpy,
        electricity_jpy,
        operating_margin_jpy: revenue_jpy - electricity_jpy
            - a.other_cost_jpy_per_day,
    })
}

fn main() {
    let assumptions = MiningAssumptions {
        miner_hashrate: 1.0,
        network_hashrate: 1_000_000.0,
        expected_blocks_per_day: 864_000.0,
        average_effective_reward_kas: 0.5,
        kas_price_jpy: 10.0,
        pool_fee_rate: 0.01,
        power_watts: 100.0,
        electricity_jpy_per_kwh: 30.0,
        other_cost_jpy_per_day: 0.0,
    };
    println!("{:#?}", estimate_daily(assumptions).unwrap());
}

#[cfg(test)]
mod tests {
    use super::*;

    fn sample() -> MiningAssumptions {
        MiningAssumptions {
            miner_hashrate: 1.0,
            network_hashrate: 1_000_000.0,
            expected_blocks_per_day: 864_000.0,
            average_effective_reward_kas: 0.5,
            kas_price_jpy: 10.0,
            pool_fee_rate: 0.01,
            power_watts: 100.0,
            electricity_jpy_per_kwh: 30.0,
            other_cost_jpy_per_day: 0.0,
        }
    }

    #[test]
    fn electricity_cost_is_correct() {
        let estimate = estimate_daily(sample()).unwrap();
        assert!((estimate.electricity_jpy - 72.0).abs() < 1e-10);
    }

    #[test]
    fn doubling_price_doubles_revenue_not_electricity() {
        let a = sample();
        let first = estimate_daily(a).unwrap();
        let second = estimate_daily(MiningAssumptions {
            kas_price_jpy: a.kas_price_jpy * 2.0,
            ..a
        }).unwrap();
        assert!((second.revenue_jpy - first.revenue_jpy * 2.0).abs() < 1e-10);
        assert_eq!(second.electricity_jpy, first.electricity_jpy);
    }

    #[test]
    fn rejects_invalid_network_hashrate() {
        let a = MiningAssumptions { network_hashrate: 0.0, ..sample() };
        assert!(estimate_daily(a).is_err());
    }

    #[test]
    fn zero_miner_hashrate_yields_zero_revenue() {
        let a = MiningAssumptions { miner_hashrate: 0.0, ..sample() };
        let estimate = estimate_daily(a).unwrap();
        assert_eq!(estimate.revenue_jpy, 0.0);
    }
}
```

### 実行方法

1. `cargo new mining-economics`
2. 上記コードを `src/main.rs` に保存
3. `cargo run`
4. `cargo test`

外部クレートは不要。コードは教育用のサンプルであり、実際のKaspaノード・プール・ASICとは接続しない。

## 19.17 感度分析の進め方

1つの条件だけを変えて結果を比較する。

| 変更する条件 | 期待される影響（その他一定） |
|---|---|
| KAS価格を2倍 | 円建て期待売上は2倍 |
| ネットワークハッシュレートを2倍 | 自分のシェアは半分 |
| 電力単価を2倍 | 電力費は2倍 |
| 消費電力を半分 | 電力費は半分 |
| 平均有効報酬を半分 | KAS建て期待受取は半分 |
| プール手数料を増やす | 手取り期待報酬が減る |

**注意**：現実には変数が相関する。たとえば価格上昇は新規参入とハッシュレート上昇を誘発し得る。単一変数分析は「予測」ではなく「依存関係の確認」に使う。

## 19.18 設計：責務境界と不変条件

マイニング経済の分析ツールを設計する場合、データ取得と計算を分けると検証しやすい。

```text
External Data Sources
  ├── Market Price Provider
  ├── Network Metrics Provider
  └── Hardware Specification Provider
                │
                ▼
        Assumption Validation
                │
                ▼
          Economics Model
                │
                ▼
       Scenario Comparison
                │
                ▼
          Report / UI
```

### 不変条件

- ネットワークハッシュレートは正である。
- マイナーハッシュレートは負にならない。
- マイナーハッシュレートはネットワーク全体を超えない（同一時点・同一アルゴリズムの測定前提）。
- 電力・価格・手数料は負にならない。
- プール手数料率は0〜1の範囲である。
- 通貨単位と時間単位を混同しない。
- 実測値と仮定値を混在させる場合、出所と取得日時を保存する。

### DDDの観点

`MiningAssumptions` は**計算の入力値**であり、Kaspaコンセンサスのドメインモデルではない。ネットワーク上の「ブロックの有効性」と、アプリケーション上の「採算性」を同じモジュールに押し込まない。

## 19.20 運用上のセキュリティ

マイニング設備の運用では、PoW以外のリスクにも対処する。

- ASICや管理画面を不用意にインターネット公開しない。
- 初期パスワードを変更し、管理ネットワークを分離する。
- ファームウェアの入手元・署名・ハッシュを確認する。
- マイニングプールの支払先アドレスを検証する。
- 電源容量、発熱、騒音、配線の安全性を確保する。
- 温度、消費電力、ハッシュレート、プールへの接続を監視する。
- 収益の記録と機器購入費・電力費の記録を分ける。

## 19.21 よくある誤解

**誤解1：ハッシュレートが高いほど必ず儲かる。**  
→ ネットワーク全体に対する比率、効率、価格、報酬、費用が重要。

**誤解2：51%を超えなければどんな攻撃もできない。**  
→ P2P妨害や検閲など、攻撃モデルによって必要条件が異なる。

**誤解3：報酬の減少は即座にセキュリティ崩壊を意味する。**  
→ 手数料、価格、採掘コスト、設備市場など複数要因が関係する。

**誤解4：プールの参加者数が多ければ分散化している。**  
→ テンプレート作成権限などの集中を別途調べる必要がある。

**誤解5：Kaspaでは並行ブロックが扱えるのでネットワーク遅延は問題にならない。**  
→ 伝播遅延は負荷、公平性、攻撃面に引き続き影響する。

## 19.22 実践課題

### 課題A：ASICの採算表

任意のASICについて、ハッシュレート・消費電力・購入費・電力単価を調べ、**データ取得日と出典**を添えて損益を計算する。価格とネットワークハッシュレートをそれぞれ±50%変化させた表も作る。

### 課題B：プール集中度

同一期間のプール別シェアを集めてHHIを計算する。さらに「プール単位」と「推定される独立した運営主体単位」で何が違うかを議論する。

### 課題C：セキュリティモデル

二重支払い・検閲・Eclipse攻撃を1つずつ選び、攻撃者の目的、必要資源、信頼境界、観測可能な兆候、防御策を表にする。

### 課題D：Rustのモデル拡張

上記のコードに `hardware_cost_jpy` を追加し、日次余剰が正の場合のみ回収日数を計算する。ゼロ・負の余剰では回収不能を表す型を返すようにする。

## 19.23 理解度チェック

1. ハッシュレートが同じでもマイナーの利益が異なるのはなぜか。
2. 難易度調整があるネットワークで、ハッシュレートと生成レートをどう区別するか。
3. ソロマイニングの期待値と実際の収入はなぜ乖離するか。
4. プール集中度を評価するとき、ハッシュ所有者とテンプレート作成者を分ける理由は何か。
5. 「51%攻撃」という言葉だけでは不十分なのはなぜか。
6. 発行報酬が減少したとき、ネットワーク安全性を考えるためにどの変数が必要か。
7. Bitcoinのチェーン再編成確率をKaspaへそのまま適用できない理由は何か。
8. セキュリティ予算と実際の攻撃費用はどう違うか。

## 19.24 まとめ

- マイニングは**計算資源・市場価格・報酬・費用**が相互に作用する経済システムである。
- ハッシュレートの大きさだけでは採算性も安全性も評価できない。
- PoWセキュリティを論じるときは、**攻撃モデルと前提条件**を明示する。
- KaspaではBlockDAGとGHOSTDAGを踏まえ、Bitcoinとは異なる確認・競合処理を考える必要がある。
- 長期的な安全性は、発行報酬だけでなく、手数料需要やマイナーの費用構造にも依存する。
- 分析ツールでは、**仮定値・実測値・計算式・単位・取得時点**を分離することが重要である。

次章では、マイニング経済の議論を踏まえ、**Kaspa Network Security & Finality（Kaspaのネットワークセキュリティとファイナリティ）**を扱う。
