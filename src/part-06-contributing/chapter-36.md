# Chapter 36 — Contributing to Kaspa（Kaspaへのコントリビュート）

> **目次順の本文レビュー：2026-11-01。基準版の開発用入口・公開手順と独自Rust教材を確認。公式CI全体や実PR提出の検証ではない。**
> この章は、Kaspaのオープンソース開発に参加するための実践ガイドである。リポジトリ構成、開発手順、CI、メンテナーの方針は変化するため、作業時点の一次資料を確認すること。

ソース照合は本書の基準版v1.0.1 / `fcd9c28f9b211b9872a0c90a8c94f79466ffb063`。実際の上流への貢献では、その時点の指定base・開発ルールを別に確認する。確認記録は `experiments/chapter-36-review-2026-11-01.md`。

## この章で学ぶこと

- Kaspaへの貢献を、コード・テスト・文書・検証・研究に分解する。
- `rusty-kaspa`の変更箇所を特定し、安全に小さなPull Requestを作る。
- コンセンサスの変更と通常のアプリケーション変更で必要な検証が異なる理由を説明する。
- 不変条件・状態遷移・依存関係を明確にした上で変更を進める。
- 失敗や実験結果を、他の開発者が再現できる形で残す。

## 36.1 コントリビュートとは何か

コントリビュート（contribution）は、ソースコードを追加することだけではない。Kaspaのような分散システムでは、仕様の曖昧さを発見する、再現可能なバグ報告を作る、テストを増やす、ドキュメントを修正することも重要な貢献になる。

| 種類 | 例 | 成果物 |
|---|---|---|
| ドキュメント | RPCの説明を修正する | 文書PR |
| テスト | 再編成時の境界条件を検証する | 回帰テスト |
| バグ修正 | エラー処理の不備を直す | 小さなコードPR |
| 開発者体験 | ローカル構築手順を改善する | スクリプト・README |
| 性能調査 | 同期処理のボトルネックを測る | ベンチマーク・レポート |
| 研究・仕様 | コンセンサス変更の妥当性を議論する | 論文レビュー・KIPへのフィードバック |

**重要：** 価値は変更行数では決まらない。小さくても、検証可能で、保守しやすい変更は大きな貢献になり得る。

## 36.2 Kaspaの開発に参加する前に

最低限、次の区別を理解しておこう。

1. **プロトコル仕様**：ネットワーク参加者が従うべき合意規則。
2. **実装**：仕様をRustなどのコードに落とし込んだもの。
3. **テスト**：実装が期待する性質を満たすか検証するもの。
4. **運用**：ノードの同期、監視、障害対応、アップグレード。
5. **アプリケーション**：RPCやSDKを通じてKaspaを利用するもの。

たとえばRPCの表示形式を改善する変更と、ブロックの受理条件を変える変更では、リスクもレビューの重さも大きく異なる。

## 36.4 開発環境の準備

以下は一般的なRustプロジェクトとしての準備例であり、実際の必須コマンドはリポジトリのREADMEに従う。

```bash
# 第1章の固定checkoutを、本書とは別の調査用ディレクトリで再利用する
cd rusty-kaspa-v1.0.1
git rev-parse HEAD
# HEADを本章の完全SHAと照合する
rustc --version
cargo --version

# no-depsのパッケージ一覧。依存解決・ビルド成功の確認ではない
cargo metadata --offline --locked --no-deps --format-version 1 > /tmp/rusty-kaspa-review-metadata.json
```

ワークスペース全体のテストは時間やリソースを多く使う場合がある。最初は対象パッケージを絞り、リポジトリが指定するテスト方法を優先する。

```bash
# 実際のパッケージ名を確認した上で実行する
cargo test --locked -p kaspa-math --lib -- --list
```

kaspa-mathは固定workspaceに存在する例で、--listはテストの一覧表示であり、テスト本体の実行ではない。一覧表示にもテスト対象のコンパイルは必要になる。実行する場合は必要な依存・環境を確認して--listを外す。--exact等で絞るときはmodule名を含む完全名と実際の実行件数を照合し、0件を成功件数に数えない（[Cargo testの仕様](https://doc.rust-lang.org/cargo/commands/cargo-test.html)）。今回この公式crateのテストは実行していない。

固定版metadataは59パッケージを列挙できた。生JSONにはローカルパスが含まれるため、そのまま公開記録へ追加しない。一般のRust導入だけで足りるとは限らず、READMEのProtobuf・clang/RocksDB・対象WASM toolchain等の要件を用途ごとに確認する。

### 公式スクリプト・CIと部分検査

- [check](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/check)はcargo fmt --allで書式を書き換え、workspaceと複数WASM featureのClippyを呼ぶ。読取専用の検査ではない。
- [test](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/test)はnextestのrelease/workspace/integration向けコマンドとwasm/build-nodeを呼ぶ。環境・実行対象を読んでから使う。
- [CI定義](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/.github/workflows/ci.yaml)はworkspace check、releaseテスト、docテスト、追加feature等を含む。GitHub runnerを掃除する手順まで手元へコピーしない。

ソースの表記を読んだこと、構文確認、特定crate/featureの成功、公式CI全体の成功は別の結果である。本章で公式スクリプトや上流CIを実行したわけではない。

## 36.5 コードを読む順番

巨大なコードベースを最初から順番に読む必要はない。**ユースケースから処理を追う**。

```text
ユーザー操作 / 外部イベント
           │
           ▼
     RPC / P2P入口
           │
           ▼
   入力検証・デコード
           │
           ▼
   ドメイン処理・状態遷移
           │
           ▼
    ストレージ・通知
```

例として「新しいブロックを受信したとき、何が起きるか」を調べるなら、受信処理→検証→DAGへの登録→コンセンサス順序→仮想状態更新→通知の順に、責務の境界を探す。

ただし、実装上の処理順やモジュール分割はバージョンにより異なる。上図は概念モデルであり、実際の呼び出し順序を保証するものではない。

## 36.6 C4モデルで変更範囲を把握する

### Context（システム全体）

```text
[Wallet / Application] --RPC--> [Kaspa Node] <--P2P--> [Other Nodes]
```

### Container / Component（内部責務の例）

```text
                 [Kaspa Node]
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   [RPC API]      [P2P Layer]    [Consensus]
                                      │
                               ┌──────┴──────┐
                               ▼             ▼
                           [BlockDAG]    [UTXO State]
                                      │
                                      ▼
                                   [Storage]
```

図は説明用の概念図であり、`rusty-kaspa`の実際のクレート境界をそのまま表してはいない。

**変更前の問い：**「この変更はどの責務に属するか」「誰がこのモジュールに依存しているか」「変更したら何が壊れるか」。

## 36.7 DDDの視点：用語と責務をそろえる

開発者同士で同じ用語を異なる意味で使うと、設計上の誤解が生じる。

| 用語 | 注意点 |
|---|---|
| BlockDAG | ブロック間の参照関係を表すデータ構造 |
| GHOSTDAG | BlockDAGから合意上の情報・順序を導くアルゴリズム |
| blue / red | GHOSTDAG上の分類。ブロックの有効／無効と同義ではない |
| Virtual State | 合意規則に基づいて導出される仮想的な状態 |
| UTXO | 未使用トランザクション出力。二重消費を防ぐ状態管理の基礎 |
| Finality | プロトコルのfinality point/検証と、アプリの確定ポリシーを区別する。第20章参照 |

用語の定義は、ドキュメント、コード、テスト名、レビューコメントで一致させる。

## 36.8 不変条件を先に書く

コードを変更する前に、**絶対に破ってはいけない性質（invariants）**を列挙する。

例：

- 同じUTXOを同じ状態遷移内で二重に消費しない。
- 不正なブロックによって有効な状態を破壊しない。
- 同じ入力と同じ合意ルールから、決定的な結果が得られる。
- エラーで処理が中断した場合に、中途半端な永続化状態を残さない。
- コンセンサスの判定を、受信順などの非決定的な要因に依存させない。

同じ入力には初期状態・入力DAG・ネットワーク設定・有効化文脈等も含める。受信途中のノードの観測差を、そのまま固定入力の決定性違反と扱わない。エラー時の保存契約も明示する。無効状態の記録が必要な場合や、ヘッダー保存とVirtual更新が別バッチの場合があり、Result::Errなら一切の保存がないとは一般化しない。

これらは概念的な例であり、実際のKaspaの検証規則は仕様と実装に照らして精密化する必要がある。

## 36.9 ステートマシンで変更を説明する

たとえば、アプリケーションがブロック処理の進捗を管理するなら、次のような状態遷移を設計できる。

```text
Received
   │ decode
   ▼
Decoded
   │ validate
   ├──────────► Rejected
   ▼
Validated
   │ apply
   ▼
Applied
```

**これは教育用のアプリケーション状態モデルであり、Kaspaの正式なブロック処理ステータスを列挙したものではない。**

遷移ごとに「入力」「事前条件」「成功時の状態」「失敗時の状態」「再試行の可否」を定義すると、テストの観点が明確になる。

## 36.10 初めてのIssueの探し方

いきなりコンセンサスの中核を変更するより、再現性が高く影響範囲の狭い課題から始める。

候補：

- ドキュメントと実際のCLI出力が一致しない。
- READMEのセットアップ手順が再現できない。
- エラーメッセージが原因を特定しにくい。
- テストで境界条件が抜けている。
- 既存Issueの再現条件を補足できる。

`good first issue`などのラベルが存在するかはリポジトリごとに異なる。ラベル名を決め打ちせず、現在のIssue一覧と貢献ガイドを確認する。

## 36.11 Issueを書くためのテンプレート

```markdown
## 概要
何が起きたかを一文で説明する。

## 期待する動作
どのように動くべきか。

## 実際の動作
観測された結果。

## 再現手順
1. ...
2. ...
3. ...

## 環境
- OS:
- rustc / cargo:
- rusty-kaspa commit:
- 完全なNetworkId: devnet / testnet-10 / testnet-11 / mainnet等
- 起動フラグ・feature・RPC形式/版（必要な範囲）

## ログ・証拠
公開用に最小化した証拠だけを添付。秘密鍵・シード・認証情報・個人ホームパスや不要な生ログ/DBを除く。脆弱性の疑いがあれば36.18の非公開報告経路を先に調べる。

## 補足
関連するIssue、KIP、テスト。
```

「壊れている」よりも「どの条件で何が起き、何を期待したか」が重要である。

## 36.12 Pull Requestは小さく作る

変更範囲が大きいほど、原因特定とレビューが難しくなる。

```text
大きなPR
  ├── リファクタリング
  ├── 新機能
  ├── テスト変更
  └── API変更
        ↓
レビュー困難・原因特定困難

小さなPR
  ├── 目的を1つに限定
  ├── 対応するテスト
  └── 変更理由を説明
        ↓
レビュー・検証が容易
```

既存コードの整理と動作変更を分けられるなら、別PRにすることを検討する。

## 36.13 ブランチを作り、変更を記録する

```bash
# upstreamの最新状態を確認してから作業する
# 実際の既定ブランチ名はリポジトリで確認する
git switch -c docs/clarify-rpc-example

# 変更を確認
git diff --check
git diff

git status
```

再現用の固定tagと、実PRが対象にする開発baseを区別する。作業中の差分を破棄して合わせるのではなく、必要なら別checkout/worktreeを用意する。forkのheadと上流baseを確認し、push・PR公開の前に公開対象を検査する。本章のレビューでは外部投稿やpushは行っていない。

作業前にIssueを立てるべきか、PR前にメンテナーと相談すべきかは、プロジェクトの方針に従う。

## 36.14 テストの階層

| レベル | 目的 | 例 |
|---|---|---|
| Unit | 小さな関数の正しさ | 不正入力の拒否 |
| Property-based | 広い入力範囲で不変条件を検証 | 状態遷移後の整合性 |
| Integration | コンポーネント間の結合 | RPCとノード状態の整合 |
| Differential | 異なる実装の結果を比較 | 参照モデルとの比較 |
| Devnet | 実ノードを使う検証 | 同期・再接続・再編成 |
| Performance | 性能退行の検出 | スループット・メモリ使用量 |

**テストが通ることは必要条件だが、コンセンサス安全性の十分条件ではない。**

## 36.15 既存教材へのテスト追加をPR形式で説明する

[第33章33.20の残高移転教材](../part-05-advanced/chapter-33.md#3320-rustで最小の状態遷移を作る)を使い、**未検査の境界を選び、テストを追加し、変更と検証を説明する**練習を行う。新しい残高移転モデルを作るのではなく、既存の契約とテストを読んで変更対象を絞る。

### 1. 検査したい性質を選ぶ

第33章の独立した学習用プロジェクトで、`apply_transfer` と既存テストを読む。すでに検査しているケースを確認し、追加する入力と期待結果を先に書く。

例えば、既存の通常送金に関する不足・オーバーフローテストに加え、**`u64::MAX`を持つアカウントから同じアカウントへ全額を送っても、残高が増減せず成功する**ことを調べる。同関数は残高不足を検査した後、自己送金を通常の加算から分岐するため、このケースで受取額のオーバーフローを起こしてはいけない。これは第33章の教材の契約であり、KaspaのUTXO取引の規則ではない。

### 2. テストを追加して検証する

1. 変更前のテストを実行し、結果を記録する。
2. 選んだ入力・期待結果に対応するテストを一つ追加する。上の例なら成功結果が元の残高集合全体と一致することも確認する。
3. 追加したテストと既存テストを実行する。対象を絞った場合も、実行件数が0ではないことを確認する。
4. 書式・Clippy・差分を検査する。

```bash
# 第33章の教材を置いた独立プロジェクト内で実行する
cargo test --offline
cargo fmt --all -- --check
cargo clippy --offline --all-targets -- -D warnings
git diff --check
git diff
```

既存実装が正しければ、テスト追加だけでよい。失敗した場合も、まず期待値と仕様を見直し、修正が必要な理由を説明してから動作を変更する。通常のErrで入力状態が維持されることと、panic・プロセスクラッシュ・永続化の保証は区別する。

### 3. PRの説明を作る

36.19のテンプレートを使い、問題・変更・検証結果を短くまとめる。例えば「最大残高の自己送金を明示的に検査していなかったため、既存の自己送金規則を確認する回帰テストを追加した。実装の動作変更はない」と説明する。実行したコマンド、テスト名・件数、環境と未確認範囲も記録する。

これはローカルでPR説明を作る演習であり、上流へそのまま提出する課題ではない。実際に貢献する場合は対象リポジトリの規則と既存テストを確認し、そのプロジェクトで必要な変更を選ぶ。教材は署名・権限・nonce・永続化を実装しておらず、テスト追加をKaspa本体の安全性検証とは扱わない。

## 36.16 非決定性を持ち込まない

Rustの非同期処理や並列処理は性能に有用だが、合意結果の計算では注意が必要になる。

- `HashMap`の反復順を合意順序として扱わない。
- スレッドの実行タイミングを判定結果に反映させない。
- 壁時計の時刻を、仕様にない合意条件として使わない。
- 同一入力を別のノードで処理したとき、結果が一致するかを検証する。

実際のコンセンサス規則には時刻やタイムスタンプに関する検証もあるため、「時刻を一切扱わない」という意味ではない。**仕様に定義されていない非決定性を混入させない**ことが重要である。

## 36.17 コンセンサス変更は特に慎重に扱う

コンセンサス規則を変えると、ネットワークの参加者間でブロックやトランザクションの受理結果が異なる可能性がある。

そのため、少なくとも次を検討する。

1. 変更対象の合意規則は何か。
2. 既存ノードとの互換性に影響するか。
3. KIPなどの仕様議論が必要か。
4. 有効化条件や移行手順が必要か。
5. 回帰テスト、境界テスト、敵対的入力テストをどう設計するか。
6. 再編成・同期・Pruningとの相互作用は何か。

コンセンサス変更を個人の判断だけでメインネットへ適用しない。まず仕様とコミュニティの開発プロセスを確認する。

## 36.18 セキュリティ上の問題を見つけたら

脆弱性の可能性がある場合は、**公開Issueに攻撃手順や悪用可能な詳細を投稿する前に、公式のセキュリティ報告窓口を確認する**。

- [対象リポジトリのSecurity policy](https://github.com/kaspanet/rusty-kaspa/security/policy)とSECURITY.md等を確認する。今回参照した公開ページはNo security policy detectedと表示し、基準版rootにもSECURITY.mdはなかった。
- 報告窓口を確認できなければ、公式に案内される信頼できる連絡経路を調べる。推測のメールアドレスや公開Issueへの詳細投稿で代用しない。
- 秘密鍵、シード、認証情報、個人情報をログに含めない。
- 本番ネットワークへの無許可の攻撃的検証を行わない。
- 再現用環境はローカルまたは許可されたDevnetなどに限定する。

## 36.19 Pull Requestの説明テンプレート

```markdown
## 問題と変更後の動作
何が起きる条件で、変更前後の結果がどう変わるか。

## 変更内容と根拠
主要な変更、仕様・ソースへの参照、必要な設計上の判断。

既存動作への影響と、必要なら移行・有効化手順。
```

小さな文書PRへ全項目を機械的に埋める必要はない。変更規模に合わせ、レビュアーが問題・変更・検証を追える説明にする。実行していないテストを「成功」と書かない。レビュー担当者が検証を再現できる情報を残す。

## 36.20 レビューコメントへの向き合い方

コードレビューは、作者の能力評価ではなく、変更の妥当性を共同で確認する工程である。

- 指摘の意図が不明なら、具体例を求める。
- 設計上の代替案があれば、メリットとコストを説明する。
- 指摘を反映したら、何をどう変更したか返信する。
- 大きな方針の違いは、コード修正の前に認識をそろえる。

**「なぜこの設計か」を説明できること**が、実装の速さと同じくらい重要になる。

## 36.21 実験と失敗を成果物にする

性能調査やコンセンサス実験では、結果だけでなく条件を記録する。

```text
experiments/
└── block-processing-latency/
    ├── README.md
    ├── environment.md
    ├── run.sh
    ├── results.csv
    └── findings.md
```

この配置は提案例で、本章で新規実験ディレクトリを作成したわけではない。公開するのは最小限の整理済み記録とし、機密情報を含むrawログ/DB等をそのまま収録しない。

最低限記録したい項目：

- 実験の仮説
- リポジトリのコミットID
- OS、CPU、メモリ、Rustバージョン
- ネットワーク条件とデータセット
- 実行コマンド
- 観測結果と失敗例
- 解釈上の限界

再現できないベンチマークは、改善の根拠として使いにくい。

## 36.22 Mastering Kaspa自体もコントリビュートになる

技術書を公開することも、開発者コミュニティへの貢献になり得る。ただし、**説明の正確性を維持する仕組み**が必要である。

推奨する各章の管理項目：

```markdown
> 検証対象バージョン: <commit / release>
> 一次資料: <URL>
> コード実行: 実施 / 未実施
> 最終技術レビュー日: YYYY-MM-DD
> 未確認事項: ...
```

特に「KIPに提案されている」「実装コードが存在する」「メインネットで有効化された」は別の状態として記述する。

## 36.23 コントリビュートの実践ロードマップ

### Step 1 — 読む

- `rusty-kaspa`のREADMEと開発ガイドを読む。
- ひとつのユースケースを選び、処理経路を追う。
- 分からない用語を公式資料で確認する。

### Step 2 — 再現する

- ローカルでビルドまたは対象パッケージのテストを実行する。
- Issueや文書の問題を再現する。
- 環境と結果を記録する。

### Step 3 — 小さく直す

- 変更目的を一つに限定する。
- 必要なテストを追加する。
- 差分を確認し、PRを提出する。

### Step 4 — 深める

- コンセンサス・ストレージ・P2Pの境界を調査する。
- 回帰テストや再現実験を充実させる。
- KIPと実装の対応を追跡する。

締切よりも、**再現できる成果物を継続的に積み重ねること**を重視する。

## 36.24 最初のPR候補を選ぶ評価表

候補ごとに次の問いに答える。

| 観点 | 質問 |
|---|---|
| 再現性 | 問題を手元で再現できるか |
| 影響範囲 | 変更するモジュールは限定されるか |
| 検証 | 失敗するテストを先に書けるか |
| 互換性 | 外部APIや合意規則を変更しないか |
| 説明可能性 | 変更理由を第三者に説明できるか |
| レビュー負荷 | 小さな差分に分割できるか |

最初の貢献では、再現性と検証可能性を優先する。

## 36.25 実践演習A：ドキュメントの改善

1. READMEまたは開発者向け文書を一つ選ぶ。
2. 手順を最初から実行する。
3. 再現できなかった箇所を記録する。
4. 実際に確認できた内容だけを修正する。
5. 変更前後の違いをPRで説明する。

**完了条件：** 別の開発者が、修正した手順を使って同じ結果を再現できる。

## 36.26 実践演習B：回帰テスト

1. 再現可能なIssueを一つ選ぶ。
2. 現状の振る舞いを記録する。
3. 問題を再現するテストを追加する。
4. 必要なら最小の修正を加える。
5. テストの成功だけでなく、周辺機能への影響も確認する。

**完了条件：** 問題が再発したときにテストが検出できる。

## 36.27 実践演習C：アーキテクチャ調査

題材：「受信ブロックがコンセンサス処理へ渡るまで」。

以下を作成する。

- C4コンポーネント図
- 呼び出し経路のメモ
- モジュール間の依存関係
- 入力検証の位置
- エラー処理の経路
- 対応するテストの一覧

**完了条件：** 他の開発者が、同じコミットから同じ処理経路を追跡できる。

## 36.28 よくある失敗

| 失敗 | 改善策 |
|---|---|
| コード全体を理解してから着手しようとする | 一つのユースケースから追う |
| テストせずにPRを出す | 再現条件とテスト結果を添える |
| リファクタリングと機能変更を混ぜる | PRを分ける |
| 仕様を確認せず合意規則を変える | KIP・仕様・メンテナーの方針を確認する |
| AI生成コードを検証せず提出する | 自分で動作と不変条件を説明できる状態にする |
| 最新の実装状況を推測で書く | コミットと一次資料を示す |

## 36.29 AIを使った開発と責任

AIはコード探索、テスト案の列挙、ドキュメントの下書きに役立つ。しかし、生成された説明やコードが正しいとは限らない。

特にKaspaのようなコンセンサス実装では、次の確認が必要になる。

1. 生成された関数名・パスは実在するか。
2. 提案された変更は現在の仕様と整合するか。
3. 境界条件と失敗時の状態を検証したか。
4. テストは本当に実行したか。
5. PRの変更内容を自分の言葉で説明できるか。

AI利用・開示の方針もプロジェクトごとに確認する。AIの利用が認められていても、提案の根拠・検証結果・提出内容への責任は投稿者が持つ。

## 36.30 最終チェックリスト

PR提出前に確認する。

- [ ] 対象Issueまたは課題を説明できる
- [ ] リポジトリの開発ルールを確認した
- [ ] 変更範囲が明確である
- [ ] 不変条件と失敗時の動作を確認した
- [ ] 関連テストを実行した
- [ ] `git diff --check`を実行した
- [ ] 実行していない検証を明記した
- [ ] 互換性・セキュリティへの影響を検討した
- [ ] ログに秘密情報が含まれていない
- [ ] レビュアーが再現できる説明を書いた

## 36.31 理解度チェック

1. コードを書かない貢献には何があるか。

本書では、デジタルマネーと暗号技術の基礎から始め、BlockDAG、GHOSTDAG、UTXO、マイニング、P2P、Rust実装、Devnet、L2、プログラマビリティまでを扱ってきた。
