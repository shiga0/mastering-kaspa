# Chapter 36 — Contributing to Kaspa（Kaspaへのコントリビュート）

> **原稿ステータス：v0.1（技術レビュー前）**  
> この章は、Kaspaのオープンソース開発に参加するための実践ガイドである。リポジトリ構成、開発手順、CI、メンテナーの方針は変化するため、作業時点の一次資料を確認すること。

## この章で学ぶこと

- Kaspaへの貢献を、コード・テスト・文書・検証・研究に分解する。
- `rusty-kaspa`の変更箇所を特定し、安全に小さなPull Requestを作る。
- コンセンサスの変更と通常のアプリケーション変更で必要な検証が異なる理由を説明する。
- 不変条件・状態遷移・依存関係を明確にした上で変更を進める。
- 失敗や実験結果を、他の開発者が再現できる形で残す。

---

## 36.1 コントリビュートとは何か

コントリビュート（contribution）は、ソースコードを追加することだけではない。Kaspaのような分散システムでは、仕様の曖昧さを発見する、再現可能なバグ報告を作る、テストを増やす、ドキュメントを修正することも重要な貢献になる。

| 種類 | 例 | 成果物 |
|---|---|---|
| ドキュメント | RPCの説明を修正する | 文書PR |
| テスト | 再編成時の境界条件を検証する | 回帰テスト |
| バグ修正 | エラー処理の不備を直す | 小さなコードPR |
| 開発者体験 | ローカル構築手順を改善する | スクリプト・README |
| 性能調査 | 同期処理のボトルネックを測る | ベンチマーク・レポート |
| 研究・仕様 | コンセンサス変更の妥当性を議論する | 論文レビュー・KIPへのフィードバック |

**重要：** 価値は変更行数では決まらない。小さくても、検証可能で、保守しやすい変更は大きな貢献になり得る。

## 36.2 Kaspaの開発に参加する前に

最低限、次の区別を理解しておこう。

1. **プロトコル仕様**：ネットワーク参加者が従うべき合意規則。
2. **実装**：仕様をRustなどのコードに落とし込んだもの。
3. **テスト**：実装が期待する性質を満たすか検証するもの。
4. **運用**：ノードの同期、監視、障害対応、アップグレード。
5. **アプリケーション**：RPCやSDKを通じてKaspaを利用するもの。

たとえばRPCの表示形式を改善する変更と、ブロックの受理条件を変える変更では、リスクもレビューの重さも大きく異なる。

## 36.3 一次資料と作業対象

最初に参照する資料は次のとおり。

- [kaspanet/rusty-kaspa](https://github.com/kaspanet/rusty-kaspa) — Rustノード実装
- [kaspanet/kips](https://github.com/kaspanet/kips) — Kaspa Improvement Proposals
- [Kaspa Wiki](https://wiki.kaspa.org/) — 技術情報の入口
- [Kaspa公式サイト](https://kaspa.org/) — プロジェクトの公式情報
- [Rust公式ドキュメント](https://doc.rust-lang.org/book/) — Rust言語の基礎
- [Cargo Book](https://doc.rust-lang.org/cargo/) — ビルド・テスト・ワークスペース

**注意：** リポジトリに`CONTRIBUTING.md`やIssueテンプレートが存在するか、どのブランチを基準にするか、必要なツールチェーンは何かを、実際の作業時点で確認する。本章は特定のブランチ構成を前提にしない。

## 36.4 開発環境の準備

以下は一般的なRustプロジェクトとしての準備例であり、実際の必須コマンドはリポジトリのREADMEに従う。

```bash
# リポジトリを取得
git clone https://github.com/kaspanet/rusty-kaspa.git
cd rusty-kaspa

# 現在の状態を記録
git rev-parse HEAD
rustc --version
cargo --version

# 利用可能なパッケージを確認
cargo metadata --no-deps --format-version 1 > /tmp/rusty-kaspa-metadata.json
```

ワークスペース全体のテストは時間やリソースを多く使う場合がある。最初は対象パッケージを絞り、リポジトリが指定するテスト方法を優先する。

```bash
# 実際のパッケージ名を確認した上で実行する
cargo test -p <package-name>
```

`<package-name>`はプレースホルダーであり、そのまま実行しない。

## 36.5 コードを読む順番

巨大なコードベースを最初から順番に読む必要はない。**ユースケースから処理を追う**。

```text
ユーザー操作 / 外部イベント
           │
           ▼
     RPC / P2P入口
           │
           ▼
   入力検証・デコード
           │
           ▼
   ドメイン処理・状態遷移
           │
           ▼
    ストレージ・通知
```

例として「新しいブロックを受信したとき、何が起きるか」を調べるなら、受信処理→検証→DAGへの登録→コンセンサス順序→仮想状態更新→通知の順に、責務の境界を探す。

ただし、実装上の処理順やモジュール分割はバージョンにより異なる。上図は概念モデルであり、実際の呼び出し順序を保証するものではない。

## 36.6 C4モデルで変更範囲を把握する

### Context（システム全体）

```text
[Wallet / Application] --RPC--> [Kaspa Node] <--P2P--> [Other Nodes]
```

### Container / Component（内部責務の例）

```text
                 [Kaspa Node]
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   [RPC API]      [P2P Layer]    [Consensus]
                                      │
                               ┌──────┴──────┐
                               ▼             ▼
                           [BlockDAG]    [UTXO State]
                                      │
                                      ▼
                                   [Storage]
```

図は説明用の概念図であり、`rusty-kaspa`の実際のクレート境界をそのまま表してはいない。

**変更前の問い：**「この変更はどの責務に属するか」「誰がこのモジュールに依存しているか」「変更したら何が壊れるか」。

## 36.7 DDDの視点：用語と責務をそろえる

開発者同士で同じ用語を異なる意味で使うと、設計上の誤解が生じる。

| 用語 | 注意点 |
|---|---|
| BlockDAG | ブロック間の参照関係を表すデータ構造 |
| GHOSTDAG | BlockDAGから合意上の情報・順序を導くアルゴリズム |
| blue / red | GHOSTDAG上の分類。ブロックの有効／無効と同義ではない |
| Virtual State | 合意規則に基づいて導出される仮想的な状態 |
| UTXO | 未使用トランザクション出力。二重消費を防ぐ状態管理の基礎 |
| Finality | 何をもってトランザクションを十分確定したと扱うかという性質・運用判断 |

用語の定義は、ドキュメント、コード、テスト名、レビューコメントで一致させる。

## 36.8 不変条件を先に書く

コードを変更する前に、**絶対に破ってはいけない性質（invariants）**を列挙する。

例：

- 同じUTXOを同じ状態遷移内で二重に消費しない。
- 不正なブロックによって有効な状態を破壊しない。
- 同じ入力と同じ合意ルールから、決定的な結果が得られる。
- エラーで処理が中断した場合に、中途半端な永続化状態を残さない。
- コンセンサスの判定を、受信順などの非決定的な要因に依存させない。

これらは概念的な例であり、実際のKaspaの検証規則は仕様と実装に照らして精密化する必要がある。

## 36.9 ステートマシンで変更を説明する

たとえば、アプリケーションがブロック処理の進捗を管理するなら、次のような状態遷移を設計できる。

```text
Received
   │ decode
   ▼
Decoded
   │ validate
   ├──────────► Rejected
   ▼
Validated
   │ apply
   ▼
Applied
```

**これは教育用のアプリケーション状態モデルであり、Kaspaの正式なブロック処理ステータスを列挙したものではない。**

遷移ごとに「入力」「事前条件」「成功時の状態」「失敗時の状態」「再試行の可否」を定義すると、テストの観点が明確になる。

## 36.10 初めてのIssueの探し方

いきなりコンセンサスの中核を変更するより、再現性が高く影響範囲の狭い課題から始める。

候補：

- ドキュメントと実際のCLI出力が一致しない。
- READMEのセットアップ手順が再現できない。
- エラーメッセージが原因を特定しにくい。
- テストで境界条件が抜けている。
- 既存Issueの再現条件を補足できる。

`good first issue`などのラベルが存在するかはリポジトリごとに異なる。ラベル名を決め打ちせず、現在のIssue一覧と貢献ガイドを確認する。

## 36.11 Issueを書くためのテンプレート

```markdown
## 概要
何が起きたかを一文で説明する。

## 期待する動作
どのように動くべきか。

## 実際の動作
観測された結果。

## 再現手順
1. ...
2. ...
3. ...

## 環境
- OS:
- rustc / cargo:
- rusty-kaspa commit:
- Network: devnet / testnet / mainnet（該当するもの）

## ログ・証拠
秘密鍵、シードフレーズ、認証情報を除去して添付。

## 補足
関連するIssue、KIP、テスト。
```

「壊れている」よりも「どの条件で何が起き、何を期待したか」が重要である。

## 36.12 Pull Requestは小さく作る

変更範囲が大きいほど、原因特定とレビューが難しくなる。

```text
大きなPR
  ├── リファクタリング
  ├── 新機能
  ├── テスト変更
  └── API変更
        ↓
レビュー困難・原因特定困難

小さなPR
  ├── 目的を1つに限定
  ├── 対応するテスト
  └── 変更理由を説明
        ↓
レビュー・検証が容易
```

既存コードの整理と動作変更を分けられるなら、別PRにすることを検討する。

## 36.13 ブランチを作り、変更を記録する

```bash
# upstreamの最新状態を確認してから作業する
# 実際の既定ブランチ名はリポジトリで確認する
git switch -c docs/clarify-rpc-example

# 変更を確認
git diff --check
git diff

git status
```

作業前にIssueを立てるべきか、PR前にメンテナーと相談すべきかは、プロジェクトの方針に従う。

## 36.14 テストの階層

| レベル | 目的 | 例 |
|---|---|---|
| Unit | 小さな関数の正しさ | 不正入力の拒否 |
| Property-based | 広い入力範囲で不変条件を検証 | 状態遷移後の整合性 |
| Integration | コンポーネント間の結合 | RPCとノード状態の整合 |
| Differential | 異なる実装の結果を比較 | 参照モデルとの比較 |
| Devnet | 実ノードを使う検証 | 同期・再接続・再編成 |
| Performance | 性能退行の検出 | スループット・メモリ使用量 |

**テストが通ることは必要条件だが、コンセンサス安全性の十分条件ではない。**

## 36.15 Rustで不変条件をテストする小さな例

以下は、Kaspa本体ではなく、状態遷移の原子性を学ぶための独立したRust例である。

```rust
use std::collections::HashMap;

#[derive(Debug, Clone, PartialEq, Eq)]
struct Ledger {
    balances: HashMap<String, u64>,
}

#[derive(Debug, PartialEq, Eq)]
enum TransferError {
    MissingAccount,
    InsufficientFunds,
    Overflow,
}

impl Ledger {
    fn transfer(&mut self, from: &str, to: &str, amount: u64) -> Result<(), TransferError> {
        let from_balance = *self.balances.get(from).ok_or(TransferError::MissingAccount)?;
        let to_balance = *self.balances.get(to).ok_or(TransferError::MissingAccount)?;

        if from == to {
            return Ok(());
        }
        let new_from = from_balance.checked_sub(amount)
            .ok_or(TransferError::InsufficientFunds)?;
        let new_to = to_balance.checked_add(amount)
            .ok_or(TransferError::Overflow)?;

        // 全ての検証が成功してから更新する。
        self.balances.insert(from.to_string(), new_from);
        self.balances.insert(to.to_string(), new_to);
        Ok(())
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    fn sample() -> Ledger {
        Ledger {
            balances: HashMap::from([
                ("alice".to_string(), 10),
                ("bob".to_string(), 5),
            ]),
        }
    }

    #[test]
    fn transfer_preserves_total() {
        let mut ledger = sample();
        ledger.transfer("alice", "bob", 4).unwrap();
        assert_eq!(ledger.balances["alice"], 6);
        assert_eq!(ledger.balances["bob"], 9);
    }

    #[test]
    fn rejected_transfer_does_not_mutate_state() {
        let mut ledger = sample();
        let before = ledger.clone();
        assert_eq!(ledger.transfer("alice", "bob", 100), Err(TransferError::InsufficientFunds));
        assert_eq!(ledger, before);
    }

    #[test]
    fn overflow_does_not_mutate_state() {
        let mut ledger = sample();
        ledger.balances.insert("bob".to_string(), u64::MAX);
        let before = ledger.clone();
        assert_eq!(ledger.transfer("alice", "bob", 1), Err(TransferError::Overflow));
        assert_eq!(ledger, before);
    }

    #[test]
    fn self_transfer_is_noop() {
        let mut ledger = sample();
        let before = ledger.clone();
        ledger.transfer("alice", "alice", 3).unwrap();
        assert_eq!(ledger, before);
    }
}
```

この例で確認できるのは、**検証完了前に状態を変更しない**という基本原則である。実際のKaspaではUTXO、DAG、仮想状態、永続化などが絡むため、同じ原則をより複雑な境界で守る必要がある。

## 36.16 非決定性を持ち込まない

Rustの非同期処理や並列処理は性能に有用だが、合意結果の計算では注意が必要になる。

- `HashMap`の反復順を合意順序として扱わない。
- スレッドの実行タイミングを判定結果に反映させない。
- 壁時計の時刻を、仕様にない合意条件として使わない。
- 同一入力を別のノードで処理したとき、結果が一致するかを検証する。

実際のコンセンサス規則には時刻やタイムスタンプに関する検証もあるため、「時刻を一切扱わない」という意味ではない。**仕様に定義されていない非決定性を混入させない**ことが重要である。

## 36.17 コンセンサス変更は特に慎重に扱う

コンセンサス規則を変えると、ネットワークの参加者間でブロックやトランザクションの受理結果が異なる可能性がある。

そのため、少なくとも次を検討する。

1. 変更対象の合意規則は何か。
2. 既存ノードとの互換性に影響するか。
3. KIPなどの仕様議論が必要か。
4. 有効化条件や移行手順が必要か。
5. 回帰テスト、境界テスト、敵対的入力テストをどう設計するか。
6. 再編成・同期・Pruningとの相互作用は何か。

コンセンサス変更を個人の判断だけでメインネットへ適用しない。まず仕様とコミュニティの開発プロセスを確認する。

## 36.18 セキュリティ上の問題を見つけたら

脆弱性の可能性がある場合は、**公開Issueに攻撃手順や悪用可能な詳細を投稿する前に、公式のセキュリティ報告窓口を確認する**。

- リポジトリのSecurityタブや`SECURITY.md`を確認する。
- 秘密鍵、シード、認証情報、個人情報をログに含めない。
- 本番ネットワークへの無許可の攻撃的検証を行わない。
- 再現用環境はローカルまたは許可されたDevnetなどに限定する。

## 36.19 Pull Requestの説明テンプレート

```markdown
## 目的
何の問題を解決するか。

## 変更内容
- ...
- ...

## 変更しないこと
今回のスコープ外を明記する。

## 設計上の判断
責務分離、依存関係、トレードオフを説明する。

## 不変条件
変更前後で守るべき性質を列挙する。

## 検証
- 実行したコマンド:
- 成功したテスト:
- 未実施のテストと理由:

## 互換性・リスク
既存動作への影響、必要なら移行手順。

## 関連Issue / KIP
リンクを記載する。
```

実行していないテストを「成功」と書かない。レビュー担当者が検証を再現できる情報を残す。

## 36.20 レビューコメントへの向き合い方

コードレビューは、作者の能力評価ではなく、変更の妥当性を共同で確認する工程である。

- 指摘の意図が不明なら、具体例を求める。
- 設計上の代替案があれば、メリットとコストを説明する。
- 指摘を反映したら、何をどう変更したか返信する。
- 大きな方針の違いは、コード修正の前に認識をそろえる。

**「なぜこの設計か」を説明できること**が、実装の速さと同じくらい重要になる。

## 36.21 実験と失敗を成果物にする

性能調査やコンセンサス実験では、結果だけでなく条件を記録する。

```text
experiments/
└── block-processing-latency/
    ├── README.md
    ├── environment.md
    ├── run.sh
    ├── results.csv
    └── findings.md
```

最低限記録したい項目：

- 実験の仮説
- リポジトリのコミットID
- OS、CPU、メモリ、Rustバージョン
- ネットワーク条件とデータセット
- 実行コマンド
- 観測結果と失敗例
- 解釈上の限界

再現できないベンチマークは、改善の根拠として使いにくい。

## 36.22 Mastering Kaspa自体もコントリビュートになる

技術書を公開することも、開発者コミュニティへの貢献になり得る。ただし、**説明の正確性を維持する仕組み**が必要である。

推奨する各章の管理項目：

```markdown
> 検証対象バージョン: <commit / release>
> 一次資料: <URL>
> コード実行: 実施 / 未実施
> 最終技術レビュー日: YYYY-MM-DD
> 未確認事項: ...
```

特に「KIPに提案されている」「実装コードが存在する」「メインネットで有効化された」は別の状態として記述する。

## 36.23 コントリビュートの実践ロードマップ

### Step 1 — 読む

- `rusty-kaspa`のREADMEと開発ガイドを読む。
- ひとつのユースケースを選び、処理経路を追う。
- 分からない用語を公式資料で確認する。

### Step 2 — 再現する

- ローカルでビルドまたは対象パッケージのテストを実行する。
- Issueや文書の問題を再現する。
- 環境と結果を記録する。

### Step 3 — 小さく直す

- 変更目的を一つに限定する。
- 必要なテストを追加する。
- 差分を確認し、PRを提出する。

### Step 4 — 深める

- コンセンサス・ストレージ・P2Pの境界を調査する。
- 回帰テストや再現実験を充実させる。
- KIPと実装の対応を追跡する。

締切よりも、**再現できる成果物を継続的に積み重ねること**を重視する。

## 36.24 最初のPR候補を選ぶ評価表

候補ごとに次の問いに答える。

| 観点 | 質問 |
|---|---|
| 再現性 | 問題を手元で再現できるか |
| 影響範囲 | 変更するモジュールは限定されるか |
| 検証 | 失敗するテストを先に書けるか |
| 互換性 | 外部APIや合意規則を変更しないか |
| 説明可能性 | 変更理由を第三者に説明できるか |
| レビュー負荷 | 小さな差分に分割できるか |

最初の貢献では、再現性と検証可能性を優先する。

## 36.25 実践演習A：ドキュメントの改善

1. READMEまたは開発者向け文書を一つ選ぶ。
2. 手順を最初から実行する。
3. 再現できなかった箇所を記録する。
4. 実際に確認できた内容だけを修正する。
5. 変更前後の違いをPRで説明する。

**完了条件：** 別の開発者が、修正した手順を使って同じ結果を再現できる。

## 36.26 実践演習B：回帰テスト

1. 再現可能なIssueを一つ選ぶ。
2. 現状の振る舞いを記録する。
3. 問題を再現するテストを追加する。
4. 必要なら最小の修正を加える。
5. テストの成功だけでなく、周辺機能への影響も確認する。

**完了条件：** 問題が再発したときにテストが検出できる。

## 36.27 実践演習C：アーキテクチャ調査

題材：「受信ブロックがコンセンサス処理へ渡るまで」。

以下を作成する。

- C4コンポーネント図
- 呼び出し経路のメモ
- モジュール間の依存関係
- 入力検証の位置
- エラー処理の経路
- 対応するテストの一覧

**完了条件：** 他の開発者が、同じコミットから同じ処理経路を追跡できる。

## 36.28 よくある失敗

| 失敗 | 改善策 |
|---|---|
| コード全体を理解してから着手しようとする | 一つのユースケースから追う |
| テストせずにPRを出す | 再現条件とテスト結果を添える |
| リファクタリングと機能変更を混ぜる | PRを分ける |
| 仕様を確認せず合意規則を変える | KIP・仕様・メンテナーの方針を確認する |
| AI生成コードを検証せず提出する | 自分で動作と不変条件を説明できる状態にする |
| 最新の実装状況を推測で書く | コミットと一次資料を示す |

## 36.29 AIを使った開発と責任

AIはコード探索、テスト案の列挙、ドキュメントの下書きに役立つ。しかし、生成された説明やコードが正しいとは限らない。

特にKaspaのようなコンセンサス実装では、次の確認が必要になる。

1. 生成された関数名・パスは実在するか。
2. 提案された変更は現在の仕様と整合するか。
3. 境界条件と失敗時の状態を検証したか。
4. テストは本当に実行したか。
5. PRの変更内容を自分の言葉で説明できるか。

**AIを使ったことではなく、検証していないことが問題になる。**

## 36.30 最終チェックリスト

PR提出前に確認する。

- [ ] 対象Issueまたは課題を説明できる
- [ ] リポジトリの開発ルールを確認した
- [ ] 変更範囲が明確である
- [ ] 不変条件と失敗時の動作を確認した
- [ ] 関連テストを実行した
- [ ] `git diff --check`を実行した
- [ ] 実行していない検証を明記した
- [ ] 互換性・セキュリティへの影響を検討した
- [ ] ログに秘密情報が含まれていない
- [ ] レビュアーが再現できる説明を書いた

## 36.32 本書のまとめ：理解から実装、そして貢献へ

本書では、デジタルマネーと暗号技術の基礎から始め、BlockDAG、GHOSTDAG、UTXO、マイニング、P2P、Rust実装、Devnet、L2、プログラマビリティまでを扱ってきた。

最後に必要なのは、知識を**他の人が検証できる成果物**へ変えることである。

```text
概念を学ぶ
    │
    ▼
問題を定義する
    │
    ▼
設計と不変条件を書く
    │
    ▼
最小実装・再現実験
    │
    ▼
テストと証拠を残す
    │
    ▼
Issue / PR / 技術文書
    │
    ▼
レビューと改善
```

Kaspaへのコントリビュートは、完成した専門家だけの活動ではない。**調べたことを正確に記録し、再現できる形で共有すること**から始められる。
