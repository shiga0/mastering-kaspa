## 1. はじめに

これまでの章では、デジタルマネー、暗号技術、分散システム、Bitcoinのアーキテクチャ、従来型ブロックチェーンの制約、そしてBlockDAGの基礎を学んだ。

ここで考えたいのは、**なぜBitcoin型のチェーンからKaspa型のBlockDAGへ設計を変える必要があったのか**、そして**データ構造を変えることで、コンセンサスやノード実装の何が変わるのか**という問題である。

Kaspaは、Proof of Work（PoW）を維持しながら、ブロック同士の並行関係をBlockDAGとして記録し、GHOSTDAGによって一貫した順序を導くネットワークである。

重要なのは「チェーンをDAGに置き換えたら自動的に高速になる」という理解ではない。BlockDAGは並行性を表現する**データ構造**であり、その上で動く**合意規則**、**トランザクション検証**、**ネットワーク通信**、**ストレージ**を一体として設計する必要がある。

本章では、これまで学んだ要素を一つのアーキテクチャとして接続する。

## 3. Bitcoinから出発する

### 3.1 Bitcoinが解決した問題

Bitcoinは、中央管理者のいないネットワークで、参加者が同じ台帳の履歴について合意する仕組みを提示した。

そのために、主として次の要素を組み合わせている。

| 要素 | 主な役割 |
|---|---|
| デジタル署名 | 資金を使用する権限を証明する |
| UTXO | 使用可能なトランザクション出力を管理する |
| P2Pネットワーク | トランザクションとブロックを伝播する |
| Proof of Work | ブロック生成に計算コストを要求する |
| チェーン選択規則 | 競合する履歴から有効な履歴を選択する |
| ブロック検証 | プロトコル規則に違反するブロックを拒否する |

これらは独立した機能ではない。例えば、署名が正しくても、すでに使用されたUTXOを再び使うことはできない。UTXOの使用可否は、どのトランザクションがどの順序で有効になったかに依存する。

### 3.2 なぜ一本のチェーンが重要だったのか

Bitcoinでは、ブロックが原則として一つの親を参照する。

```text
Genesis → A → B → C → D
                  
                   └─ C'（競合するブロック）
```

ノードは、有効なチェーンのうち累積作業量が最大となるものを選ぶ。これにより、各参加者が一時的に異なる履歴を見ていても、ネットワークが伝播・採掘を続けることで共通の履歴に収束することを目指す。

この構造は理解しやすい一方、ほぼ同時に生成されたブロックが同じ高さで競合すると、一方が主チェーンから外れることがある。

## 4. ブロック生成を速くすると何が起きるか

### 4.1 生成間隔と伝播遅延

ブロックがネットワーク全体に伝わるには時間がかかる。あるマイナーが新しいブロックを発見しても、遠く離れたマイナーは古い先端を基準に採掘を続けている可能性がある。

```text
時間 ───────────────────────────→

Miner A:  発見 B ──→ 伝播 ───────────→
Miner B:      古い先端を採掘 ─→ 発見 C
Miner C:           Bを受信 ─→ 次の候補

B と C が同じ親を持つ場合、競合が生じる。
```

平均ブロック生成間隔を短くすると、前のブロックが伝播し終わる前に次のブロックが見つかる機会が増える。

**ブロック生成頻度を上げることと、ネットワーク全体で即座に同じ状態を観測できることは別問題**である。

### 4.2 単純化した確率モデル

学習用に、ブロック発見が一定率のポアソン過程に従うと仮定する。平均ブロック生成間隔を `T` 秒、伝播時間を `d` 秒とすると、その時間内に少なくとも一つの別ブロックが発見される確率は、次のように表せる。

\[
P(N(d) \ge 1) = 1 - e^{-d/T}
\]

例えば `d = 1秒` と仮定すると、以下のようになる。

| 平均生成間隔 T | 伝播時間 d | その間に別ブロックが発見される確率（近似） |
|---|---:|---:|
| 600秒 | 1秒 | 約0.17% |
| 10秒 | 1秒 | 約9.52% |
| 1秒 | 1秒 | 約63.21% |

このモデルは、ネットワークの伝播遅延を一定とする単純化であり、**実際のステール率、Kaspaのセキュリティ、確定時間を直接予測するものではない**。マイナーの地理的分布、ハッシュパワー、伝播方式、ブロックサイズ、敵対的行動などは含まれていない。

この計算から読み取れるのは、**高頻度のブロック生成を目指すほど、並行ブロックを例外ではなく通常の事象として扱う設計が重要になる**という点である。

## 5. チェーンからBlockDAGへ

### 5.1 一つの親から複数の親へ

Bitcoin型のチェーンでは、各ブロックは基本的に一つの親を参照する。

KaspaのBlockDAGでは、ブロックが複数の親を参照できる。

```text
          Genesis
             │
             A
           ／ ＼
          B     C
           ＼ ／
             D
           ／ ＼
          E     F
           ＼ ／
             G
```

図では読みやすさのため親から子へ線を描いているが、実際にブロックが保持する参照は**子から親**へ向かう。例えばDはBとCを参照する。

BとCは互いを祖先としていないため、DAG上で並行した関係にある。

### 5.2 BlockDAGが解決すること、解決しないこと

BlockDAGは、競合したブロックの参照関係を同じグラフの中に保持できる。

しかし、DAGにブロックを保存できることと、そのブロック内の全トランザクションが有効になることは同じではない。

例えば、BとCが同じUTXOを使用するトランザクションを含んでいた場合、両方の支出を承認することはできない。

```text
              UTXO X
             ／    ＼
      Tx B: Xを使用   Tx C: Xを使用
             ＼    ／
           二重支払い競合
```

必要なのは、**DAG上のブロックから一貫した処理順序を導き、その順序に従ってトランザクションの有効性を判定すること**である。

## 6. GHOSTDAGが必要になる理由

GHOSTDAGは、KaspaのBlockDAG上でブロックを分類し、順序付けるコンセンサスアルゴリズムである。

### 6.1 データ構造と合意規則を分けて考える

| 層 | 問い | Kaspaにおける主な仕組み |
|---|---|---|
| データ構造 | ブロック間の関係をどう保存するか | BlockDAG |
| 合意規則 | どのようにブロックを分類・順序付けするか | GHOSTDAGなどのコンセンサス規則 |
| 状態遷移 | どのトランザクションをどの順序で適用するか | トランザクション検証・UTXO状態 |
| 通信 | ブロックをどう共有するか | P2Pプロトコル |
| 実装 | 上記をどう安全に動かすか | rusty-kaspaなど |

**BlockDAGそのものはコンセンサスアルゴリズムではない。**

### 6.2 GHOSTDAGの主要概念

| 用語 | この章での理解 |
|---|---|
| Past | ブロックから親参照をたどって到達できる過去のブロック |
| Future | そのブロックを祖先として参照する将来のブロック |
| Anticone | 互いに祖先・子孫関係にないブロックの集合 |
| Selected Parent | コンセンサス規則によって選択される親 |
| blue / red | GHOSTDAGの規則に基づく分類。単純な有効・無効の意味ではない |
| blue score | 選択された過去のblueブロックに基づく指標 |
| Virtual Block | 現在のDAG先端を基にコンセンサス状態を考える仮想的なブロック |

GHOSTDAGは、ブロックを単純に発見時刻で並べるわけではない。ブロック間の参照関係とアルゴリズムの規則を使って、ノードが同じ順序を計算できるようにする。

具体的なselected parentの選択、blue set、`k`パラメータ、順序付けの詳細は第12章で扱う。

### 6.3 PHANTOMとの関係

Kaspaの背景には、PHANTOMとGHOSTDAGに関する研究がある。PHANTOMはBlockDAG上のコンセンサスを研究する枠組みであり、GHOSTDAGはその系譜に属する実用的な順序付け手法である。

ここでは両者を同一視せず、**論文で提案された概念と、現行ノードに実装された規則を区別して読む**ことが重要である。

## 7. BlockDAGからUTXO状態へ

### 7.1 ブロックの順序とトランザクションの順序

DAGの中には、複数のブロックが並行して存在できる。しかし、UTXOは「使用済みか未使用か」を一貫して判定する必要がある。

概念的には、次の流れになる。

```text
P2Pでブロックを受信
        │
        ▼
ブロックの基本検証
        │
        ▼
BlockDAGへ取り込み
        │
        ▼
GHOSTDAGによる分類・順序付け
        │
        ▼
コンセンサス順序に沿った取引処理
        │
        ▼
UTXO状態の更新
```

※ これは理解用の概念図であり、実際の`rusty-kaspa`の関数呼び出し順序や並列実行構造を正確に写したものではない。

### 7.2 トランザクションがDAGに含まれるだけでは不十分

例えば、次の2つのトランザクションを考える。

- `Tx A`：UTXO `X`をAliceからBobへ送る。
- `Tx B`：同じUTXO `X`をAliceからCarolへ送る。

両方のトランザクションが異なるブロックに含まれたとしても、二重支払いは許されない。

コンセンサスが定める順序と検証規則によって、どのトランザクションが有効な状態遷移を構成するかが決まる。

ここに、**ブロックの包含（inclusion）とトランザクションの受理（acceptance）を区別する必要性**がある。

### 7.3 Virtual State

Kaspaでは、DAGの先端（tips）を踏まえた仮想的な状態を計算する考え方が重要になる。

チェーンであれば「現在の先端」を一つのブロックとして想像しやすいが、DAGには複数の先端が存在しうる。

このため、Virtual BlockやVirtual Stateという概念を通じて、現在のコンセンサス状態を理解する。

詳細は第14章「Consensus Ordering & Virtual State」で扱う。

## 9. BitcoinとKaspaを設計上の選択として比較する

| 観点 | Bitcoin | Kaspa |
|---|---|---|
| PoW | 採用 | 採用 |
| 台帳構造 | Blockchain | BlockDAG |
| ブロックの親参照 | 基本的に一つ | 複数を参照可能 |
| 並行ブロック | 主チェーンから外れる場合がある | DAGに取り込み、順序付けの対象にできる |
| 合意の中心 | 累積作業量に基づく有効チェーン選択 | GHOSTDAG等によるDAG上のコンセンサス |
| トランザクションモデル | UTXO | UTXO |
| ブロック生成 | 約10分を目標 | 高頻度の生成を目指す設計 |
| 実装の主な学習対象 | Bitcoin Core | rusty-kaspa |

### 9.1 「速さ」を分解する

技術比較では、少なくとも次の指標を分けて考える。

- **Block Rate**：単位時間あたりに生成されるブロック数。
- **Throughput**：単位時間あたりに処理できるトランザクション数。
- **Latency**：送信から観測・受理などの状態に到達するまでの時間。
- **Finality / Confirmation Confidence**：履歴が覆る可能性をどの程度小さいと評価できるか。
- **Decentralization Cost**：ノード運用に必要な帯域、CPU、メモリ、ストレージなど。

ブロック生成頻度が高くても、それだけでスループットや確定性が同じ比率で向上するわけではない。

### 9.2 トレードオフを評価する

Kaspaの設計は、並行ブロックをより積極的に扱うことで、従来のチェーンにおける一部の制約を緩和しようとする。

一方で、DAGの管理、順序付け、状態更新、同期、ストレージなどの複雑さは増える。

**優れた設計かどうかは、単一の性能値ではなく、どの制約を緩和し、何を新たなコストとして引き受けるかで判断する。**

## 10. Kaspaの設計を理解するための依存関係

次の順番で理解すると、個々の概念がつながりやすい。

```text
デジタル署名・ハッシュ
         │
         ▼
取引・UTXO・二重支払い
         │
         ▼
PoW・マイニング
         │
         ▼
P2Pネットワークと伝播遅延
         │
         ▼
競合ブロックの発生
         │
         ▼
BlockDAG（並行関係の記録）
         │
         ▼
GHOSTDAG（分類・順序付け）
         │
         ▼
取引の受理・Virtual State
         │
         ▼
RPC・Wallet・アプリケーション
```

この図は学習上の依存関係であり、実装の呼び出し順序ではない。

例えば、GHOSTDAGのコードを読むときにAnticoneが分からなければ、まずBlockDAGの概念へ戻る。UTXOの受理処理が分からなければ、トランザクション検証とコンセンサス順序の関係へ戻る。

このように、**分からない部分を依存元までたどって調べる**と、複雑な実装でも整理しやすくなる。

## 11. 実践：ブロック生成間隔と競合機会を計算する

ここでは、第4節の単純化した確率モデルをRustで計算する。これはKaspaのコンセンサスを再現するコードではなく、伝播遅延とブロック生成頻度の関係を直感的に理解するための実験である。

### 11.1 Rustコード

`main.rs`：

```rust
fn probability_of_competing_block(
    mean_interval_seconds: f64,
    propagation_seconds: f64,
) -> f64 {
    assert!(mean_interval_seconds > 0.0);
    assert!(propagation_seconds >= 0.0);

    1.0 - (-propagation_seconds / mean_interval_seconds).exp()
}

fn main() {
    let propagation_seconds = 1.0;

    for interval in [600.0, 10.0, 1.0] {
        let probability =
            probability_of_competing_block(interval, propagation_seconds);

        println!(
            "平均間隔: {:>6.1} 秒 / 競合機会: {:>6.2}%",
            interval,
            probability * 100.0
        );
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn no_propagation_delay_means_zero_probability() {
        assert_eq!(probability_of_competing_block(10.0, 0.0), 0.0);
    }

    #[test]
    fn shorter_interval_increases_probability() {
        let slow = probability_of_competing_block(600.0, 1.0);
        let fast = probability_of_competing_block(1.0, 1.0);
        assert!(fast > slow);
    }
}
```

### 11.2 実行方法

```bash
cargo new block-propagation-demo
cd block-propagation-demo
```

`src/main.rs`を上記コードに置き換え、次を実行する。

```bash
cargo run
cargo test
```

期待される出力（概数）：

```text
平均間隔:  600.0 秒 / 競合機会:   0.17%
平均間隔:   10.0 秒 / 競合機会:   9.52%
平均間隔:    1.0 秒 / 競合機会:  63.21%
```

### 11.3 実験から何を学ぶか

1. 平均生成間隔を短くすると、伝播中に別ブロックが発見される機会が増える。
2. 競合機会が増えるからといって、すべての競合ブロックが無効になるわけではない。
3. BlockDAGは並行したブロックを記録する仕組みであり、GHOSTDAGがその順序付けに関わる。
4. 現実のネットワークでは伝播時間が一定ではなく、このモデルだけで安全性は評価できない。

## 12. 公式資料と実装を照合する方法

Kaspaの技術を学ぶ際は、次の三つを分けて扱う。

| 情報源 | 主に確認する内容 | 注意点 |
|---|---|---|
| 論文 | アルゴリズムの前提・安全性の議論 | 実装やMainnet設定と一致するとは限らない |

| rusty-kaspa | 特定バージョンの実際のコード | ブランチやコミットによって動作が変わりうる |

### 12.1 調査時のチェックリスト

- 何を説明したいのか：概念、仕様、実装、運用のどれか。
- どのネットワークか：Mainnet、Testnet、Devnetのどれか。
- どのバージョンか：リリース、タグ、コミットを特定したか。
- どの根拠か：論文、KIP、コード、テスト、実測値を区別したか。
- どこまで確認したか：読解のみか、ビルド・テスト・実験済みか。

「提案されている」「コードに存在する」「Mainnetで利用可能である」は別の主張である。高度な機能ほど、この区別が重要になる。

## 13. よくある誤解

### 誤解1：BlockDAGを使えば二重支払いがなくなる

BlockDAGはブロックの関係を記録する構造であり、トランザクションの競合をそれ自体で解決するわけではない。コンセンサス順序とUTXO検証が必要である。

### 誤解2：GHOSTDAGはブロックを単純に時刻順へ並べる

GHOSTDAGは、DAGの参照関係とプロトコルの規則を用いる。ローカル時計による単純な時刻順ではない。

### 誤解3：blueは有効、redは無効

blueとredはGHOSTDAGにおける分類である。ブロックの構造的・暗号学的な有効性とは区別する。

### 誤解4：ブロックが速く生成されれば、トランザクションは必ず即時確定する

ブロック生成頻度、トランザクション受理、確定性、安全性は異なる概念である。

### 誤解5：KaspaはBitcoinの全要素を置き換えた

KaspaはPoW、UTXO、署名、P2P通信など、Bitcoinと共通する基礎を持つ。大きく変わるのは、並行ブロックを扱う台帳構造とコンセンサス設計である。

## 14. 理解度チェック

**Q1. Bitcoin型チェーンでブロック生成頻度を極端に高めると、どのような問題が増えやすいか。**  
A. ネットワーク伝播が完了する前に競合ブロックが生成される機会が増える。

**Q2. BlockDAGとGHOSTDAGは何が違うか。**  
A. BlockDAGはブロック間の参照関係を表すデータ構造であり、GHOSTDAGはその上でブロックを分類・順序付けするコンセンサスアルゴリズムである。

**Q3. 並行する2ブロックが同じUTXOを使うトランザクションを含んでいた場合、両方のトランザクションが有効になるか。**\
A. ならない。コンセンサス順序とトランザクション検証によって二重支払いを防ぐ必要がある。

**Q4. Block RateとFinalityは同じ意味か。**  
A. 異なる。Block Rateはブロック生成頻度、Finalityは履歴の不可逆性に関する安全性の概念である。

**Q5. 論文に記載された機能が現在のMainnetで利用できると断言できるか。**  
A. できない。KIPの状態、実装、ネットワークでの有効化状況を別々に確認する必要がある。

**Q6. 第12章を読む前に理解しておきたいBlockDAGの用語は何か。**  
A. 親、祖先、子孫、Past、Future、Anticone、Selected Parentなど。
