# Chapter 06 — Blockchain Limitations（ブロックチェーンの限界）

> **Mastering Kaspa** · Part I — Foundations（基礎編）  
> 原稿ステータス：v0.1（初稿）

## 1. はじめに

Bitcoinは、中央管理者なしに取引履歴を共有し、二重支払いを防ぐ仕組みを実現した。しかし、単一のチェーンにブロックを積み重ねる方式には、通信遅延、ブロック競合、処理能力、確定までの待ち時間などの設計上の制約がある。

これらは単なる「Bitcoinの欠点」ではない。分散システムにおいて、参加者が異なる情報を異なる時刻に受け取ることから生じる根本的な問題である。

KaspaのBlockDAGとGHOSTDAGを理解するには、まず従来のブロックチェーンがなぜ低いブロック生成頻度を採用するのかを理解する必要がある。

**本章の中心的な問い：ブロックをもっと頻繁に作れば、単純に処理性能が上がるのだろうか。**

## 2. 学習目標

本章を終えると、次を説明できる。

1. ブロック生成間隔とネットワーク伝播遅延の関係
2. 同時に発見されたブロックが競合する理由
3. 孤立ブロック・ステールブロックと再編成の違い
4. ブロックサイズ、帯域、検証コストのトレードオフ
5. スループット、レイテンシ、確定性を区別する方法
6. マイニングの公平性とネットワーク遅延の関係
7. BlockDAGが解決しようとする問題と、解決しない問題

## 3. ブロック生成間隔と伝播遅延

分散ネットワークでは、新しいブロックの情報が全ノードに瞬時に届くことはない。

```text
マイナーA                  マイナーB
   |                         |
   | ブロックXを発見          | ブロックXをまだ知らない
   |                         | ブロックYを発見
   +---------- X ----------->|
   |<--------- Y ------------+
   |                         |
   +--- 異なる先端を観測 -----+
```

ブロック伝播に時間がかかる間にも、別のマイナーは次のブロックを発見し得る。ブロック生成間隔を短縮するほど、伝播中に別のブロックが見つかる可能性は増える。

### 3.1 簡単な確率モデル

**学習用の単純化**として、ネットワーク全体のブロック発見をポアソン過程とし、平均ブロック生成間隔を `T` 秒、あるブロックの伝播に要する時間を `d` 秒とする。

伝播中に少なくとも1個の別ブロックが発見される確率は、概算で次のようになる。

\[
P(\text{別ブロック発見}) = 1 - e^{-d/T}
\]

| 平均生成間隔 T | 伝播時間 d | 概算確率 |
|---|---:|---:|
| 600秒 | 1秒 | 約0.17% |
| 60秒 | 1秒 | 約1.65% |
| 10秒 | 1秒 | 約9.52% |
| 1秒 | 1秒 | 約63.21% |

この数値は**実ネットワークのステール率を予測するものではない**。伝播時間の分布、マイナー間の接続、ブロックサイズ、複数ブロックの相関などを無視している。ここでは「生成間隔が伝播遅延に近づくと競合が増える」という傾向だけを示している。

## 4. チェーンの分岐とステールブロック

Bitcoinのようなチェーン型の設計では、同じ親を持つ有効なブロックが複数見つかる場合がある。

```text
Genesis → A → B → C → D → F
                 \
                  E
```

`D` と `E` は同じ親 `C` から伸びる競合ブロックである。後続の累積Proof of Workにより `D → F` 側が選ばれると、`E` は最終的な主チェーンに含まれない。

ここで用語を区別する。

- **競合ブロック**：同じ履歴の先端付近で競合する有効なブロック。
- **ステールブロック**：有効でも、選択された主チェーンに残らなかったブロック。
- **無効ブロック**：コンセンサスルールを満たさないブロック。ステールブロックとは異なる。
- **再編成（reorganization）**：ノードが選択する主チェーンが切り替わり、以前の履歴の一部が主チェーンから外れること。

ステールブロックのProof of Workは、チェーン型コンセンサスの主履歴に直接積み上がらない。これは高頻度ブロック生成の設計で重要な問題となる。

## 5. ブロックサイズを大きくすればよいのか

スループットを上げる方法として、ブロックサイズの拡大が考えられる。

ただし、ブロックが大きくなると次の負荷も増える。

| 要素 | ブロック拡大の影響 |
|---|---|
| ネットワーク帯域 | 送受信するデータ量が増える |
| 伝播遅延 | 大きいブロックほど配信に時間がかかりやすい |
| 検証コスト | トランザクション数に応じて処理が増える |
| ストレージ | 保存・索引付けするデータが増える |
| ノード参加 | 必要資源が増えると参加障壁になり得る |
| マイニング | 通信条件の良い参加者が有利になり得る |

ブロックを大きくすることは、処理能力とノード運用コストの交換でもある。

## 6. スループット・レイテンシ・確定性は別の指標

**スループット**は単位時間あたりに処理できる取引数、**レイテンシ**は送信から観測・取り込みまでの待ち時間、**確定性（finality）**は履歴が覆るリスクをどの程度小さく評価できるかを指す。

```text
送信 ──→ ネットワーク伝播 ──→ ブロックへの取り込み ──→ 確定性の評価
          (伝播遅延)           (取り込み待ち)          (安全性の判断)
```

ブロック生成を高速化すると取り込み待ち時間を短縮できる可能性があるが、それだけで安全な確定性が保証されるわけではない。

### 6.1 TPSの概算

平均ブロック当たりの取引数を `N`、平均生成間隔を `T` 秒とすれば、理想化した上限の目安は `N/T` TPSとなる。

ただし実効TPSは、取引サイズ、ブロックの利用率、検証・ネットワーク負荷、プロトコル制限などに左右される。

## 7. マイニングの公平性と集中化圧力

ブロック伝播が遅いマイナーは、自分の発見したブロックが他のマイナーに届くまでに競合ブロックを生成されるリスクが相対的に高い。

その結果、低遅延ネットワークや良好な接続を持つマイナーが有利になる可能性がある。ブロック生成間隔の短縮は、必ずしもすべての参加者に等しい利益をもたらさない。

この問題は単なる通信速度の問題ではなく、**コンセンサス設計と分散性の問題**でもある。

## 8. スケーラビリティのトレードオフ

分散型台帳の設計では、複数の目標を同時に考える必要がある。

- **性能**：多数の取引を低遅延で処理したい。
- **安全性**：攻撃者による履歴改変や二重支払いを困難にしたい。
- **分散性**：幅広い参加者がノードを運用できるようにしたい。
- **検証可能性**：各参加者が自分でルールを確認できるようにしたい。

これらは単純な三者択一ではないが、性能を上げるための変更が帯域・CPU・保存容量などのコストを増やす場合がある。

**設計を評価するときは、何を改善し、何のコストを増やしたかをセットで考える。**

## 9. 解決策の分類

ブロックチェーンの性能改善には、複数のアプローチがある。

| アプローチ | 考え方 | 主なトレードオフ |
|---|---|---|
| ブロックサイズ拡大 | 1ブロックに多くの取引を格納 | 伝播・検証・保存負荷 |
| ブロック間隔短縮 | ブロックを頻繁に生成 | 競合ブロックの増加 |
| Layer 2 | 一部の処理を別レイヤーへ移す | ブリッジ・決済・運用の複雑性 |
| シャーディング | 状態・処理を分割する | シャード間通信・安全性 |
| BlockDAG | 並行ブロックをグラフとして扱う | 順序付け・状態管理の複雑性 |

どの方式も「無償の高速化」ではない。

## 10. KaspaのBlockDAGは何を変えるのか

Kaspaは、複数のブロックが並行して見つかることを前提に、ブロック間の参照関係をDAGで管理する。

```text
チェーン型                         BlockDAG型

A → B → C → D                     A
     \                           / \
      X                         B   C
                                 \ /
                                  D
                                 / \
                                E   F
                                 \ /
                                  G
```

チェーン型では、並行ブロックが主履歴から外れることがある。BlockDAGでは、それらの参照関係を保持し、コンセンサスアルゴリズムで扱う。

KaspaのGHOSTDAGは、DAGの構造をもとにブロックの分類と順序付けを行う。ここで重要なのは、**並行ブロックを扱えること**と、**すべてのトランザクションが必ず有効になること**は別だという点である。競合する二重支払いを同時に有効化することはできない。

また、BlockDAGは帯域・CPU・保存容量の制約を消すものではない。高いブロック生成頻度を安全に運用するには、効率的な実装、同期、検証、セキュリティ分析が必要となる。

## 11. BitcoinとKaspaの設計上の違い

| 観点 | Bitcoin | Kaspa |
|---|---|---|
| 基本構造 | 単一チェーン | BlockDAG |
| コンセンサス基盤 | Proof of Work | Proof of Work |
| 並行ブロック | 主チェーンから外れる場合がある | DAG内の関係として扱う |
| 順序の導出 | 選択されたチェーンの順序 | GHOSTDAGに基づく順序 |
| 設計上の重点 | 保守的なブロック頻度と単純な履歴 | 並行性を活用した高頻度ブロック生成 |
| 共通の課題 | 帯域・検証・攻撃耐性 | 帯域・検証・攻撃耐性 |

本書では、Bitcoinを「古い技術」、Kaspaを「すべて解決した技術」として扱わない。それぞれが異なる設計上の選択をしていると理解する。

## 12. 実践：ブロック競合の簡易シミュレーション

以下は、ブロック発見をポアソン過程と仮定した**学習用モデル**である。KaspaやBitcoinの実際のネットワーク挙動を再現するものではない。

### 12.1 Rustコード

`examples/block-propagation/src/main.rs` などに配置する。

```rust
fn probability_of_competing_block(
    mean_interval_seconds: f64,
    propagation_seconds: f64,
) -> f64 {
    assert!(mean_interval_seconds > 0.0);
    assert!(propagation_seconds >= 0.0);

    1.0 - (-propagation_seconds / mean_interval_seconds).exp()
}

fn main() {
    let propagation_seconds = 1.0;

    for interval in [600.0, 60.0, 10.0, 1.0] {
        let p = probability_of_competing_block(interval, propagation_seconds);
        println!("interval={interval:>6.0}s, probability={:.2}%", p * 100.0);
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn zero_propagation_means_zero_probability() {
        assert_eq!(probability_of_competing_block(10.0, 0.0), 0.0);
    }

    #[test]
    fn shorter_interval_increases_competition() {
        let slow = probability_of_competing_block(600.0, 1.0);
        let fast = probability_of_competing_block(1.0, 1.0);
        assert!(fast > slow);
    }
}
```

実行例：

```bash
cargo new examples/block-propagation --bin
# 上記コードを examples/block-propagation/src/main.rs に保存
cargo run --manifest-path examples/block-propagation/Cargo.toml
cargo test --manifest-path examples/block-propagation/Cargo.toml
```

`cargo new` は既存の `examples/block-propagation` ディレクトリがない状態で実行する。

## 13. よくある誤解

### 誤解1：ブロック生成を10倍速くすればTPSも必ず10倍になる

実効スループットは、ネットワーク、検証、ブロック競合、プロトコル制限などに左右される。

### 誤解2：ステールブロックは不正なブロックである

ステールブロックは有効な場合がある。コンセンサスルール違反の無効ブロックとは異なる。

### 誤解3：BlockDAGなら通信遅延がなくなる

通信遅延は残る。BlockDAGは、並行して生成されたブロックの扱い方を変える。

### 誤解4：ブロックに入れば取引は絶対に覆らない

PoW型ネットワークでは、履歴が再編成される可能性を考慮し、用途に応じた確定性の判断が必要である。

## 14. 理解度チェック

**Q1.** ブロック生成間隔を短くすると競合が増えやすいのはなぜか。  
**A.** ブロックが全ノードに伝わる前に、別のマイナーが新しいブロックを発見する可能性が高まるため。

**Q2.** ステールブロックと無効ブロックは同じか。  
**A.** 違う。ステールブロックは有効でも主チェーンに選ばれなかったブロックを指し得る。

**Q3.** スループットと確定性は同じか。  
**A.** 違う。前者は処理量、後者は履歴が覆るリスクに関する性質である。

**Q4.** ブロックサイズを大きくする際のコストは何か。  
**A.** 帯域、伝播時間、検証負荷、ストレージ、ノード参加障壁など。

**Q5.** KaspaがBlockDAGを採用する主な理由は何か。  
**A.** 並行して生成されたブロックをDAG内で扱い、高頻度のブロック生成を支えるため。

## 15. まとめ

従来のブロックチェーンには、ブロック伝播遅延と競合、処理性能と検証負荷、分散性と運用コストなどのトレードオフがある。

ブロック生成間隔の短縮やサイズの拡大は、単純な性能改善ではなく、ネットワークとコンセンサスに新たな負荷をもたらす。

Kaspaは、**並行ブロックを主チェーンから排除するのではなく、BlockDAGとして扱う**という設計を採用した。次章では、その基礎となるDAGのデータ構造を詳しく学ぶ。
