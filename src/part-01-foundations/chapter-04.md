## 1. はじめに

インターネット上のコンピューターは、同じ情報を同じ瞬間に知ることができない。あるノードがブロックを受信しても、遠くのノードにはまだ届いていないかもしれない。通信が切れれば、一部のノードだけが異なる情報を保持することもある。

分散型暗号資産ネットワークは、このような不確実な環境で動作する。中央サーバーが唯一の正解を配るのではなく、各ノードが受信したデータを独立に検証し、共通のルールに基づいて状態を更新する。

Kaspaは、こうした**分散システムの制約を前提として設計されたProof of Work（PoW）型ネットワーク**である。BlockDAGとGHOSTDAGを理解するには、まず「なぜ同時に複数のブロックが生まれるのか」「ノードはどうやって互いを発見するのか」「ネットワーク分断が起きると何が変わるのか」を説明できる必要がある。

本章では、特定のKaspa実装の詳細に入る前に、分散システムとP2Pの基礎を整理する。

## 3. 分散システムとは何か

### 3.1 単一システムと分散システム

単一サーバーでは、処理やデータの管理を一つの主体に集約できる。設計は比較的単純だが、そのサーバーが停止するとサービス全体に影響する場合がある。

分散システムでは、複数のコンピューターがネットワークを介して協調する。

```text
集中型                          分散型

Client A ─┐                    Node A ─── Node B
Client B ─┼── Server            │  \       / │
Client C ─┘                    │   \     /  │
                               Node C ─── Node D
```

| 観点     | 集中型                                   | 分散型                               |
| -------- | ---------------------------------------- | ------------------------------------ |
| 状態管理 | 集中させやすい                           | 複数ノード間で整合させる必要がある   |
| 障害     | 中央コンポーネントが単一障害点になり得る | 一部障害に耐えられる設計が可能       |
| 通信     | クライアント・サーバー中心               | ノード間通信が重要                   |
| 運用     | 統一した管理をしやすい                   | ノードごとに環境や管理者が異なる     |
| 信頼     | 中央管理者への信頼を置く場合が多い       | 相手を無条件には信頼しない設計が可能 |

**分散化は、それ自体が目的ではない。** 障害耐性や検証可能性などの利点と引き換えに、通信、整合性、監視、デバッグの複雑さが増える。

### 3.2 ノードとピア

- **Node（ノード）**：ネットワークに参加し、プロトコルに従ってデータを処理するコンピューターまたはプロセス。
- **Peer（ピア）**：あるノードから見た通信相手のノード。
- **Message（メッセージ）**：ブロック、トランザクション、要求、応答など、ノード間で交換する情報。
- **Topology（トポロジー）**：ノード間の接続関係。

ノードが多数存在しても、すべてのノードが直接接続しているとは限らない。情報は複数のピアを経由して広がる。

## 4. 分散システムにおける時間

### 4.1 世界共通の「今」は簡単には得られない

各ノードの時計は完全には一致しない。また、送信したメッセージが相手に届くまでの時間は一定ではない。

```text
時刻の流れ ↓

Node A                  Node B                  Node C
  |                       |                       |
  |-- Block X ----------->|                       |
  |                       |-- Block X ----------->|
  |                       |                       |
  |<------ Block Y -------|                       |
  |                       |                       |
```

この図では、Node CがBlock Xを知る時点はNode Bより遅い。

「Node Aで先に観測した」という事実だけでは、すべてのノードにとっての絶対的な発生順序は決まらない。

### 4.2 遅延・帯域幅・ジッター

| 用語                | 意味                             | ブロック伝播への影響                   |
| ------------------- | -------------------------------- | -------------------------------------- |
| Latency（遅延）     | メッセージが届くまでの時間       | 他ノードが最新ブロックを知るまでの遅れ |
| Bandwidth（帯域幅） | 単位時間あたりの転送可能量       | 大きなデータを送る時間                 |
| Jitter（ジッター）  | 遅延の変動                       | 伝播時間の予測しにくさ                 |
| Packet loss（損失） | データの一部が届かないこと       | 再送や同期処理の必要性                 |
| Partition（分断）   | 一部のノード間で通信できないこと | ノード間で見えている履歴が異なる       |

### 4.3 ブロック生成頻度と並行ブロック

ブロック生成間隔がネットワークの伝播時間に近づくと、前のブロックをまだ知らないマイナーが新しいブロックを見つける機会が増える。

```text
Miner A:  ── Block X ────────────────>
Miner B:  ─────── Block Y ───────────>
                 ↑
          Xを受信する前にYを発見
```

このとき、XとYは同じ過去を参照する並行ブロックになる場合がある。

説明用の単純化として、ブロック発見が平均レート `λ` のポアソン過程に従い、伝播時間を一定の `Δ` 秒と仮定すると、その間に少なくとも1つの別ブロックが発見される確率は次のように表せる。

\[
P(N\_{\Delta}\ge 1)=1-e^{-\lambda\Delta}
\]

これは**教育用の近似モデル**である。実際の競合率は、ネットワーク構造、ブロックサイズ、マイニング能力の分布、伝播方式などにも左右される。

この関係が、KaspaのBlockDAGを学ぶうえで重要な出発点になる。

## 5. P2Pネットワークの仕組み

### 5.1 クライアント・サーバー型との違い

P2P（Peer-to-Peer）では、参加ノード同士がデータを交換する。ブロックチェーン系ネットワークでは、各ノードが受信した情報を検証し、必要に応じて他のピアへ伝える。

```text
             Node A
            /      \
        Node B ---- Node C
          |          |
        Node D ---- Node E
```

この図は論理的な接続例であり、実際のネットワークでは接続数、通信方向、ピア選択の規則が異なる。

### 5.2 ピア発見

新しいノードは、接続可能なピアを知る必要がある。一般的な手段には次のものがある。

1. あらかじめ設定された初期接続先（bootstrap）
2. DNSなどによる候補の取得
3. 既存ピアからのアドレス情報の交換
4. 過去に接続したピア情報の再利用

Kaspaで実際に使用される発見方式や接続制御は、対象バージョンの`rusty-kaspa`実装と設定を確認すること。

### 5.3 情報の伝播

ノードは、新しいトランザクションやブロックの存在を知ると、他のピアへ情報を広める。

```text
User → Node A → Node B → Node D
          └────→ Node C → Node E
```

このように複数経路を通じて広がる仕組みは、一般に**Gossip（ゴシップ）型の伝播**と呼ばれる。

実装では、帯域幅の節約や重複処理の回避のため、識別子の通知、必要なデータの要求、検証後の中継などを組み合わせることがある。上図は概念図であり、Kaspaのメッセージ順序を厳密に示すものではない。

### 5.4 伝播と検証は別の責任

情報を受信しただけで、それを正しいと判断してはいけない。

```text
受信 → デコード → 形式検証 → コンセンサス規則の検証 → 保存・伝播
```

実際の検証は段階的で、順序やキャッシュ戦略は実装に依存する。重要なのは、**「相手が送ってきた」ことと「有効である」ことを区別する**ことである。

## 6. 整合性と可用性

### 6.1 整合性（Consistency）

分散システムにおける整合性とは、ノードがどのような規則で状態を観測・更新できるかに関する性質である。整合性には複数のモデルがあり、すべての分散システムが同じ保証を提供するわけではない。

暗号資産ネットワークでは、各ノードが一時的に異なるブロック集合を知っていても、プロトコルに従って共通の状態へ収束することが重要になる。

### 6.2 可用性（Availability）

可用性は、システムが要求に応答し、利用可能な状態を維持できるかに関係する。

ただし、ノードが要求に応答したからといって、常にネットワーク全体の最新状態を持っているとは限らない。

### 6.3 ネットワーク分断とCAP定理

CAP定理は、ネットワーク分断が起き得る分散データシステムにおいて、特定の意味での強い整合性と可用性を同時に常に保証することはできない、という制約を示す。

```text
      Group A              Group B
    Node 1 ─ Node 2   X   Node 3 ─ Node 4
                       ↑
                   通信が分断
```

**注意：CAP定理を「ブロックチェーンはCかAのどちらか」と単純に分類するために使ってはいけない。** CAPが扱う整合性・可用性の定義と、PoWの確率的なコンセンサス・ファイナリティは異なる問題である。

## 7. 故障モデルと信頼

### 7.1 故障停止とビザンチン行動

| 故障・攻撃         | 例                                 | 対応の考え方                    |
| ------------------ | ---------------------------------- | ------------------------------- |
| Crash fault        | ノードが突然停止する               | 再接続、冗長化、再同期          |
| Omission fault     | メッセージを送らない・受け取れない | タイムアウト、別経路            |
| Delay fault        | メッセージが大幅に遅れる           | 遅延に耐える設計                |
| Byzantine behavior | 嘘の情報や矛盾する情報を送る       | 独立検証、コンセンサス規則      |
| Sybil attack       | 多数の偽の参加者を装う             | 接続制御とPoW等による影響の制約 |

### 7.2 ノード数と計算能力は異なる

PoWネットワークでは、コンセンサスにおける影響力を単純なノード数で数えない。多数の接続先を作っただけで、同量の正当なPoWを生み出したことにはならない。

ただし、Sybil攻撃が無意味というわけではない。接続先を攻撃者が支配すると、情報の遮断や偏りが起こり得る。

### 7.3 Eclipse攻撃

Eclipse攻撃では、攻撃者が特定ノードの通信相手を支配し、そのノードが受け取るネットワーク情報を制限することを狙う。

```text
正直なネットワーク ── [攻撃者のピア群] ── 被害ノード
```

対策は実装と脅威モデルに依存するが、一般にピアの多様性、接続制御、異常検知などが検討される。

## 8. コンセンサスはなぜ必要なのか

### 8.1 伝播だけでは履歴を決められない

P2Pネットワークは情報を広める仕組みである。しかし、互いに競合するトランザクションやブロックが届いた場合、伝播だけではどちらを採用するか決められない。

```text
Node A が見る順序: Block X → Block Y
Node B が見る順序: Block Y → Block X
```

単に「最初に受け取ったものを採用する」と、ノードごとに結果が異なる可能性がある。

そのため、受信順序に依存しない共有ルールが必要になる。

### 8.2 PoWとコンセンサスの関係

PoWはブロック生成に計算コストを要求する。一方、**どのブロック群をどの順序で扱い、どの状態を有効とするか**は、コンセンサス規則の役割である。

Kaspaでは、BlockDAG上のブロック関係を扱うためにGHOSTDAGが重要になる。

### 8.3 安全性と活性

分散合意の議論では、次の2つの観点が重要である。

- **Safety（安全性）**：許されない矛盾した結果が確定しないこと。
- **Liveness（活性）**：適切な条件のもとで、処理が前に進み続けること。

ネットワーク遅延、分断、攻撃者の能力などの仮定が変わると、どのような保証が成り立つかも変わる。Kaspaの安全性を評価するときは、必ず対象のプロトコルと脅威モデルを明示する。

## 9. BlockchainとBlockDAGをネットワークから考える

### 9.1 一本のチェーンにおける競合

```text
           Parent
           /    \
      Block A  Block B
          |
      Block C
```

従来のチェーン型PoWでは、競合した枝のうち一方が主となる履歴から外れることがある。

### 9.2 BlockDAGにおける並行性

```text
           Parent
           /    \
      Block A  Block B
           \   /
           Block C
```

BlockDAGでは、Block CがAとBの両方を参照できる。これにより、並行ブロックの存在をグラフに記録し、コンセンサス処理の対象にできる。

ただし、**すべてのブロックが無条件に有効な取引を生み、すべての競合が消えるわけではない**。ブロックの有効性、順序、トランザクションの競合解決は別途定義される。

### 9.3 Kaspaでの意味

Kaspaの設計は、通信遅延をなくすものではない。通信遅延によって発生する並行ブロックを、従来とは異なる方法で扱う。

この違いを理解することが、次章以降のBitcoin、BlockDAG、GHOSTDAGを学ぶための土台となる。

## 10. ノード同期と初期参加

### 10.1 新しいノードが参加するとき

新しいノードは、ネットワークに接続した瞬間からすべての履歴と最新状態を知っているわけではない。

概念的には次の段階が必要になる。

1. 接続可能なピアを発見する
2. 相手とプロトコル情報を交換する
3. 自分が持つデータと相手のデータの差を把握する
4. 不足するデータを取得する
5. 受信したデータを検証する
6. 現在のコンセンサス状態へ追いつく
7. 継続して新しい情報を受信する

Kaspaでは、BlockDAGとPruningを前提とした同期方式が重要になる。具体的な同期プロトコルは第21章で扱う。

### 10.2 同期済みと接続済みは違う

ノードがピアと接続できても、最新のコンセンサス状態まで同期しているとは限らない。アプリケーションがRPCを利用するときは、接続状態だけでなく同期状態も確認する必要がある。

## 11. ネットワーク設計のトレードオフ

| 設計上の選択                 | 利点                       | 代償・注意点                   |
| ---------------------------- | -------------------------- | ------------------------------ |
| 接続ピアを増やす             | 伝播経路の多様化           | 帯域幅・メモリ・接続管理コスト |
| ブロック生成を高頻度にする   | 迅速なブロック生成         | 並行ブロックと検証負荷の増加   |
| メッセージを積極的に中継する | 伝播を速めやすい           | 重複通信やDoS耐性の課題        |
| データを広く保存する         | 過去データを参照しやすい   | ストレージコスト               |
| Pruningを導入する            | 保存負担を減らせる         | 履歴取得・同期設計が複雑化     |
| 厳格な検証を行う             | 不正データの受け入れを防ぐ | CPU・I/O負荷                   |

重要なのは「速さ」だけを最適化しないことだ。**安全性、可用性、検証可能性、資源コストのバランス**を考える必要がある。

## 12. 実践：小さなP2P伝播シミュレーション

ここでは、Kaspaのプロトコルを再実装するのではなく、ネットワーク遅延によってノードの観測時刻が異なることを体験する。

### 12.1 実験の目的

- ノードごとに受信時刻が異なることを確認する
- 同じメッセージが複数経路で届く可能性を理解する
- 遅延を変えると伝播時間が変化することを観察する

### 12.2 Rustサンプル

以下は標準ライブラリだけで動作する**離散イベント型の教育用シミュレーション**である。実際のソケット通信、P2Pハンドシェイク、Kaspaのメッセージ仕様は実装していない。

```rust
use std::cmp::Reverse;
use std::collections::{BinaryHeap, HashSet};

fn main() {
    // 無向グラフ: (接続先, 遅延ミリ秒)
    let graph: Vec<Vec<(usize, u64)>> = vec![
        vec![(1, 20), (2, 80)], // A
        vec![(0, 20), (3, 30)], // B
        vec![(0, 80), (3, 10)], // C
        vec![(1, 30), (2, 10)], // D
    ];
    let names = ["A", "B", "C", "D"];

    // (受信予定時刻, ノードID)
    let mut events = BinaryHeap::new();
    let mut received = HashSet::new();
    events.push(Reverse((0_u64, 0_usize)));

    while let Some(Reverse((time, node))) = events.pop() {
        if !received.insert(node) {
            continue; // 重複受信を無視
        }

        println!("{} received at {} ms", names[node], time);
        for &(peer, delay) in &graph[node] {
            if !received.contains(&peer) {
                events.push(Reverse((time + delay, peer)));
            }
        }
    }
}
```

実行例：

```bash
rustc propagation.rs
./propagation
```

期待される出力：

```text
A received at 0 ms
B received at 20 ms
D received at 50 ms
C received at 60 ms
```

AからCへの直接経路は80msだが、A→B→D→Cの経路では60msで届く。**受信時刻は、接続関係と遅延によって変わる**。

### 12.3 発展課題

1. A–B間の遅延を20msから100msに変更する。
2. B–D間の接続を削除する。
3. ノードを10個に増やす。
4. 2つのマイナーが異なる時刻にブロックを生成するイベントを追加する。
5. 各ノードが、どのブロックを最初に知ったか記録する。

この実験は、BlockDAGが必要になる背景を直感的に理解するためのものだ。Kaspaのコンセンサス安全性を検証するテストではない。

## 13. 実際のKaspaノードを観察する

実際のノードを使う場合は、対象バージョンの公式ドキュメントに従って、テスト用ネットワークまたは隔離された環境で実験する。

観察する項目の例：

| --------------------- | -------------------------------------- |

| Sync status           | ネットワークに追いついているか         |

| RPC errors            | 通信・同期の問題が発生していないか     |

**注意**：RPCの具体的なメソッド名、返却フィールド、ポート番号、Dockerオプションはネットワーク種別と実装バージョンによって異なる場合がある。本章では固定値を断定せず、第22章・第28章で実際に確認する。

## 14. よくある誤解

### 誤解1：分散型なら通信障害に影響されない

誤り。分散型システムでもネットワーク遅延や分断は起きる。設計によって影響を抑えたり回復したりする。

### 誤解2：すべてのノードは常に同じ最新ブロックを知っている

誤り。ノードが観測する情報には伝播遅延がある。

### 誤解3：ノード数が多いほどPoWコンセンサスの投票力が増える

誤り。PoWのコンセンサスを単純なノード数の多数決として理解してはいけない。

### 誤解4：P2Pで情報が広まれば、その情報は正しい

誤り。受信したブロックやトランザクションは、各ノードがルールに従って検証する。

### 誤解5：BlockDAGはネットワーク遅延をなくす

誤り。BlockDAGは、遅延によって並行生成されるブロックを扱うためのデータ構造である。

### 誤解6：CAP定理だけでKaspaの安全性を説明できる

誤り。CAP定理とPoWの確率的コンセンサスは、前提も保証の定義も異なる。

## 15. 理解度チェック

**Q1. P2Pネットワークで、すべてのノードが同時に同じブロックを受信できないのはなぜか。**

A. ネットワークには伝播遅延があり、接続経路や通信状況も異なるため。

**Q2. ピアから受信したトランザクションを、そのまま有効と判断してよいか。**

A. いけない。ノード自身がプロトコルの規則に従って検証する必要がある。

**Q3. Sybil攻撃とPoWの関係は何か。**

A. 多数の偽ノードを作ることは可能でも、それだけで同等のPoW計算能力を得られるわけではない。ただしネットワーク接続の妨害には注意が必要である。

**Q4. 高頻度のブロック生成とネットワーク遅延の関係は何か。**

A. 伝播が完了する前に別のブロックが生成される可能性が高まり、並行ブロックが増えやすくなる。

**Q5. P2Pネットワークとコンセンサスの責任はどう異なるか。**

A. P2Pは情報の交換・伝播を担い、コンセンサスは共有ルールに基づく履歴や状態の決定を担う。

**Q6. 新しいノードがピアに接続できたら、すぐに同期済みと判断してよいか。**

A. いけない。必要なデータの取得・検証を経て同期状態を確認する必要がある。

## 16. まとめ

本章では、Kaspaを支える分散システムとP2Pネットワークの基礎を学んだ。

- 分散システムでは、ノードが同じ情報を同時に知ることはできない。
- P2Pネットワークは、ピア発見、接続、情報伝播の基盤となる。
- 情報の受信と、その情報の検証は別の処理である。
- ネットワーク遅延は、並行するブロック生成の重要な要因となる。
- PoWは計算コストを要求するが、履歴と状態を決めるためにはコンセンサス規則も必要である。
- BlockDAGは通信遅延をなくすのではなく、並行ブロックを扱う設計を可能にする。

**KaspaのBlockDAGとGHOSTDAGを理解する第一歩は、ネットワークが完全には同期しないことを理解することである。**

次章では、Bitcoinのアーキテクチャを取り上げ、PoW、ブロックチェーン、UTXO、P2Pがどのように組み合わされているかを学ぶ。
