## 1. はじめに

暗号資産のネットワークでは、互いを信頼していない参加者がデータを交換する。誰でもトランザクションを送信でき、誰でも受信したブロックを検証できる。そのため、データの改ざんを検出し、資金を使用する権限を証明する仕組みが必要になる。

その基盤となるのが、**暗号学的ハッシュ関数、公開鍵暗号、デジタル署名**である。

暗号技術が担う役割は、それぞれ異なる。

- **ハッシュ関数**：データから固定長の値を計算し、変更の検出や識別に利用する。
- **公開鍵暗号の鍵ペア**：秘密鍵と公開鍵の数学的な関係を提供する。
- **デジタル署名**：メッセージと鍵の関係を、秘密鍵を公開せずに検証可能にする。本人の意図を直接証明するものではない。
- **Proof of Work（PoW）**：所定の条件を満たすハッシュ値を見つけるために計算作業を必要とする。

ただし、**署名が正しいことと、トランザクションが有効であることは同じではない**。同じUTXOを二重に使っていないか、残高に相当する入力が十分か、ネットワークの合意ルールに従っているかは、別途検証する必要がある。

本章では、Kaspa固有の実装に進む前に、これらの基本原理を整理する。

## 3. 暗号学的ハッシュ関数

### 3.1 ハッシュ関数とは

ハッシュ関数は、任意長の入力を受け取り、決められた長さの出力を返す関数である。

```text
入力データ ── Hash Function ──> 固定長のハッシュ値
```

一般に、暗号学的ハッシュ関数には次の性質が求められる。

| 性質 | 意味 | 重要な点 |
|---|---|---|
| 決定性 | 同じ入力から同じ出力が得られる | ノード間で結果を再計算できる |
| 原像計算困難性 | 指定されたハッシュ値になる入力を見つけるのが困難 | 「復号できない」こととは別の概念 |
| 第二原像計算困難性 | 既知の入力と同じハッシュになる別入力を見つけるのが困難 | 既存データのすり替えに関係する |
| 衝突計算困難性 | 同じハッシュになる異なる2入力を見つけるのが困難 | 衝突が数学的に存在しないわけではない |
| アバランシェ効果 | 入力の小さな変化で出力が大きく変化する傾向 | それ自体が安全性の証明ではない |

例えば、あるメッセージの1文字を変えるだけでハッシュ値は大きく変わることが期待される。

### 3.2 ハッシュは暗号化ではない

以下の3つを混同しないことが重要である。

| 技術 | 主な目的 | 元に戻せるか |
|---|---|---|
| エンコード | データの表現形式を変える | 通常、復元できる |
| 暗号化 | 鍵を用いて内容を秘匿する | 適切な鍵があれば復号できる |
| 暗号学的ハッシュ | データを固定長の値に写像する | 一般に逆算は困難。暗号化のような復号操作はない |

ハッシュは機密情報を自動的に保護する技術ではない。短いパスワードや推測可能な入力を単純にハッシュしただけでは、辞書攻撃などの危険がある。

### 3.3 ハッシュ値を識別子として使う

ブロックやトランザクションの識別子には、内容に基づくハッシュ値が用いられることがある。

```text
Transaction Data
      │
      ▼
  Hash Function
      │
      ▼
 Transaction ID
```

ただし、**何をハッシュ対象にするか**はプロトコルごとに異なる。シリアライズ形式、含めるフィールド、ハッシュ関数、ドメイン分離の規則が一致しなければ、同じ識別子を再現できない。

照合先のハッシュ値の入手経路も重要である。データとそのハッシュ値を両方すり替えられれば、単純な比較だけでは改ざんを見抜けない。

Kaspaの具体的なトランザクションIDやブロックハッシュの計算方法は、後の章で実装と照合する。

## 4. SHA-256、BLAKE2b、ドメイン分離

### 4.1 ハッシュアルゴリズムは一種類ではない

代表的な暗号学的ハッシュ関数にはSHA-256やBLAKE2bなどがある。

- **SHA-256**：256ビットの出力を生成するSHA-2ファミリーの関数（[FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)）。
- **BLAKE2b**：高速なハッシュ処理を目的として設計された関数。出力長やパラメータの指定が可能（[RFC 7693](https://www.rfc-editor.org/rfc/rfc7693)）。

Bitcoinで広く使われるSHA-256と、Kaspaで利用されるハッシュ方式は同一ではない。Kaspaでは用途ごとに異なるハッシュ処理があり、PoWにも専用のアルゴリズムが使われる。

**「KaspaはBLAKE2bを使う」だけで、すべてのハッシュ処理を説明したことにはならない。** 具体的な用途・バージョン・実装を確認する必要がある。

### 4.2 ドメイン分離（Domain Separation）

同じハッシュ関数を異なる目的で使う場合、用途を区別するためにドメイン分離を行うことがある。

概念的には、次のように用途ごとの識別情報を含める。

```text
Hash("BLOCK" || block_data)
Hash("TX"    || transaction_data)
```

この例は**概念図**であり、Kaspaの実際のバイト列やハッシュ仕様を示したものではない。

ドメイン分離は、異なる文脈で同じデータを処理した際の意図しない混同を避けるために役立つ。`||` はバイト列の連結を表すが、可変長の複数フィールドを組み合わせる場合は、長さや境界も一意に解釈できる形式が必要となる。

基準版の[ハッシュ実装](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/crypto/hashes/src/hashers.rs)では、`BlockHash` や `TransactionID` は出力長32バイトのBLAKE2bを使い、公開の用途タグを `key` パラメータへ渡している。この用途タグは秘密鍵ではなく、上の単純な前置連結とも異なる。ECDSA用の署名ハッシュにはSHA-256を使う別の処理がある。PoWは[専用の処理](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/consensus/pow/src/lib.rs)として分けて読む。

## 5. 公開鍵暗号の基礎

### 5.1 秘密鍵と公開鍵

公開鍵を使う暗号方式では、数学的に関連する2つの鍵を使用する。本章では主に署名のための鍵ペアを扱う。署名はメッセージを暗号化して隠す処理ではない。

- **秘密鍵（Private Key）**：所有者が厳重に管理する秘密情報。
- **公開鍵（Public Key）**：第三者に公開してよい情報。

```text
秘密鍵 ── 公開鍵導出 ──> 公開鍵
  │                        │
  │ 署名                   │ 検証
  ▼                        ▼
Signature ────────────> Valid / Invalid
```

秘密鍵から公開鍵を計算することはできるが、適切に設計された方式では公開鍵から秘密鍵を求めることは計算上困難である。

### 5.2 秘密鍵は「パスワード」ではない

秘密鍵は、署名に使われる暗号学的な値である。秘密鍵が漏えいすると、対応する資金の使用権限を第三者に奪われる可能性がある。

秘密鍵は以下の場所に書き込んではならない。

- Gitリポジトリ
- 公開IssueやPull Request
- アプリケーションログ
- スクリーンショット
- 公開された設定ファイル

開発用の秘密鍵と本番用の秘密鍵は必ず分離する。

## 6. 楕円曲線暗号とSchnorr署名

### 6.1 楕円曲線暗号の考え方

楕円曲線暗号では、曲線上の点に対する演算を利用して公開鍵を導出する。

概念的には、秘密鍵を整数 `d`、基準点を `G`、公開鍵を `P` とすると、次のように表せる。

```text
P = d × G
1 ≤ d < n（nは基準点Gの位数）
```

ここでの `×` は通常の数値の掛け算ではなく、楕円曲線上の点のスカラー倍を意味する。

Kaspaの署名方式を理解するうえでは、楕円曲線とSchnorr署名の基本を押さえておくとよい。

### 6.2 デジタル署名

デジタル署名は、メッセージに対する署名を対応する公開鍵で検証する仕組みである。検証には署名・公開鍵・署名対象のメッセージが必要となる。

```text
送信者                             検証者

メッセージ                         メッセージ
   │                                  │
秘密鍵で署名                        公開鍵で検証
   │                                  │
   ▼                                  ▼
署名 ─────────────────────────> 成功 / 失敗
```

署名検証に成功しても、以下までは保証されない。

- そのトランザクションが二重支払いではないこと
- 送信者が現実世界の特定の人物であること
- 送信先アドレスが意図した相手のものであること
- トランザクションがネットワークで確定したこと

署名は、**メッセージと鍵の関係**を検証する仕組みである。

### 6.3 Schnorr署名の注意点

Schnorr署名では、署名時に使用する一時的な値（nonce）の扱いが重要になる。方式に反するnonceの再利用や不適切な生成は、秘密鍵漏えいにつながる場合がある。

このnonceは、PoWで探索するnonceや、第2章のアカウント型で使う実行回数のカウンターとは別のものである。[BIP 340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki)はSchnorr署名とnonce管理の参考になるが、KaspaのSighashやScriptの仕様全体を定義する資料ではない。

署名アルゴリズムを独自実装するのではなく、十分に検証されたライブラリを使用する。

## 7. ウォレット、アドレス、鍵管理

### 7.1 アドレスと公開鍵は同じではない

ウォレットは秘密鍵を管理し、必要に応じてトランザクションに署名する。

単一の鍵を使うアドレスを作る場合の概念的な関係は次のとおりである。

```text
Seed / Key Material
        │
        ▼
    Private Key
        │
        ▼
     Public Key
        │
        ▼
 Address Encoding
        │
        ▼
    Kaspa Address
```

ただし、ウォレットの鍵導出、アドレス形式、スクリプト条件は具体的な方式によって異なる。すべてのアドレスが単純に「公開鍵を1回ハッシュしたもの」とは限らない。基準版の[アドレス型](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/crypto/addresses/src/lib.rs)には `PubKey`、`PubKeyECDSA`、`ScriptHash` があり、上の図だけではScriptを基にする方式を表していない。

### 7.2 シードフレーズとHDウォレット

多くのウォレットでは、復元用のシードフレーズと階層的な鍵導出を利用する。

- **シードフレーズ**：ウォレット復元の起点となる情報。
- **HDウォレット**：1つの起点から複数の鍵を導出する仕組み。
- **導出パス**：どの子鍵を生成するかを指定する経路。

復元できるかどうかは、フレーズだけでなく、対応する導出方式やウォレット仕様にも依存する。

### 7.3 鍵管理の原則

1. 秘密鍵・シードをGitに含めない。
2. Devnet用とMainnet用の鍵を分離する。
3. バックアップと復元手順を検証する。
4. 外部からの要求で署名する場合は、操作権限と署名対象を確認する。
5. アドレスとネットワーク種別を検証する。
6. 依存ライブラリの更新と監査を継続する。

## 8. UTXOとデジタル署名

KaspaはUTXOモデルを採用する。

UTXOは、**Unspent Transaction Output（未使用トランザクション出力）**の略である。

あるトランザクションの入力は、過去に生成された未使用の出力を参照する。

```text
過去のトランザクション
        │
        ▼
   UTXO（未使用）
        │
        │ 参照 + 解除条件の充足
        ▼
新しいトランザクション
        │
        ├── 送金先の新しいUTXO
        └── おつりの新しいUTXO
```

### 8.1 署名とコンセンサスの責任分担

| 検証対象 | 主に確認すること |
|---|---|
| 署名・スクリプト | 指定された使用条件を満たしているか |
| UTXO状態 | 参照先の出力が存在し、未使用か |
| 金額・手数料 | 入力と出力の整合性があるか |
| コンセンサス | ネットワークのルールと順序付けに従うか |

例えば、正しい秘密鍵で署名されたトランザクションでも、既に使用されたUTXOを参照していれば受け入れられない。

### 8.2 署名対象（Sighash）

署名時には、トランザクションのどのデータを承認対象とするかを定義する必要がある。この計算規則を理解することは、トランザクション署名の安全性に直結する。

Kaspaの具体的なSighash方式、Script、署名エンコーディングは[第16章](../part-03-transactions/chapter-16.md)で扱う。

## 9. Proof of Workと暗号学的ハッシュ

### 9.1 PoWの基本

PoWでは、ブロック候補に関連するデータをハッシュし、ネットワークが定めた難易度条件を満たす値を探す。

概念的には、ハッシュ値を整数として解釈し、次の条件を満たすことを目指す。

```text
PoWValue(block_header, nonce, ...) <= Target
```

これは説明用の擬似式であり、Kaspaの実際のPoWアルゴリズムをそのまま表すものではない。基準版の `State::check_pow` は、計算したPoW値がtarget以下かを比較する。ブロック識別子のハッシュ値とPoW値の計算は区別する。

```text
ブロック候補を作成
        │
        ▼
nonceなどを変更
        │
        ▼
PoWハッシュを計算
        │
        ▼
難易度条件を満たす？
   ├── No  → 再試行
   └── Yes → ブロックを伝播
```

### 9.2 計算は難しく、検証は容易

条件を満たす値を探すには多数の試行が必要になる一方、見つかった結果の検証は比較的容易である。

この非対称性がPoWの基本的な性質である。

### 9.3 PoWとコンセンサスは同じではない

PoWは、ブロック生成に計算コストを要求する仕組みである。

一方、どのブロックを採用し、どの順序でトランザクションを処理するかは、コンセンサスルールが決定する。

KaspaではBlockDAGとGHOSTDAGが、この順序付けに関わる。

## 10. Merkle Treeとコミットメント

### 10.1 Merkle Treeの基本

Merkle Treeは、複数のデータのハッシュを階層的に組み合わせ、全体を代表するルートハッシュを作るデータ構造である。

```text
                 Root
                /    \
             H(AB)  H(CD)
             /  \    /  \
           H(A) H(B) H(C) H(D)
            |    |    |    |
            A    B    C    D
```

※ `H(AB)` は子ハッシュを所定の形式で結合してハッシュすることを表す概念的な表記である。

### 10.2 Merkle Proof

あるデータの包含を確認する際、すべてのデータを受け取らずに、必要な兄弟ハッシュと左右の位置情報を使ってルートを再計算できる。ただし、葉の作り方や木の構成は決めておく必要があり、照合先のルートが信頼できることも別途確認する。

この考え方は、軽量な検証やデータのコミットメントを理解するうえで重要である。

### 10.3 Kaspaとの関係

Kaspaのブロックやトランザクション処理でも、暗号学的コミットメントの考え方が重要になる。

ただし、実際のブロックヘッダーに含まれるルート値や対象データ、計算規則については、Kaspaの仕様と`rusty-kaspa`実装に従って確認する必要がある。

## 11. 暗号技術が保証すること・しないこと

暗号技術の能力を過大評価しないことが重要である。

| 技術 | 主に保証すること | それだけでは保証しないこと |
|---|---|---|
| ハッシュ | 入力と出力の再計算可能な関係 | 入力が真実であること |
| デジタル署名 | 鍵に対応する承認の検証 | 現実世界の本人確認 |
| PoW | 計算作業の条件を満たしたこと | トランザクションの最終確定 |
| Merkle Proof | 指定ルートへのデータ包含の検証 | ルート自体の正当性 |
| UTXO検証 | 出力の使用可能性をルールに照らして確認 | 秘密鍵の安全な保管 |

例えば、署名付きの誤情報は、署名が正しくても誤情報のままである。

**暗号技術は「何が数学的に検証できるか」を明確にする道具であり、すべての信頼問題を自動的に解決するものではない。**

## 12. 実践：RustでSHA-256を計算する

この節では、Kaspa固有のハッシュ実装ではなく、暗号学的ハッシュ関数の基本的な性質をRustで観察する。本書のリポジトリとは別の作業用ディレクトリで実行する。Rust/Cargoが必要で、初回の依存取得にはネットワーク接続が必要となる。

### 12.1 プロジェクトの作成

```bash
cargo new --edition 2021 hash-lab
cd hash-lab
cargo add 'sha2@=0.10.9'
```

`sha2` は本章で確認した0.10.9へ固定する（[同版のAPI資料](https://docs.rs/sha2/0.10.9/sha2/)）。生成された `Cargo.lock` は間接依存の版も記録するため、再現するときに保持する。

### 12.2 サンプルコード

`src/main.rs`を次のように編集する。

```rust
use sha2::{Digest, Sha256};

fn sha256_hex(input: &[u8]) -> String {
    let digest = Sha256::digest(input);
    format!("{digest:x}")
}

fn main() {
    let first = sha256_hex(b"Kaspa");
    let second = sha256_hex(b"kaspa");

    println!("Kaspa: {first}");
    println!("kaspa: {second}");
    println!("same? {}", first == second);
}
```

実行する。

```bash
cargo run
```

この例の入力はUTF-8/ASCIIの5バイトであり、改行は含まない。期待する標準出力は次の通りである。

```text
Kaspa: 46d79b6244e1263a61af7d460e98247ea3e57551ab214011f563bb913346b21d
kaspa: e0d9d0a56149f986b0828ae0eb0ea2677d2546ed216059cf08ca3d7f9cb906da
same? false
```

これは各32バイトのダイジェストを64文字の16進数として表示したものである。

> **注意**：これはSHA-256の学習用コードであり、KaspaのブロックハッシュやトランザクションIDを計算する実装ではない。2026-10-31に本文から抽出したコードのビルド・実行・テストを確認した。

### 12.3 テストを追加する

`src/main.rs`の末尾に追加する。

```rust
#[cfg(test)]
mod tests {

    #[test]
    fn matches_known_sha256_vectors() {

            "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"

    }

    #[test]
    fn case_examples_match_expected_digests() {
        assert_eq!(
            sha256_hex(b"Kaspa"),
            "46d79b6244e1263a61af7d460e98247ea3e57551ab214011f563bb913346b21d"

        assert_eq!(
            sha256_hex(b"kaspa"),
            "e0d9d0a56149f986b0828ae0eb0ea2677d2546ed216059cf08ca3d7f9cb906da"

```

```bash
cargo test
```

`abc` の期待値は[NISTのSHA-256計算例](https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Standards-and-Guidelines/documents/examples/SHA256.pdf)に対応する。空入力と大小文字の例も含め、期待値をPython標準ライブラリの `hashlib.sha256` と独立に照合した。これらは具体的な入力に対する確認であり、衝突が存在しないことの証明ではない。

## 14. よくある誤解

### 誤解1：ハッシュ値から元のデータを復号できる

ハッシュは暗号化ではない。暗号学的ハッシュ関数の出力から元の入力を一般的に復元することは困難である。

### 誤解2：異なる入力は必ず異なるハッシュ値になる

同じハッシュ関数・設定では、同じ入力から同じハッシュ値が得られるので、**ハッシュ値が異なれば入力も異なる**。一方、入力が異なってもハッシュ値が同じになる衝突は理論上存在する。

### 誤解3：署名が正しければ送金は必ず成立する

署名以外にも、UTXOの存在、二重支払い、手数料、コンセンサスルールなどの検証が必要である。

### 誤解4：公開鍵とアドレスは常に同一である

アドレスはネットワークや使用条件を表すためのエンコード形式であり、公開鍵そのものとは限らない。

### 誤解5：PoWのハッシュ関数を知ればコンセンサスを理解できる

PoWはブロック生成の条件に関わるが、Kaspaの順序付けにはBlockDAGとGHOSTDAGの理解が必要である。

### 誤解6：独自の暗号実装でもテストが通れば安全である

暗号実装では、サイドチャネル、nonce管理、鍵漏えい、仕様の誤解など、通常の機能テストだけでは検出できない問題がある。原則として、十分に検証されたライブラリを利用する。

## 15. 理解度チェック

**Q1. 暗号学的ハッシュ関数の衝突計算困難性とは何か。**  
A. 同じハッシュ値を持つ異なる2つの入力を見つけることが計算上困難であるという性質。

**Q2. ハッシュと暗号化の違いは何か。**  
A. 暗号化は適切な鍵による復号を前提とするが、ハッシュは一般に元の入力への逆変換を目的としない。

**Q3. 秘密鍵を公開せずに送金の承認を検証できるのはなぜか。**  
A. 秘密鍵で生成した署名を、対応する公開鍵で検証できるため。

**Q4. 正しい署名を持つトランザクションが拒否される例を挙げよ。**  
A. 既に使用されたUTXOを参照している場合など。

**Q5. Merkle Proofだけでブロックの正当性を証明できるか。**  
A. できない。指定ルートへの包含関係を検証できても、そのルートが正しいコンセンサス状態に属するかは別問題である。

**Q6. KaspaのPoWとGHOSTDAGは同じ役割か。**  
A. 異なる。PoWはブロック生成に計算作業を要求し、GHOSTDAGはBlockDAG内のブロック分類・順序付けに関わる。

## 16. まとめ

本章では、Kaspaを理解するための暗号技術の基礎を学んだ。

- **ハッシュ関数**はデータの識別、コミットメント、PoWなどに利用される。
- **公開鍵と秘密鍵**は、秘密情報を公開せずに検証可能な関係を提供する。
- **デジタル署名**は、鍵に基づく承認を検証する。
- **UTXO検証**は、署名に加えて出力の使用可能性を確認する。
- **PoW**は、ブロック生成に計算コストを要求する。
- **Merkle Tree**は、複数データへのコミットメントと効率的な包含証明を可能にする。

重要なのは、各技術の責任範囲を分けて理解することである。

**ハッシュはデータを識別し、署名は承認を検証し、コンセンサスはネットワークが共有する履歴と状態を決定する。**

[次章](chapter-04.md)では、これらの暗号技術が実際に動作する環境として、分散システムとP2Pネットワークを学ぶ。
