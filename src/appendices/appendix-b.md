## B.1 用語の読み方

| 表記 | 意味 |
|---|---|
| **L1** | 基盤となるKaspaネットワーク／コンセンサス層 |
| **L2** | L1とは別の実行・状態管理などを行い、何らかの形でL1を利用する仕組み |
| **Consensus** | ノードが合意するプロトコル上のルール |
| **Policy** | ノードやアプリの運用上の受け入れ方針。コンセンサスルールとは異なる |
| **Proposal** | 研究・仕様提案。実装済みとは限らない |

## B.2 基礎・暗号・ネットワーク

### Address（アドレス）
送金先を表すためのエンコードされた識別子。秘密鍵そのものではない。アドレス形式やネットワーク接頭辞を混同しないこと。

### Block（ブロック）
トランザクションなどのデータをまとめ、PoWで保護する単位。Kaspaではブロック同士の参照関係がDAGを形成する。

### Block Header（ブロックヘッダー）
親ブロック参照やコンセンサスに必要なメタデータなどを含む部分。厳密なフィールドは実装・プロトコル定義を参照。

### Block Reward（ブロック報酬）
ブロック生成に関連して支払われる報酬。補助金と手数料を区別して考える。

### Coinbase Transaction（コインベーストランザクション）
マイニング報酬を生成・分配するための特別なトランザクション。通常の送金とは制約が異なる。

### Cryptographic Hash（暗号学的ハッシュ）
任意長のデータから固定長の値を計算する関数。改ざん検知やPoWなどに利用される。

### Digital Signature（デジタル署名）
秘密鍵で作成し公開鍵で検証する暗号学的な署名。署名対象のメッセージと鍵との対応を検査する。署名単体で現実の所有者の身元やトランザクション全体の有効性が証明されるわけではなく、支出条件や他の検証規則も満たす必要がある。

### Double Spending（二重支払い）
同一の資産を矛盾する複数のトランザクションで使おうとすること。UTXOでは同じ出力の二重消費として現れる。

### Full Node（フルノード）
ネットワークのルールに従ってブロックやトランザクションを検証するノード。保持する履歴データの範囲とは別の概念。

### Genesis Block（ジェネシスブロック）
ネットワークの起点となる特別なブロック。

### Hashrate（ハッシュレート）
単位時間あたりに試行されるハッシュ計算の規模を示す指標。単一マイナーとネットワーク全体を区別する。

### Merkle Tree（マークルツリー）
ハッシュを階層的に組み合わせ、集合への所属を効率的に証明するデータ構造。

### Mining（マイニング）
PoW条件を満たすブロック候補を探索し、ネットワークに提示する作業。

### Node（ノード）
P2Pネットワークに参加するソフトウェアまたはその実行主体。役割や構成によって機能は異なる。

### P2P（Peer-to-Peer）
中央の単一サーバーを前提とせず、参加ノード同士が情報を交換するネットワーク方式。

### Private Key（秘密鍵）
署名を作るための機密情報。漏えいすると資産を失う可能性がある。ソースコードやログに記録しない。

### Proof of Work / PoW（プルーフ・オブ・ワーク）
計算資源を使った探索結果によってブロック生成を制限する仕組み。コンセンサスの安全性はPoWだけでなくネットワーク条件や検証規則にも依存する。

### Public Key（公開鍵）
署名の検証などに利用する公開可能な鍵。アドレスと同義ではない。

### Transaction（トランザクション）
入力・出力などを持ち、UTXO集合の変更を表すデータ。作成・送信・ブロック収録だけで状態へ適用されるとは限らず、コンセンサスで受理される必要がある。

### Transaction Fee（トランザクション手数料）
一般に入力額と出力額の差として扱われるマイナーへのインセンティブ。実際の計算・検証規則はプロトコルに従う。

## B.3 BlockDAGとGHOSTDAG

### Anticone（アンチコーン）
対象ブロック自身を除き、参照関係でその祖先でも子孫でもないブロックの集合。同じ時計時刻に生成されたかではなく、到達可能性で判断する。

### BlockDAG（ブロックDAG）
ブロックの参照関係が**有向非巡回グラフ（Directed Acyclic Graph）**を構成する構造。単一の直線的チェーンに限らない。

### blue block（ブルーブロック）
GHOSTDAGの規則でblue集合に分類されたブロック。分類は評価対象の履歴に相対的で、ブロック固有の不変な色ではない。検証規則への適合や、その中の全トランザクションの受理とは別である。

### blue score（ブルースコア）
blueブロックの累積的な数に関する指標。基準版の通常ブロックでは、selected parentのblue scoreに、そのブロックのmergeset_bluesの要素数を加える。同配列はselected parent自身を含み、対象ブロック自身は含まない。Genesisは0。全DAGのブロック数・時刻・DAA scoreとは異なる（[第12章](../part-02-consensus/chapter-12.md#128-blue-scoreとblue-work)）。

### blue work（ブルーワーク）
blue集合に関連する累積作業量の指標。基準版ではselected parentのblue workに、mergeset_bluesの各ブロックの難易度bitsから求めるwork（level workによる下限付き）を加える。実際に試したハッシュ回数やハッシュレートの直接測定値ではない。

### DAG（Directed Acyclic Graph）
有向辺を持ち、閉路のないグラフ。Kaspaではブロックの親子関係を表す。

### GHOSTDAG
BlockDAG上でブロックを選択・順序付けするKaspaのコンセンサス関連アルゴリズム。PHANTOMの考え方を踏まえた実用的な構成として理解する。

### k Parameter（kパラメータ）
blue集合内で各ブロックが持つblue anticoneの大きさに関わる上限。対象ブロックの全anticone数や親の数の上限ではない。具体的な値・フォーク境界はネットワーク設定と版を確認する。

### Merge Set（マージセット）
selected parentの履歴へ新たに取り込むブロック群。Pastが自身を含まない定義では、対象B・selected parent Pに対し、Pを除く候補は `Past(B) \ (Past(P) ∪ {P})`。基準版の候補列挙関数はPを除くが、保存するmergeset_bluesはPを含む。関数・データ構造ごとに区別する（[第12章](../part-02-consensus/chapter-12.md#1234-merge-set)）。

### Ordering（順序付け）
DAG内の複数のブロックやトランザクションについて、コンセンサス上の処理順序を決定すること。

### Parent（親ブロック）
ブロックが直接参照する先行ブロック。Kaspaでは複数の親を参照できる。

### Past / Future（過去／未来）
あるブロックの祖先集合／子孫集合。本書の集合の定義では対象自身を含まない。実装の到達可能性APIには自身を含む判定もあるため、関数の仕様を確認する。時計上の前後とは異なる。

### PHANTOM
BlockDAGの順序付けに関する研究プロトコル。GHOSTDAGとの違いを確認し、同一の実装として扱わない。

### Reachability（到達可能性）
グラフ上の参照関係を通じて、あるブロックから別のブロックに到達できるかを表す性質。

### red block（レッドブロック）
ある評価対象のGHOSTDAG分類でblue集合に入らないブロック。分類は評価対象に相対的で、無効なブロックと同義ではない。red内のトランザクションがすべて拒否されるという意味でもない。

### Selected Parent（選択された親）
親の中からGHOSTDAGのルールで一つ選ぶ評価の基準。基準版は `(blue_work, hash)` の比較で最大の親を選ぶ。blue scoreや到着順だけで選ぶ説明にはしない。

### Selected Parent Chain（選択された親チェーン）
各ブロックのSelected Parentを繰り返したどる経路。DAG全体がチェーンに変わるわけではない。

### Tips（先端ブロック群）
観測対象のDAGで子を持たないブロック群。各ノードの観測・保存状態によって異なり、新しい子を取得すれば変化する。

### Virtual Block（仮想ブロック）
ノードが選ぶ親集合をもとに現在のDAGを評価する論理的な対象。全tipを無条件に親にするとは限らず、実際にマイニングされたブロックではない。

### Virtual State（仮想状態）
現在のDAGに基づいて計算される、トランザクションの受理結果などを反映した状態。更新中の中間状態と区別する。

## B.4 コンセンサス・安全性・同期

### Block Validation（ブロック検証）
ブロックの形式・PoW・親との関係・トランザクションなどがルールを満たすか確認する処理。

### Consensus Rule（コンセンサスルール）
参加ノード間で一致しなければならない検証規則。変更にはネットワーク全体への影響がある。

### DAA（Difficulty Adjustment Algorithm）
目標ブロック生成ペースに合わせ、PoW難易度を調整するアルゴリズム。

### DAA Score（DAAスコア）
基準版の難易度調整に用いるスコア。blue scoreとは計算対象・用途が異なり、フォーク設定の切替にも使われる（[第13章](../part-02-consensus/chapter-13.md)）。

### DAGKnight
ネットワーク遅延などの条件を扱うBlockDAGコンセンサスの研究・提案に関する名称。論文・KIP・実装の各段階を区別する。

### Finality（ファイナリティ）
履歴の再評価を制限する規則、または覆るリスクが十分小さいとみなす性質。Kaspa実装のfinality point/chain選択規則と、アプリの入金確定ポリシーを区別する。確認数やisSyncedだけで無条件の不可逆性は保証しない（[第20章](../part-03-transactions/chapter-20.md)）。

### Fork（分岐）
複数の競合する履歴やソフトウェア規則の分岐を指す語。ブロック生成の並行性とプロトコル変更のフォークは文脈を区別する。

### IBD（Initial Block Download）
ノードが初回起動時などにネットワークの履歴・状態を同期する過程。

### Orphan / Missing Parent（孤立・親未取得）
必要な親ブロックがまだ取得できず、直ちに完全な検証ができない状態。各実装での用語定義を確認する。

### Pruning（プルーニング）
検証に必要な情報を保ちながら、古いデータの一部を削除・縮約して保存量を抑える仕組み。

### Reorganization / Reorg（再編成）
新しいブロックの到着などにより、選択される履歴や適用結果が変わること。アプリケーションは再評価を考慮する。

### Security Parameter（セキュリティパラメータ）
攻撃耐性・確認ポリシーなどを設計する際に使う設定値や前提。単一の値で安全性を保証できるとは限らない。

### Sync（同期）
ノード間でブロック・ヘッダー・UTXO関連データなどを交換し、整合する状態へ近づける処理。

### UTXO Commitment（UTXOコミットメント）
UTXO集合に対する暗号学的な要約。正確なデータ構造と検証用途は実装資料で確認する。

## B.5 トランザクション・ウォレット・Script

### Change Output（お釣り出力）
選択したUTXOの入力総額が支払額と手数料を超えるとき、残額を自分の管理する出力へ戻すもの。

### Coin Selection（コイン選択）
送金に利用するUTXOを選ぶ処理。手数料、プライバシー、UTXOの断片化に影響する。

### Covenant（コヴナント）
UTXOを将来どのような条件で使用できるかについて、支出先やトランザクション構造などに制約を課す設計概念。**具体的に表現できる制約は利用可能なScript機能次第**。

### Derivation Path（導出パス）
階層型ウォレットで鍵を導出する経路を示す表記。ウォレット規格・対応ネットワークを確認する。

### HD Wallet（階層的決定性ウォレット）
シードなどをもとに複数の鍵・アドレスを決定的に導出するウォレット構成。

### Input（入力）
過去のUTXOを参照し、その支出条件を満たすためのデータを含むトランザクション要素。

### Locking Script（ロックスクリプト）
UTXOを使用するための条件を表すスクリプト。用語や実装詳細はScript VMの仕様に依存する。

### Mass（マス）
トランザクションの資源負荷を評価する指標。単なるバイト数ではなく、compute/storage等の計算と適用規則は版・ネットワーク設定による。feeそのものとは区別する（[第17章](../part-03-transactions/chapter-17.md)）。

### Mempool（メモリプール）
ブロックに取り込まれる前のトランザクション候補を保持する領域。ノードごとに内容が異なり得る。

### Multisignature / Multisig（マルチシグ）
複数の署名者による承認を要求する仕組み。具体的な実現方法はScript機能・ウォレット設計による。

### Outpoint（アウトポイント）
トランザクションIDと出力インデックスの組で特定の出力を指す参照。参照先が存在し、現在も未使用かどうかは別途検証する。

### Output（出力）
金額と支出条件などを指定するトランザクション要素。受理・適用されればUTXOを生成するが、出力を作成した時点で使用可能になるわけではない。

### Script / Script VM（スクリプト／仮想マシン）
トランザクションの支出条件を記述・評価する仕組み。汎用的なEVMと同じ機能を持つと考えてはいけない。

### Sighash（署名ハッシュ）
署名対象となるトランザクションデータを規則に従って要約した値。対象範囲は署名方式・フラグに依存する。

### Transaction ID / TXID（トランザクションID）
規則に従う符号化から求めるトランザクション識別子。基準版の通常トランザクションではsignature script・sigop count・massを除いて計算する。完全なデータに対するtransaction hashや、署名対象のsighashとは区別する（[第16章](../part-03-transactions/chapter-16.md)）。

### UTXO（Unspent Transaction Output）
まだ使用されていないトランザクション出力。残高は通常、管理するUTXOの集合から計算される。

### UTXO Set（UTXO集合）
特定のコンセンサス状態で未使用の出力を管理する集合。集合に存在しても、coinbase maturity・支出条件等により直ちに使用できるとは限らない。mempoolやウォレットが予約した入力も別に扱う。

### Wallet（ウォレット）
鍵の管理、UTXOの把握、送金作成・署名などを行うソフトウェアや機器。資産そのものがウォレット内に格納されるわけではない。

### Watch-only Wallet（監視専用ウォレット）
秘密鍵を保持せず、アドレスやトランザクション状況を監視する構成。署名はできない。

## B.6 ノード・API・開発

### API（Application Programming Interface）
ソフトウェア間で機能やデータをやり取りするためのインターフェース。

### Cargo
Rustのビルド・依存関係管理・テスト実行などを担う標準ツール。

### CLI（Command-Line Interface）
コマンド入力で操作するインターフェース。RPCクライアントの検証にも使える。

### Devnet（開発ネットワーク）
開発・実験用の独立したネットワーク。メインネットの資産やセキュリティ前提と混同しない。

### Docker
アプリケーションやノードをコンテナで実行する技術。タグは付替え可能なので再現用にはdigestも記録し、OS/CPUを照合する。digestだけでソースとバイナリーの対応や動作成功が証明されるわけではない。

### Indexer（インデクサ）
ブロックやトランザクションをアプリ向けに検索・集計できる形へ変換・保存するシステム。コンセンサスの正しさを保証する主体とは限らない。

### Integration Test（統合テスト）
複数コンポーネントを接続し、相互作用を検証するテスト。

### KIP（Kaspa Improvement Proposal）
Kaspaの改善案を記録・議論するための提案文書。**KIPの存在＝採用・有効化済み**ではない。

### Mainnet（メインネット）
実際の資産価値を扱う本番ネットワーク。実験用鍵・設定を持ち込まない。

### RPC（Remote Procedure Call）
ネットワーク越しにノードの機能を呼び出す仕組み。認証・公開範囲・バージョン互換性を確認する。

### Rust
安全性と性能を重視したプログラミング言語。`rusty-kaspa`の主要実装を読むための基礎となる。

### rusty-kaspa
KaspaのRust実装を含む公式コードベース。プロトコルの挙動を調べる際の重要な一次資料。

### SDK（Software Development Kit）
アプリケーション開発向けにAPIや型、補助機能などを提供するツール群。

### Testnet（テストネット）
機能検証のための公開または共有テスト用ネットワーク。Devnetと運用目的が異なる場合がある。

### WASM（WebAssembly）
ブラウザなど多様な環境で実行可能なバイナリ形式。RustのコードをWebアプリへ組み込む際にも使う。

### wRPC
KaspaのSDKやアプリケーションから利用されるWebSocket系のRPCインターフェースを指す文脈で使われる名称。実際のトランスポートとAPIは利用バージョンで確認する。

## B.7 高度なプログラマビリティ・L2・ZK

### Argent
Kaspa関連のプログラマビリティを扱う言語・コンパイラ・runtime等のツール群。Silverscriptとは別の調査対象。ローカルcompile/runtime試験と、ネットワークによる検証・Mainnetでの有効化を区別する（[Argent補足](../part-05-advanced/argent.md)）。

### Based Application / Based App
L1の順序付けなどを活用するアプリケーション設計の概念。具体的な保証範囲は設計によって異なる。

### Bridge（ブリッジ）
異なるチェーンや実行環境の間で資産・メッセージを移動または対応付ける仕組み。ロック・発行、流動性、証明検証などの方式で信頼前提が異なる。

### Data Availability / DA（データ可用性）
状態を再構築・検証するために必要なデータが利用可能であること。**有効性証明があることとDAが保証されることは別**。

### EVM（Ethereum Virtual Machine）
Ethereum系のスマートコントラクト実行環境。Kaspa L1のScript VMとは別物。

### Fraud Proof（不正証明）
不正な状態遷移を検出・異議申し立てするための証明方式。一般にチャレンジ期間などの設計と関係する。

### L2（Layer 2）
基盤チェーンとは別の処理層。セキュリティ継承の度合いは、決済・検証・DA・管理者権限などの構成で異なる。

### Prover（証明者）
計算結果が定められた制約を満たすことを示す暗号学的証明を生成する主体。

### Rollup（ロールアップ）
複数のトランザクションや状態遷移をまとめ、基盤チェーンを利用して検証・決済などを行う設計。具体的な安全性は実装による。

### Sequencer（シーケンサー）
トランザクションの受け付け・順序付けなどを担う主体。単一運営か分散型かで停止・検閲リスクが異なる。

### Silverscript
Kaspa関連の高度なスクリプティングを扱う高水準言語・ツール群の名称。**言語仕様、コンパイラ、対応opcode、メインネット利用可否はバージョンごとに検証する**。

### Smart Contract（スマートコントラクト）
プログラムやスクリプトで定義した条件を、システムが検証・実行する仕組み。実行モデルはUTXO型・アカウント型などで異なる。

### State Commitment（状態コミットメント）
状態全体を暗号学的に要約し、後から整合性を検証するための値。

### Validity Proof（有効性証明）
計算や状態遷移が定められた規則を満たすことを証明するもの。証明対象外の性質まで保証するわけではない。

### Verifier（検証者）
証明の妥当性を検証する主体。証明生成より軽い計算で済む設計が多いが、具体的なコストは方式による。

### vProgs
Kaspaのプログラマビリティを拡張する研究・開発構想で用いられる名称。独立したプログラムの状態遷移や証明、相互作用をどう組み合わせるかが重要な論点。**研究設計と実運用の対応状況を区別する**。

### ZK Proof / ZKP（ゼロ知識証明）
秘密情報そのものを開示せずに、ある命題の正しさを証明できる暗号技術。実用システムではプライバシー目的に限らず計算の正しさの検証にも利用される。

### ZK-SNARK
簡潔な非対話型の知識証明方式の総称。信頼できるセットアップの要否などは具体的な方式による。

### ZK-STARK
透明性やスケーラビリティを重視する証明方式の系統。証明サイズ・検証コストなどは設計によって異なる。

## B.8 設計・品質保証の用語

### C4 Model
ソフトウェア構造をContext、Container、Component、Codeの視点で整理する図解手法。

### DDD（Domain-Driven Design）
業務領域の言葉・ルール・境界を中心にソフトウェアを設計する考え方。

### Idempotency（冪等性）
同じ操作を同じ条件で繰り返しても、対象への効果が一度適用した場合と同じになる性質。通知再受信や再試行に使う。重複排除キーの保存と会計等の更新を原子的に扱わなければ、二重反映を防げない場合がある。

### Invariant（不変条件）
定義した状態・遷移で常に守る性質。例：同じUTXOを有効状態で二重に消費しない。金額の保存を挙げる場合は、coinbaseの発行や手数料等を明示して式を定義し、単純に総量一定とはしない。

### State Machine（ステートマシン）
状態と、その間の許可された遷移を明示したモデル。支払い受付や入金確認の設計に役立つ。

### Threat Model（脅威モデル）
保護対象、攻撃者の能力、信頼境界、想定攻撃を整理したもの。

### Trust Assumption（信頼前提）
システムが安全に動くために、どの主体や条件を信用する必要があるかという前提。

## B.9 混同しやすい概念の比較

| A | B | 主な違い |
|---|---|---|
| BlockDAG | Blockchain | 複数親の参照関係を持つDAGか、主に一本のチェーンとして扱うか |
| blue block | Valid Block | blueは順序付けアルゴリズム上の分類、Validは検証規則への適合 |
| blue score | blue work | 数え方に関する指標か、作業量の重みを考慮する指標か |
| Anticone | Past | 参照関係上、互いに祖先・子孫でない集合か、祖先集合か |
| Virtual Block | Mined Block | 論理的な集約対象か、実際に生成されたブロックか |
| Consensus Rule | Mempool Policy | 全ノードの合意に必要なルールか、ノード固有の受理方針か |
| Transaction Seen | Payment Final | 観測されたことと、業務上十分な確信を持って確定扱いすることは別 |
| UTXO | Account Balance | 個々の未使用出力か、アカウントに紐付く集約残高か |
| Covenant | Wallet-side Rule | コンセンサスで強制する支出制約か、アプリ側だけの運用ルールか |
| L2 | Sidechain | L1とのセキュリティ・決済・検証関係によって区別する。名称だけでは判断できない |
| Validity Proof | Data Availability | 計算の正しさと、再検証に必要なデータの入手可能性は別 |
| Proposal | Mainnet Feature | 提案が存在することと、実際に有効化されていることは別 |
