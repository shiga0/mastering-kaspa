# Appendix C — 数学・確率・暗号技術の補足

> **Mastering Kaspa** / 付録C  
> 原稿ステータス：**v0.1（技術レビュー前）**  
> 対象：数学が得意でなくても、Kaspaの論文・仕様・Rust実装を読み進めたい開発者

本付録は、Kaspaを理解するうえで必要になる数学を、**直感 → 定義 → 具体例 → コード → 検証**の順で整理する。数式は原理を理解するための簡略化を含む。Kaspaの実際のコンセンサス規則や難易度計算を再現する際は、対象バージョンの仕様と `rusty-kaspa` の実装を優先する。

## C.1 この付録の読み方

本付録では次の記号を用いる。

| 記号 | 意味 |
|---|---|
| `V` | グラフの頂点集合（ブロック集合） |
| `E` | 有向辺集合（参照関係） |
| `G = (V, E)` | グラフ |
| `P(A)` | 事象Aの確率 |
| `E[X]` | 確率変数Xの期待値 |
| `λ` | 単位時間あたりの平均発生回数 |
| `H(x)` | 入力xのハッシュ値 |
| `T` | PoWのターゲット値 |
| `p` | 1回の試行で成功する確率 |
| `n` | 試行回数、または対象の個数 |

**注意**：図の矢印は本付録では「新しいブロックから参照先の古いブロックへ」を表す。論文やツールによって矢印の向きの描画規約は異なる。

## C.2 集合・関係・写像

集合は要素の集まりである。例えば `V = {A, B, C}` は3つのブロックからなる集合。

- `A ∈ V`：AはVの要素。
- `X ⊆ V`：XはVの部分集合。
- `X ∪ Y`：和集合。
- `X ∩ Y`：共通部分。
- `X \ Y`：差集合。

ブロック間の参照は、ブロックの組 `(新しいブロック, 参照先)` の集合として表せる。これが有向グラフの基礎になる。

## C.3 有向グラフとDAG

**グラフ**は頂点と辺の組 `G = (V, E)` である。辺に向きがあれば有向グラフ（Directed Graph）。

**DAG（Directed Acyclic Graph）**は、**有向閉路を持たない有向グラフ**である。BlockDAGは複数のブロックが並行して生成される状況を表現できる。

```text
      D       E      ← 新しいブロック
      |\     /|
      | \   / |
      v  v v  v
      B   C   B
       \  |  /
        v v v
          A          ← 古いブロック
```

上図は概念図であり、重複表示した `B` は同じブロックを指す。厳密な辺の集合で考えるほうが混乱しない。

例えば `E = {(B,A), (C,A), (D,B), (D,C), (E,C)}` とする。このとき `D` と `E` の間に互いをたどる経路がない場合、両者は並行関係になり得る。

### C.3.1 経路と到達可能性

`X → Y → Z` という辺の列があれば、XからZへ到達可能である。ブロック参照の向きに沿って古いブロックへたどると、祖先に相当するブロック群を求められる。

### C.3.2 トポロジカル順序

DAGには、すべての有向辺の前後関係を満たす並べ方が存在する。これを**トポロジカル順序**という。一般のDAGでは順序が複数存在し得る。

Kaspaで必要なのは単に「どれか一つのトポロジカル順序を選ぶ」ことではなく、**ネットワーク参加者が同じ規則で合意できる順序**を決定すること。GHOSTDAGなどのコンセンサス規則を理解する際は、この違いを意識する。

## C.4 Past・Future・Anticone

あるブロック `B` に対して：

- **Past(B)**：Bから親参照をたどって到達できるブロック。
- **Future(B)**：Bを参照する側からたどり、Bを過去に含むブロック。
- **Anticone(B)**：Bの過去でも未来でもないブロック。

概念的には、対象とするブロック集合 `V` の中で、

```text
Anticone(B) = V \ (Past(B) ∪ Future(B) ∪ {B})
```

と表せる。ここでの `V` は観測対象のDAG全体。実装で扱う範囲や仮想ブロックの扱いには注意が必要。

**直感**：Anticoneは「Bと直接の祖先・子孫関係にないブロック」。必ずしも「無効なブロック」や「攻撃ブロック」ではない。

## C.5 部分順序と全順序

BlockDAGの参照関係は、一般にすべてのブロックの先後を決めない**部分順序**である。例えば並行するBとCの間には、参照関係だけでは前後が定まらない。

一方、UTXOの競合を一貫して処理するには、トランザクションを評価するための決定的な順序が必要になる。Kaspaでは、DAG上の情報から合意された順序を導く仕組みが重要になる。

## C.6 GHOSTDAGの数学的な直感

GHOSTDAGは、ブロックの並行生成を考慮しながらDAGの構造を評価するためのプロトコルである。説明上は、あるブロック集合が「互いのAnticoneが大きくなりすぎない」という条件に関係する、と捉えられる。

ただし、**「Anticoneがk以下なら青、そうでなければ赤」という単純な単独判定が、そのまま実装の全規則ではない**。選択親（selected parent）、merge set、青・赤集合、順序付けなどの手順を含むため、正確な定義は原論文と実装を参照する。

### C.6.1 kパラメータの意味

`k` は、プロトコルの定義のもとで許容する並行性に関係するパラメータ。単純に「毎秒k個までのブロックを許す」という意味ではない。

### C.6.2 blue scoreとblue work

- **blue score**：選択された履歴における青ブロックの数に関係する指標。
- **blue work**：ブロックの作業量を考慮する指標。

**ブロック数と作業量は同じではない**。難易度が変化する状況では、単純な個数だけで作業量を表せない。

## C.7 確率の基礎

確率 `P(A)` は事象Aが起きる割合のモデルで、`0 ≤ P(A) ≤ 1` を満たす。

独立な事象AとBでは：

```text
P(A ∩ B) = P(A) × P(B)
```

例えば、成功確率が `p = 0.01` の独立試行を2回行い、両方成功する確率は `0.01² = 0.0001`。

**独立性は仮定であり、現実のネットワーク通信やマイナー行動が常に独立という意味ではない。**

## C.8 ベルヌーイ試行・二項分布

成功/失敗の2値をとる試行をベルヌーイ試行という。成功確率 `p` の独立試行を `n` 回行ったとき、成功回数 `X` は二項分布に従う。

```text
P(X = r) = C(n, r) p^r (1-p)^(n-r)
E[X] = np
Var(X) = np(1-p)
```

例：成功確率10%の試行を20回行う場合、平均成功回数は `20 × 0.1 = 2` 回。ただし「必ず2回成功する」わけではない。

## C.9 幾何分布とPoWの試行回数

各ハッシュ試行が独立で成功確率 `p` と近似できるとき、最初の成功までの試行回数 `N` は幾何分布に従う。

```text
P(N = n) = (1-p)^(n-1) p    (n ≥ 1)
E[N] = 1/p
P(N > n) = (1-p)^n
```

例えば `p = 1/1000` なら、平均試行回数は1000回。しかし1000回試しても見つからない確率はおよそ `e^-1 ≈ 36.8%`。**平均は保証ではない**。

## C.10 ポアソン過程とブロック生成

多数の独立した小さな成功確率の試行を連続して行う状況では、ブロック発見をポアソン過程で近似することがある。

一定の発生率 `λ`（回/秒）で、時間 `t` に起きる回数 `N(t)` は：

```text
P(N(t) = r) = exp(-λt) (λt)^r / r!
E[N(t)] = λt
```

次のイベントまでの待ち時間 `W` は指数分布で近似できる。

```text
P(W > t) = exp(-λt)
E[W] = 1/λ
```

例：平均1秒に1回なら `λ = 1`。2秒間ブロックが見つからない確率は `e^-2 ≈ 13.5%`。

**注意**：現実のブロック生成にはハッシュレート変化、難易度調整、ネットワーク遅延、マイナーの相関などがある。ポアソンモデルは説明用の近似である。

## C.11 ネットワーク遅延と並行ブロック

平均生成率 `λ` と伝播遅延 `Δ` 秒を仮定すると、遅延時間内に新しいブロックが1個以上生成される確率は、単純化したポアソンモデルでは：

```text
P(N(Δ) ≥ 1) = 1 - exp(-λΔ)
```

例えば `λ = 1 / 秒`、`Δ = 0.2 秒` なら、`1 - e^-0.2 ≈ 18.1%`。

これは**同時期にブロックが発見され得ることの直感的な指標**であって、Kaspaにおける実際の競合率やセキュリティ閾値を直接表すものではない。

## C.12 ハッシュ関数

暗号学的ハッシュ関数 `H` は任意長の入力から固定長の出力を生成する。重要な性質は次のとおり。

1. **原像計算困難性**：出力から対応する入力を見つけにくい。
2. **第二原像計算困難性**：既知の入力と同じハッシュになる別入力を見つけにくい。
3. **衝突計算困難性**：同じ出力になる異なる入力の組を見つけにくい。

衝突が**数学的に存在しない**わけではない。有限長の出力へ無数の入力を写すため衝突は存在するが、発見が計算上困難である。

### C.12.1 Avalanche Effect

入力を1ビット変更すると出力が大きく変わる性質。ハッシュの品質を考える直感として有用だが、これだけで暗号学的安全性を証明できない。

### C.12.2 Kaspaのハッシュ

Kaspaは用途別にハッシュを使い分ける。**Bitcoinと同じSHA-256をすべての用途で使う**と決めつけてはいけない。Kaspa固有のアルゴリズムやドメイン分離の実装は、対象バージョンの `rusty-kaspa` と仕様を確認する。

## C.13 PoWターゲットと難易度

PoWの基本的なモデルは、ハッシュを非負整数とみなし、次の条件を満たすnonceなどを探すこと。

```text
integer(H(block_header)) ≤ T
```

`T` が小さいほど条件を満たすのが難しくなる。`b` ビットの一様なハッシュ出力を仮定すれば：

```text
p = (T + 1) / 2^b
E[試行回数] = 2^b / (T + 1)
```

**注意**：実際のPoWヘッダー構築、ハッシュ手順、ターゲットのエンコード、比較規則、難易度調整はKaspaの仕様に従う。上式は一般的な概念モデルである。

## C.14 コンパクトターゲット表現

多くのPoWシステムでは巨大なターゲット整数を短いフィールドへ符号化する。指数部と仮数部を使う形式は典型例だが、**符号・オーバーフロー・正規化・ゼロの扱い**が重要になる。

「短い表現を展開したら同じ数になる」だけでは検証に十分でない場合がある。実装を読むときは次の点を確認する。

- 負値やゼロが許されるか。
- 仮数部の正規化条件は何か。
- 最大ターゲットの制限はあるか。
- 展開時のオーバーフローをどう扱うか。
- 比較は `<` か `≤` か。

## C.15 難易度調整とフィードバック制御

難易度調整は、観測されたブロック生成の速さに応じてPoWの目標を更新する仕組み。一般的な直感として：

```text
ブロックが速すぎる → より厳しいターゲットへ
ブロックが遅すぎる → より緩いターゲットへ
```

ただしKaspaの実際のDAAは、単純に直近N個のブロックの時間差を平均するだけの実装ではない。**DAG上のどのブロックをサンプルに含めるか**が重要で、選択親や合意規則との関係を持つ。第13章と実装を参照すること。

## C.16 期待値と分散を分けて考える

期待値は平均的な結果、分散はばらつきの大きさを表す。

```text
Var(X) = E[(X - E[X])²]
```

マイニングで「平均1分に1回」といっても、毎分ちょうど1回発見されるわけではない。平均だけを示してリスクを説明したことにしない。

## C.17 条件付き確率とベイズの定理

事象Bが観測されたときのAの確率は：

```text
P(A | B) = P(A ∩ B) / P(B)      (P(B) > 0)
```

ベイズの定理：

```text
P(A | B) = P(B | A) P(A) / P(B)
```

例えば「ノードが応答しない」という観測だけで「攻撃を受けている」と結論できない。障害、ネットワーク断、設定ミスなど複数の原因を考慮する必要がある。

## C.18 誕生日のパラドックスとハッシュ衝突

`b` ビットの理想的なハッシュを `n` 個生成するとき、衝突が少なくとも1回起きる確率は、`n` が `2^b` より十分小さい場合、おおむね：

```text
P(衝突) ≈ 1 - exp(-n(n-1) / 2^(b+1))
```

衝突の確率が無視できなくなる規模は概ね `2^(b/2)`。ただしこれは**無作為な衝突探索**の話であり、原像攻撃の計算量とは異なる。

## C.19 デジタル署名の数学的な役割

署名方式は概念的に3つの操作を持つ。

```text
(sk, pk) = KeyGen()
sig = Sign(sk, message)
valid = Verify(pk, message, sig)
```

- `sk`：秘密鍵。公開しない。
- `pk`：公開鍵。
- `message`：署名対象のメッセージ。
- `sig`：署名。

**署名が有効でも、トランザクション全体が有効とは限らない。** UTXOの存在、二重支払い、Script条件、コンセンサス規則などの検証が別に必要。

### C.19.1 署名対象（sighash）

トランザクションのどのフィールドに署名がコミットするかは非常に重要。署名対象が曖昧だと、署名者が承認していない内容へ改変できる余地が生まれる。Kaspaの署名方式とsighash構築は、第16章と一次実装を参照する。

## C.20 楕円曲線暗号の直感

楕円曲線暗号では、有限体上の点の演算を利用する。秘密鍵 `d` から公開鍵 `Q = dG` を計算できるが、適切なパラメータでは `Q` から `d` を求めるのは計算上困難と考えられている。

ここで `G` は基準点、`dG` は点Gをd回加える演算の略記。通常の整数の掛け算ではない。

Kaspaの実際の鍵・署名方式を説明するときは、一般的なECDSAの説明をそのまま当てはめないこと。**Schnorr署名など、対象機能の採用方式を仕様で確認する。**

## C.21 Merkle Treeとコミットメント

Merkle Treeは、複数のデータのハッシュを階層的にまとめ、根（Merkle Root）で集合全体へコミットする構造。

```text
              Root
             /    \
           H01    H23
          /  \    /  \
         H0  H1  H2  H3
         |    |   |   |
         A    B   C   D
```

データBの包含を検証する際、すべての葉を受け取らずに、兄弟ハッシュと位置情報を使って根を再計算できる。

ただし、**何を葉としてハッシュするか、左右の順序、奇数個の葉の処理、ドメイン分離**が違うと別の木になる。Kaspa固有のコミットメント構造は実装で確認する。

## C.22 ゼロ知識証明の数学的な位置づけ

ゼロ知識証明では、公開情報 `x` と秘密情報 `w` に対して、ある関係 `R(x, w)` が成り立つことを示す。

```text
Statement: 「ある w が存在し、R(x, w) = true」
Prover:     w を知っている側
Verifier:   証明 π を検証する側
```

重要な性質：

1. **完全性（Completeness）**：正しい主張なら適切な証明が受理される。
2. **健全性（Soundness）**：偽の主張に対する証明を通しにくい。
3. **ゼロ知識性（Zero Knowledge）**：証明から秘密の追加情報が漏れない。

**ZKは必ずしも「すべてを非公開にする技術」ではない**。何が公開入力かは回路設計に依存する。またZK証明は、ブリッジの資産管理、データ可用性、検証鍵の更新権限などを自動的に安全にしない。

## C.23 有限体とmod演算

`a mod m` は、aをmで割った余りを表す。例えば：

```text
17 mod 5 = 2
(4 + 4) mod 5 = 3
(4 × 4) mod 5 = 1
```

素数 `p` を法とする整数集合では、0以外の要素が乗法逆元を持つ。ZK回路や楕円曲線暗号で有限体が重要なのは、こうした演算を厳密に定義できるため。

## C.24 不変条件を数式で書く

**不変条件（Invariant）**とは、状態遷移の前後で常に成り立つべき性質。

UTXOの単純な保存則の例：

```text
Σ(input values) = Σ(output values) + fee
```

ただしこれは**通常の手数料付き支出を説明する概念式**であり、coinbaseなどの特別なトランザクションやプロトコル固有の規則を含む万能式ではない。

ウォレットや支払いアプリでの別の例：

```text
credited_amount ≥ 0
settled(invoice) ⇒ accepted_amount(invoice) ≥ invoice.amount
```

数式にすると、コードの`if`条件が何を保証すべきか明確になる。

## C.25 Rustで確率モデルを検証する

以下は**標準ライブラリのみで実行できる教育用サンプル**。Kaspaの実際のブロック生成やコンセンサスを再現するコードではない。

`src/main.rs`:

```rust
fn at_least_one_event(rate_per_sec: f64, seconds: f64) -> f64 {
    assert!(rate_per_sec >= 0.0 && seconds >= 0.0);
    1.0 - (-rate_per_sec * seconds).exp()
}

fn expected_trials(success_probability: f64) -> f64 {
    assert!(success_probability > 0.0 && success_probability <= 1.0);
    1.0 / success_probability
}

fn main() {
    let probability = at_least_one_event(1.0, 0.2);
    println!("0.2秒間に1回以上の発生確率: {:.2}%", probability * 100.0);
    println!("平均試行回数: {:.0}", expected_trials(0.001));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn zero_duration_has_zero_probability() {
        assert_eq!(at_least_one_event(1.0, 0.0), 0.0);
    }

    #[test]
    fn poisson_probability_matches_reference() {
        let actual = at_least_one_event(1.0, 0.2);
        let expected = 0.18126924692201818;
        assert!((actual - expected).abs() < 1e-12);
    }

    #[test]
    fn geometric_expected_trials() {
        assert_eq!(expected_trials(0.001), 1000.0);
    }
}
```

実行：

```bash
cargo new probability-lab
cd probability-lab
# src/main.rs を上記コードに置き換える
cargo test
cargo run
```

## C.26 RustでDAGの祖先を求める

次のコードは、ブロックIDから親IDへの隣接リストをたどる**教育用モデル**。循環がないことを前提とし、KaspaのBlockDAG処理とは別物。

```rust
use std::collections::{HashMap, HashSet};

fn ancestors<'a>(
    start: &'a str,
    parents: &HashMap<&'a str, Vec<&'a str>>,
) -> HashSet<&'a str> {
    let mut found = HashSet::new();
    let mut stack = parents.get(start).cloned().unwrap_or_default();

    while let Some(node) = stack.pop() {
        if found.insert(node) {
            if let Some(next) = parents.get(node) {
                stack.extend(next.iter().copied());
            }
        }
    }
    found
}

fn main() {
    let parents = HashMap::from([
        ("A", vec![]),
        ("B", vec!["A"]),
        ("C", vec!["A"]),
        ("D", vec!["B", "C"]),
    ]);
    let past = ancestors("D", &parents);
    assert_eq!(past, HashSet::from(["A", "B", "C"]));
    println!("Dの祖先: {:?}", past);
}
```

### C.26.1 実装で追加すべき検証

- 未知の親IDを許すか拒否するか。
- 自己参照や閉路をどう検出するか。
- 重複した親をどう扱うか。
- メモリ消費と探索計算量をどう抑えるか。
- 同じDAGを異なる挿入順で与えても結果が一致するか。

## C.27 計算量の基礎

入力サイズを `n` としたとき、アルゴリズムが必要とする計算量の増え方を**漸近計算量**で表す。

| 計算量 | 直感 | 例 |
|---|---|---|
| `O(1)` | 入力が増えても一定 | ハッシュマップの平均的な単一キー参照（条件付き） |
| `O(log n)` | ゆっくり増える | 二分探索 |
| `O(n)` | 入力に比例 | 全要素の走査 |
| `O(n log n)` | ソートでよく現れる | 比較ソート |
| `O(n²)` | 組合せで増える | 全ペア比較 |

DAGの単純な深さ優先探索は、対象部分グラフについて概ね `O(|V| + |E|)`。ただしキャッシュ、データ構造、ディスクアクセス、並列処理などで実際の性能は変わる。

## C.28 セキュリティの確率と「確定」の言葉

PoWシステムで「安全性が高まる」と述べるとき、何を攻撃者が制御でき、どのネットワークモデルを仮定し、どの失敗確率を評価しているのかが重要。

- 攻撃者のハッシュレート比率。
- ネットワーク遅延と分断。
- ノードが観測するDAGの範囲。
- ブロック生成率と難易度。
- 適用するコンセンサス規則。

**「一定秒数で絶対に覆らない」と断言しない**。Kaspa固有のファイナリティの意味と保証は、該当する研究・仕様・実装に基づいて説明する。

## C.29 よくある誤解

| 誤解 | 正しい捉え方 |
|---|---|
| DAGなら順序付けは不要 | 並行ブロックを表せても、トランザクションの評価順序には合意規則が必要 |
| Anticoneのブロックは不正 | 祖先・子孫関係にないという構造上の関係であり、不正の意味ではない |
| PoWは平均時間どおりに必ず成功 | 発見時間には確率的なばらつきがある |
| ハッシュには衝突が存在しない | 衝突は存在するが、発見が計算上困難 |
| 署名が正しければトランザクションは有効 | UTXO、Script、コンセンサスなどの追加検証が必要 |
| ZKならブリッジも自動的に安全 | 証明対象外の資産管理やDAなどに別のリスクがある |
| blue scoreは作業量そのもの | blue workとの違いを確認する必要がある |

## C.30 実践演習

### 演習1：DAGの関係を手で求める

`A` を親に持つ `B` と `C`、両方を親に持つ `D`、`C` を親に持つ `E` を考える。

1. `Past(D)` を列挙する。
2. `Past(E)` を列挙する。
3. `D` と `E` が祖先・子孫関係にあるか調べる。
4. 対象集合 `{A,B,C,D,E}` における `Anticone(D)` を求める。

### 演習2：ブロック生成の確率

`λ = 2 / 秒`、`Δ = 0.1 秒` のモデルで、遅延中に1回以上ブロックが生成される確率を求める。

```text
P = 1 - exp(-2 × 0.1) ≈ 18.13%
```

この数字をそのまま「Kaspaの実測フォーク率」と呼んではいけない理由を説明する。

### 演習3：PoWのターゲット

8ビットの一様なハッシュ出力で、`H ≤ 15` を成功条件とする。

```text
p = (15 + 1) / 256 = 1/16
E[N] = 16
```

ターゲットを7にした場合の平均試行回数を求める。

### 演習4：実装の読み比べ

`rusty-kaspa` の対象コミットを固定し、次の対応を表にする。

1. ブロックの親参照を保持する型。
2. Past/Anticoneに相当する概念の実装。
3. blue score/blue workを扱う箇所。
4. 難易度調整の計算。
5. 署名検証とPoW検証の責務境界。

**重要**：ファイル名や関数名はバージョンで変わるため、本付録では未検証のパスを固定しない。

## C.33 まとめ

Kaspaを理解するための数学は、すべてを高度な証明から始める必要はない。まずは次の対応を押さえる。

```text
BlockDAG           → グラフ理論・部分順序
GHOSTDAG           → DAGの構造・決定的な合意規則
PoW                → ハッシュ関数・確率・期待値
難易度調整         → 観測値・確率・フィードバック
署名とUTXO         → 暗号技術・不変条件
L2 / ZK / vProgs   → 有限体・証明・状態遷移
```

**数式は実装の代わりではなく、実装が守るべき性質を言葉より正確に表す道具である。** 論文を読み、簡単なモデルをRustで動かし、公式実装と照合することで、理解を検証可能な知識に変えていこう。
