# Chapter 10 — Kaspa Node & P2P Network（KaspaノードとP2Pネットワーク）

> **Part II — Kaspa Consensus & Architecture**  
> 原稿ステータス: v0.1（技術レビュー前）

## この章で学ぶこと

Kaspaのノードがどのように他のノードを発見し、ブロックとトランザクションを伝播させ、BlockDAGを同期するのかを理解する。P2P通信とコンセンサスを混同せず、ノード実装を調査・テストするための視点を身につける。

学習目標は次のとおり。

1. フルノード、マイナー、ウォレット、RPCクライアントの責務を区別できる。
2. ピア発見からハンドシェイク、メッセージ伝播、切断までのライフサイクルを説明できる。
3. BlockDAG特有の同期課題を、線形チェーンと比較して説明できる。
4. 通信相手を信頼せずに検証する設計原則を説明できる。
5. Rustで小さな伝播モデルを実装し、重複排除とネットワーク分断をテストできる。

> **実装上の注意:** 本章はアーキテクチャを理解するための概念モデルである。メッセージ名、ハンドシェイク順序、ポート、同期プロトコル、CLIオプションは `rusty-kaspa` のリリースやネットワークによって変わり得る。実運用時は対象バージョンのコードと公式ドキュメントで確認する。

## 10.1 なぜP2Pネットワークが重要なのか

Kaspaは中央サーバーが台帳を配布する仕組みではない。複数のノードが独立してブロックとトランザクションを受信・検証し、互いに情報を伝える。**P2Pネットワークはデータを運ぶ層**であり、**コンセンサスはそのデータから合意可能な状態を決める層**である。

```text
  Wallet / App              Miner
       |                       |
       | RPC / wRPC            | block submission
       v                       v
   +---------+             +---------+
   | Node A  |<----------->| Node B  |
   +---------+    P2P      +---------+
      /   \                    |
     /     \                   |
+---------+  +---------+   +---------+
| Node C  |--| Node D  |---| Node E  |
+---------+  +---------+   +---------+

各ノードが受信した情報を検証し、ローカルの状態を更新する。
```

ネットワークが十分に接続されていれば、情報は多数の経路で伝わる。一方、接続先が少ない、通信が遅い、あるいは一部のノードが悪意を持つ場合、ノードごとに観測するBlockDAGの先端が一時的に異なる。

## 10.2 Kaspaノードの責務と境界

| コンポーネント | 主な責務 | 他の責務との境界 |
|---|---|---|
| P2Pネットワーク | ピア接続、メッセージ交換、伝播、同期の調整 | 受信したブロックの正しさを最終決定しない |
| コンセンサス | ブロック検証、DAG関係、GHOSTDAG、順序付け、状態遷移 | ネットワーク接続を直接管理する層ではない |
| Mempool | 未確定トランザクションの受理・保持・選択 | 台帳の確定状態ではない |
| ストレージ | ブロック・インデックス・状態などの永続化 | データの意味を決めるのは上位の検証処理 |
| RPC / wRPC | 外部クライアントに操作・照会機能を提供 | P2Pピア間の内部通信とは別のAPI境界 |
| マイニング関連 | 候補ブロックの構築とPoW計算の連携 | コンセンサスルールを変更できない |

この表は**責任分担の概念図**であり、実装のモジュールが完全に一対一で対応することを意味しない。

### 10.2.1 フルノードとウォレットは異なる

フルノードはネットワークのデータを検証し、ルールに従って状態を保持する。ウォレットは鍵管理・残高照会・トランザクション作成と署名を担う。ウォレットがノードのRPCを利用しても、ウォレット自体がフルノードになるわけではない。

### 10.2.2 ノードを動かすこととマイニングは異なる

ノードはマイニングを行わなくても検証・伝播に参加できる。マイナーはPoWを実行して候補ブロックを提案するが、他のノードは提案されたブロックを独立に検証する。

## 10.3 ピアのライフサイクル

概念的な接続の流れを示す。

```text
[起動]
   |
   v
[接続先候補の取得] -- DNS seed / 保存済みアドレス / 手動設定など
   |
   v
[通信接続]
   |
   v
[互換性・ネットワークの確認]
   |
   v
[ピアとして利用可能]
   |              \
   |               +--> [ブロック・TXの通知/要求/応答]
   |               +--> [同期処理]
   |               +--> [接続品質・異常の監視]
   v
[切断・再接続候補の管理]
```

接続できたことは、相手が正直であることの証明にはならない。相手から受け取ったデータは、形式、サイズ、識別子、ネットワーク条件、コンセンサスルールなどに従って確認する必要がある。

### 10.3.1 ピア発見とブートストラップ

新しいノードは初めから全ピアを知らない。一般的には、設定された接続先、既知アドレス、ブートストラップ用の仕組みなどから接続候補を得る。

**設計上の問い:** 初期接続先がすべて攻撃者の管理下だった場合、ノードはどのような情報しか観測できないだろうか。これが後述するEclipse攻撃の理解につながる。

### 10.3.2 接続数は多ければよいわけではない

ピア数が増えると経路の多様性は高まる可能性があるが、帯域、メモリ、CPU、ファイルディスクリプタなどの消費も増える。接続先の分散性とリソース制限を両立する必要がある。

## 10.4 メッセージ伝播の基本

P2Pでは、あるノードが知ったデータを他のノードに伝える。単純な設計では全データを毎回送信できるが、ブロックサイズや通信量が増えると非効率になる。そのため、一般に「新しい識別子の通知」「未取得データの要求」「データの応答」のような段階分離が役立つ。

```text
Node A                  Node B                  Node C
  |                       |                       |
  |-- 新しいブロックの通知 ->|                       |
  |                       |-- 通知 -------------->|
  |                       |                       |
  |<-- 必要データの要求 ----|                       |
  |-- データの応答 -------->|                       |
  |                       |-- 検証・格納 ---------|
```

これは**説明用の抽象シーケンス**であり、Kaspaの特定バージョンの実際のメッセージ列を示すものではない。

### 10.4.1 重複排除

同じブロックが複数のピアから届くことは正常である。ブロック識別子を使い、既知のデータを再取得・再処理しないことが重要になる。ただし、重複判定だけで内容の正当性を保証できない。

### 10.4.2 順不同の到着

ネットワークでは、子ブロックが親ブロックより先に届くことがある。実装には、親の不足を検知して取得する、処理を保留する、あるいは不正な依存関係を拒否するなどの判断が必要になる。

## 10.5 BlockDAGが同期を難しくする理由

Bitcoinのブロックチェーンでは、ブロックは基本的に一つの親を参照する。一方、KaspaのBlockDAGでは、ブロックが複数の親を参照できる。

```text
線形チェーンのイメージ

A -> B -> C -> D

BlockDAGのイメージ（矢印は古いブロックから新しいブロックへ）

        B ----> D
       / \     / \
A ----    --->    ---> F
       \       \ /
        C ----> E
```

BlockDAGでは、同期対象を「最長チェーンの末尾までの一列」として捉えられない。**どのブロックを持っているか、どの親が不足しているか、どのDAG関係が既知か**を考える必要がある。

### 10.5.1 BlockDAGの先端（tips）

「tip」は、観測しているDAG内で後続ブロックを持たないブロックを指す。複数のtipが同時に存在することは、BlockDAGでは異常とは限らない。ノード間の通信遅延により、一時的に見えるtip集合が異なることもある。

### 10.5.2 同期とコンセンサスは別工程

1. ピアからブロックや関連情報を取得する。
2. 取得したデータの依存関係と基本的な妥当性を確認する。
3. コンセンサスルールに従ってBlockDAGへ組み込む。
4. 必要に応じて選択・順序付け・仮想状態の更新を行う。

これらは理解のために整理した段階であり、実装上は並列・非同期に進む場合がある。

### 10.5.3 IBDと通常運用

**Initial Block Download（IBD）**は、ノードが既存ネットワークに追いつくための初期同期である。通常運用時の新規ブロック伝播とは、扱うデータ量も最適化の目的も異なる。

Kaspaでは、過去の全履歴を無制限に保持し続けることを前提としない**Pruning**も重要な設計要素となる。したがって「初期同期は必ず全ブロックを創世時点から取得する」と単純化してはいけない。Pruningと同期の詳細は第21章で扱う。

## 10.6 P2P通信とGHOSTDAGの境界

ここが本章で最も重要な区別である。

- **P2P:** どのブロック情報が、いつ、どのノードに届くか。
- **BlockDAG:** ブロック同士がどのような親子・祖先関係を持つか。
- **GHOSTDAG:** DAG上のブロックをどのように評価・順序付けするか。
- **UTXO状態:** その順序付けなどに基づいて、どのトランザクション効果を適用するか。

P2Pの通信が速くても、受信データを無条件に信頼してよいわけではない。また、GHOSTDAGはネットワーク遅延そのものを消す仕組みではない。並行して作られたブロックを扱うためのコンセンサス設計である。

## 10.7 非同期ネットワークと整合性

インターネット上では、メッセージ到着までの時間に厳密な上限を置けない状況がある。ノードが一時的に異なるデータを見ていることと、コンセンサスが恒久的に破綻したことは同義ではない。

### 10.7.1 SafetyとLiveness

| 性質 | 意味 | ネットワークとの関係 |
|---|---|---|
| Safety（安全性） | 互いに矛盾する状態を誤って受け入れないこと | 不正・順不同・競合を適切に処理する必要がある |
| Liveness（活性） | 条件が満たされれば処理が前進すること | 長期分断や検閲は進行を妨げ得る |

実際の保証は、攻撃者の能力、ハッシュレート分布、ネットワーク条件などの仮定に依存する。「分散しているから必ず安全」「PoWだから即時確定」とは言えない。

### 10.7.2 伝播遅延と並行ブロック

ブロック生成間隔が短いほど、別のマイナーが最新ブロックを知る前に新しいブロックを作る場面が増える。従来のチェーンでは競合ブロックの一部が主チェーンに入らない。一方、BlockDAGは並行生成を構造として保持できる。ただし、**すべての並行ブロックが無条件に同等の扱いになるわけではない**。

## 10.8 セキュリティ: ピアは信頼境界の外にある

### 10.8.1 Sybil攻撃

攻撃者が多数のノードIDや接続を用意し、ネットワーク上で影響力を得ようとする。PoWのコンセンサス上の重みとP2P接続数は別物だが、接続先の偏りは情報の可視性に影響する。

### 10.8.2 Eclipse攻撃

特定ノードの接続先を攻撃者側に偏らせ、正直なネットワークからの情報を見えにくくする攻撃。ピアの多様性、接続先の選定、再接続方針などが防御上の論点となる。

### 10.8.3 DoS・リソース枯渇

大量の接続要求、巨大なメッセージ、重複要求、検証コストの高いデータなどが、CPU・メモリ・帯域を圧迫し得る。対策の設計原則は以下である。

- 受信サイズやキュー長に上限を設ける。
- 解析前に可能な範囲で安価な検査を行う。
- 受信元ごとの負荷と全体負荷を監視する。
- 不足データの取得処理に無限ループを作らない。
- ネットワーク入力をパニックや未処理例外につなげない。

### 10.8.4 無効なブロックと未取得ブロックを混同しない

親がまだ届いていないブロックは、直ちに「コンセンサス上無効」とは限らない。一方、必要なデータが揃って検証した結果、ルール違反と判定されるブロックは別である。この状態の区別は障害調査でも重要になる。

## 10.9 ノードの状態遷移を設計する

接続状態を単なる `connected: bool` で管理すると、途中の失敗やタイムアウトを表現しにくい。状態遷移として考えると、必要なテストが明確になる。

```text
Discovered -> Connecting -> Handshaking -> Active
                 |               |           |
                 v               v           v
               Failed          Rejected    Disconnected
                 |                           |
                 +----------> Retry <--------+
```

これは学習用の状態モデルであり、`rusty-kaspa` の列挙型をそのまま表したものではない。

**不変条件の例:**

1. ネットワークの互換性確認前に、相手を信頼済みピアとして扱わない。
2. 未検証データを確定済みUTXO状態へ反映しない。
3. 同じブロック識別子を無制限に再要求しない。
4. 切断したピアに対する待機処理を無制限に残さない。
5. メモリ上のキューが上限なく増えない。

## 10.10 Rustで作る最小Gossipモデル

ここでは実際のKaspaプロトコルを実装するのではなく、**グラフ上のメッセージ伝播と重複排除**を確認する。ネットワークソケット、署名、PoW、ブロック検証は省略する。

### 10.10.1 `src/main.rs`

```rust
use std::collections::{HashMap, HashSet, VecDeque};

#[derive(Debug, Default)]
struct Network {
    peers: HashMap<u32, Vec<u32>>,
    seen: HashMap<u32, HashSet<String>>,
}

impl Network {
    fn connect(&mut self, a: u32, b: u32) {
        self.peers.entry(a).or_default().push(b);
        self.peers.entry(b).or_default().push(a);
    }

    /// origin からメッセージを伝播させ、新たに受信したノード数を返す。
    fn broadcast(&mut self, origin: u32, message_id: &str) -> usize {
        let mut queue = VecDeque::from([origin]);
        let mut delivered = 0;

        while let Some(node) = queue.pop_front() {
            let is_new = self
                .seen
                .entry(node)
                .or_default()
                .insert(message_id.to_owned());
            if !is_new {
                continue;
            }

            delivered += 1;
            if let Some(neighbors) = self.peers.get(&node) {
                queue.extend(neighbors.iter().copied());
            }
        }

        delivered
    }
}

fn main() {
    let mut network = Network::default();
    network.connect(1, 2);
    network.connect(2, 3);
    network.connect(3, 1); // ループを含む接続
    network.connect(3, 4);

    println!("first delivery: {}", network.broadcast(1, "block-A"));
    println!("second delivery: {}", network.broadcast(1, "block-A"));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn duplicate_message_is_ignored() {
        let mut n = Network::default();
        n.connect(1, 2);
        n.connect(2, 3);
        n.connect(3, 1);
        assert_eq!(n.broadcast(1, "A"), 3);
        assert_eq!(n.broadcast(1, "A"), 0);
        assert_eq!(n.broadcast(1, "B"), 3);
    }

    #[test]
    fn disconnected_component_does_not_receive() {
        let mut n = Network::default();
        n.connect(1, 2);
        n.connect(3, 4);
        assert_eq!(n.broadcast(1, "A"), 2);
        assert!(!n.seen.get(&3).is_some_and(|ids| ids.contains("A")));
    }
}
```

### 10.10.3 発展課題

1. `connect` に同じ接続を二度追加しても影響が出ないようにする。
2. メッセージごとにTTLを設け、転送回数を制限する。
3. ノード間リンクに遅延を追加し、到着順が変わる様子を観察する。
4. 一部のリンクを切断し、分断前後の到達可能性を比較する。
5. `Block { id, parents }` を導入し、親ブロックが未到着のときの保留キューを作る。
6. キュー長の上限と、満杯になった場合の方針を決める。

## 10.11 実際の `rusty-kaspa` を読む

コードを調べるときは、まずバージョンを固定する。`main` ブランチの現在の実装と、ローカルノードの実装が一致するとは限らない。

```bash
git clone https://github.com/kaspanet/rusty-kaspa.git
cd rusty-kaspa
git tag --list | tail -n 20
```

調査の順序は次のようにするとよい。

| 観点 | 探すもの | 確認する質問 |
|---|---|---|
| エントリーポイント | ノード起動処理・設定読み込み | P2Pはどこで初期化されるか |
| 接続管理 | 接続受付、アウトバウンド接続、ピア管理 | 接続数やタイムアウトはどう制御するか |
| プロトコル | メッセージ定義、ルーティング、シリアライズ | 何を通知し、何を要求するか |
| 同期 | IBD、DAG同期、欠落データ取得 | 追いつくまでの状態遷移は何か |
| コンセンサス境界 | ブロック受信から検証処理への呼び出し | 未検証データはどこで止まるか |
| テスト | ネットワーク・同期・コンセンサスのテスト | 切断、重複、順不同をどう検証するか |

リポジトリ内で検索する例:

```bash

```

検索結果が多い場合は、該当するクレートやディレクトリへ範囲を絞る。**ファイル名だけで責務を推測せず、呼び出し元と呼び出し先を追う**ことが大切である。

## 10.12 ノード運用時の観測ポイント

ノードの障害は「同期していない」という一言では原因が特定できない。少なくとも次の観点を分けて観測する。

| 観測対象 | 典型的な兆候 | 次の調査 |
|---|---|---|
| ピア接続 | 接続数が極端に少ない | FW、NAT、接続先、切断理由 |
| データ受信 | 接続はあるがブロックが届かない | 通信量、プロトコル状態、相手の同期状態 |
| 初期同期 | 進捗が停滞 | IBD状態、ディスク、CPU、ネットワーク |
| 検証処理 | 受信量に対して処理が進まない | 検証待ち、エラー、リソース使用率 |
| ストレージ | I/O待ちや空き容量不足 | ディスク性能、容量、Pruning設定 |
| RPC | アプリから接続できない | RPCの待受設定、認証・公開範囲、FW |

**注意:** RPCのポートをインターネットへ公開することと、P2Pポートを公開することは異なる。外部公開するインターフェースは、目的とアクセス制御を明確にする。

### 10.12.1 障害調査の順番

```text
接続できるか？
  |
  +-- No --> ネットワーク・設定・FW・DNS
  |
  +-- Yes --> データは届いているか？
                  |
                  +-- No --> ピア状態・プロトコル・同期段階
                  |
                  +-- Yes --> 検証は進んでいるか？
                                  |
                                  +-- No --> CPU・ログ・不正データ・待機状態
                                  |
                                  +-- Yes --> 状態更新と保存は進んでいるか？
```

## 10.13 BitcoinのP2Pとの比較

| 観点 | Bitcoin | Kaspa |
|---|---|---|
| ブロックの参照関係 | 基本的に単一親 | 複数親を持てるBlockDAG |
| 並行ブロック | チェーン選択の競合として扱う | DAGの構成要素として保持・評価する |
| 同期で重要な関係 | ヘッダー連鎖とチェーンワーク | DAGの親子関係とコンセンサス上の選択・順序 |
| P2Pの共通課題 | 遅延、重複、攻撃者、DoS | 遅延、重複、攻撃者、DoS |
| 台帳の正しさ | コンセンサスルールで検証 | コンセンサスルールで検証 |

両者とも「P2Pで情報を運び、コンセンサスで妥当性と状態を判断する」という原則は共通する。違いは、**運ぶデータの関係構造と、その上で動くコンセンサス**にある。

## 10.14 よくある誤解

**Q. 接続したピアが多ければ、コンセンサス上の投票権も増える？**  
A. いいえ。P2P接続数とPoWコンセンサス上の重みは別の概念である。

**Q. ブロックが先に届いたノードの判断が正解になる？**  
A. いいえ。到着順だけで正当性や最終的なコンセンサス順序が決まるわけではない。

**Q. 複数tipが見えるのはネットワーク異常？**  
A. 必ずしもそうではない。BlockDAGでは並行ブロックが自然に存在する。

**Q. RPCでブロック情報を取得できれば、P2P同期も正常？**  
A. そうとは限らない。RPCの応答性とP2P同期・検証の進行は別々に観測する必要がある。

**Q. Pruningノードは不正なブロックを検証できない？**  
A. そのように一般化できない。Pruningは保存する過去データの範囲に関する設計であり、検証能力や同期手順はプロトコルの具体的な仕組みに依存する。

## 10.15 理解度チェック

1. P2Pネットワークとコンセンサスの責務をそれぞれ一文で説明しよう。
2. なぜ同じブロックが複数回届くことがあるのか。
3. 親が未到着のブロックを受信したとき、即座に不正と断定できないのはなぜか。
4. BlockDAGでは複数tipが自然に生じるのはなぜか。
5. Sybil攻撃とEclipse攻撃の違いは何か。
6. IBDと通常の新規ブロック伝播では、どのような要求が異なるか。
7. 受信キューに上限が必要なのはなぜか。
8. 「RPCは応答するが同期が進まない」場合、何を調べるか。
9. 第10.10節のコードで、ネットワークを二つの連結成分に分けた場合、伝播はどうなるか。
10. BitcoinとKaspaのP2Pに共通する問題と、DAG固有の問題をそれぞれ挙げよう。

## 10.16 まとめ

- KaspaのP2P層はブロックとトランザクションなどの情報をノード間で伝播させる。
- **受信した情報が正しいかどうかは、接続相手ではなくローカルの検証ルールで判断する。**
- BlockDAGでは複数親、複数tip、順不同到着、欠落した親の取得が重要になる。
- 初期同期、通常伝播、Pruningは関連するが同じ処理ではない。
- P2Pの接続品質とコンセンサスの安全性は区別して考える。
- 実装を読むときは、**通信 → 検証 → DAG管理 → 順序付け → 状態更新**という責務の境界を追う。
