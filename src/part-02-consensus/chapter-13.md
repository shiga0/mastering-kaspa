本章の目的は、Proof of Work（PoW）の難易度がなぜ必要なのか、ハッシュレートが変化してもブロック生成ペースをどう調整するのか、そして**線形チェーンとBlockDAGで難易度調整の観測対象がどう変わるのか**を理解することである。

読み終えたとき、次の問いに説明できるようになる。

1. Target、Difficulty、Hashrateはどう関係するか。
2. なぜ「直近のブロック間隔の平均」をそのまま信じるだけでは危険なのか。
3. BlockDAGの並行ブロックをどう考慮する必要があるか。
4. タイムスタンプ操作・ネットワーク遅延・ハッシュレート急変にどんなリスクがあるか。
5. `rusty-kaspa` で実際のDAAルールをどこから追うべきか。

## 13.1 難易度調整が解決する問題

PoWではマイナーがブロックヘッダーの候補を変え、ハッシュ値がネットワークの定める**ターゲット（target）以下**になる解を探す。試行回数が増えるほど、一定時間内に解を発見する確率は高くなる。

ハッシュレートが2倍になってもターゲットが変わらなければ、平均的なブロック生成間隔は概ね半分になる。逆に、マイナーが減ると生成は遅くなる。難易度調整アルゴリズム（Difficulty Adjustment Algorithm、DAA）は、**ネットワーク全体の計算能力の変化に応じてPoWの目標を調整する仕組み**である。

```text
ハッシュレート増加
      │
      ▼
同じターゲットならブロック発見が速くなる
      │
      ▼
観測した生成ペースを評価
      │
      ▼
ターゲットを小さくする（難易度を上げる）
      │
      ▼
目標の生成ペースに近づける
```

重要なのは、DAAが**毎ブロックを決まった秒数で生成させる時計ではない**ことだ。PoWの発見は確率的であり、短時間のばらつきは正常である。

### 13.1.1 制御対象と観測対象

| 概念 | 役割 | 注意点 |
|---|---|---|
| ハッシュレート | マイナーの計算試行速度 | ノードが直接・正確に観測できる量ではない |
| Target | 成功と認めるハッシュ値の上限 | 小さいほど厳しい |
| Difficulty | PoWの相対的な厳しさ | 定義・基準値は実装に依存する |
| ブロック生成ペース | DAAが間接的に観測する現象 | ランダム性と通信遅延を含む |
| DAA window | 推定に利用する履歴の範囲 | 大小で応答性と安定性が変わる |

## 13.2 PoWの確率モデル

暗号学的ハッシュの出力を、`0` から `2^n - 1` までほぼ一様な整数とみなす。ターゲットを `T` とすると、1回の試行が成功する確率は概ね次のようになる。

\[
p = \frac{T+1}{2^n}
\]

> mdBookの標準環境では上の数式表示に追加設定が必要な場合がある。本文を数式プラグインなしで公開する場合は `p = (T + 1) / 2^n` と読めばよい。

試行の独立性を近似すると、成功までの期待試行回数は `1/p`。ネットワーク全体の試行速度を `H`（hashes/second）とすれば、期待ブロック発見時間は次の近似になる。

```text
E[block_interval] ≈ 1 / (H × p)
```

### 13.2.1 数値例（仮想ネットワーク）

- 1回の試行の成功確率：`p = 1 / 1,000,000`
- ネットワークの試行速度：`H = 100,000 hash/s`
- 期待発見時間：`1 / (100,000 × 0.000001) = 10秒`

ハッシュレートが `200,000 hash/s` に増えれば期待発見時間は約5秒になる。再び10秒程度にしたいなら、成功確率を概ね半分にする方向へターゲットを調整する。

これは**説明用のモデル**であり、実際のKaspaのターゲット値やハッシュレートを表していない。

### 13.2.2 平均値と実際の観測値

期待間隔が10秒でも、毎回10秒後に発見されるわけではない。PoWの発見は近似的にポアソン過程として扱え、発見間隔には大きなばらつきがある。

したがって「直近の1ブロックが速かった」だけで難易度を大きく変更すると、ランダムな揺れに過剰反応してしまう。

## 13.3 Target・Difficulty・Compact Bits

### 13.3.1 TargetとDifficultyは逆向き

概念上、基準ターゲット `T_ref` を固定すれば、難易度は次のように定義できる。

```text
Difficulty = T_ref / Target
```

- Targetが小さくなる → 成功条件が厳しくなる → Difficultyが高くなる。
- Targetが大きくなる → 成功条件が緩くなる → Difficultyが低くなる。

ただし、**Difficultyの数値は基準ターゲットの取り方によって変わる**。異なるチェーンの表示難易度をそのまま比較しても、計算量の直接比較にはならない。

### 13.3.2 Compact Bitsとは

PoW系プロトコルでは、非常に大きいターゲット整数をコンパクトな形式でブロックヘッダーへ格納することがある。Bitcoinの `nBits` は代表例である。

Kaspaのヘッダーにも難易度に関わる `bits` フィールドがあるが、**エンコーディング・境界条件・検証手順は対象バージョンの実装を正とする**。

実装時に確認すべき不変条件は次のとおり。

1. コンパクト表現を復号したターゲットが許容範囲内にある。
2. 対象ブロックの `bits` がコンセンサスルールで期待される値と一致する。
3. PoWハッシュがそのターゲットを満たす。
4. 整数オーバーフロー、符号、丸め方がネットワーク全体で一致する。

**「ハッシュがターゲットを満たす」だけでは十分ではない**。任意に緩いターゲットをヘッダーに書けてしまえば、マイナーは簡単にブロックを作れてしまうからだ。

## 13.4 Bitcoinの難易度調整を基準に考える

Bitcoinは難易度調整の比較対象として理解しやすい。基本的には**2,016ブロックごと**に、対象期間の経過時間と目標時間を比較してターゲットを調整する。目標間隔は約10分なので、2,016ブロック分の目標時間は約2週間となる。

```text
目標期間: 2016 × 10分 = 20,160分

観測期間が短い → ブロック生成が速すぎる → 難易度を上げる
観測期間が長い → ブロック生成が遅すぎる → 難易度を下げる
```

Bitcoinの調整には上限・下限の制約があり、実際の計算はコンセンサス実装に従う。**KaspaのDAAをBitcoinの2,016ブロック方式と同一視してはいけない**。

### 13.4.1 方式のトレードオフ

| 観点 | 長い調整周期 | 短い調整周期 |
|---|---|---|
| 突発的な変動への応答 | 遅い | 速い |
| 偶然の発見間隔への反応 | 小さめ | 大きくなりやすい |
| 急激なハッシュレート減少 | 復旧が遅れる場合がある | 追従しやすい |
| 時刻データのノイズ | 平均化しやすい | 影響を受けやすい |

「速く調整するほど優秀」という単純な話ではない。**安定性・応答性・攻撃耐性のバランス**が設計の中心となる。

## 13.5 BlockDAGで難易度調整が難しくなる理由

線形チェーンでは、主鎖上のブロック列を比較的単純に追える。一方、BlockDAGには並行して生成された複数のブロックが存在し、全ブロックが一本の親子列に並ぶわけではない。

```text
Blockchain:

A ── B ── C ── D

BlockDAG（概念図）:

        ┌── B ── D ──┐
A ──────┤             ├── F
        └── C ── E ──┘
```

BlockDAGでは、どのブロック集合を「直近の観測対象」とするかをコンセンサスとして定義する必要がある。

### 13.5.1 直感的な落とし穴

仮にDAGに `B` と `C` が並行して追加されたとする。Selected-parent chainだけを見て生成レートを推定すると、**DAG上で実際に採掘されたブロックの一部を無視する可能性**がある。

逆に、ネットワークから見えた全ブロックを無条件に数えれば、重複、無効ブロック、遅延到着、攻撃者が作った構造の影響を受けかねない。

そのため、KaspaのDAAを理解するには、**GHOSTDAGが定めるブロックの関係と、DAAが採用するブロック集合の定義**を同時に調べる必要がある。

### 13.5.2 blue score・blue workとの区別

| 指標 | 大まかな意味 | DAAとの関係 |
|---|---|---|
| blue score | GHOSTDAGで計算される青ブロックの累積的な尺度 | ブロック数に関連するが、そのまま時刻やハッシュレートではない |
| blue work | 選択・比較に用いる累積的なPoWの尺度 | 難易度や選択規則との関係を理解する手がかり |
| DAA Score | 難易度調整上の進行度を表すコンセンサス上の指標 | blue scoreと同義と決めつけない |
| Block timestamp | ブロックヘッダーが持つ時刻情報 | 正確な実世界の生成時刻と同一ではない |

> **重要**：これらの定義はプロトコルの詳細に依存する。本章では概念を整理し、実際のDAA windowの構築や例外条件を単純化している。

## 13.6 KaspaのDAAを理解するための処理モデル

Kaspaの実装を読む前に、次の**概念モデル**を頭に入れておくとよい。

```text
候補ブロック
    │
    ├── 親ブロック情報を参照
    │
    ▼
コンセンサスが定める過去のブロック集合を特定
    │
    ▼
DAA用の履歴・時刻・仕事量を評価
    │
    ▼
期待される難易度（bits / target）を計算
    │
    ▼
候補ヘッダーのbitsと照合
    │
    ▼
PoWハッシュの条件を検証
    │
    ▼
他の検証条件と合わせて受理可否を決定
```

この図は**実際の関数呼び出し順序を示すものではない**。コンセンサス処理はキャッシュ、並列処理、親の検証状態、ストレージへのアクセスを含み、コード上の依存関係はさらに複雑になる。

### 基準版で確認した計算経路

基準版v1.0.1の `DualWindowManager` は、selected parentのDAA scoreによるCrescendo activation判定でFull/Sampledの窓と計算器を切り替える。本書のDevnet既定設定はactivationがneverのためFull側。Sampled側の説明をそのままDevnetの実測へ適用しない。

| 段階 | 基準版の処理 |
|---|---|
| 窓の構築 | GHOSTDAG・selected parent chain・merge setを使って対象を集める。受信順の全ブロック一覧ではない |
| DAA score | selected parentのDAA scoreに、merge setのうちnon-DAAでない要素数を加える |
| Fullで履歴不足 | 要素数がmin window size未満ならGenesisのbitsを返す |
| 通常のtarget計算 | 最小timestampの要素を1つ除き、残ったtargetを多倍長整数で合計・平均化する |
| 時間差 | 除く前に得た最大timestamp−最小timestampを使い、最低1ミリ秒とする |
| 出力 | 時間比を整数演算で適用し、最大targetで制限してcompact bitsへ戻す |

Fullの通常計算を、最小時刻の要素を除いた件数 `n`、そのtarget平均 `avg` として書くと次になる。

```text
avg = floor(sum(remaining_targets) / n)
new_target = floor(avg × max(max_ts − min_ts, 1) / (target_time_per_block × n))
```

timestampが同じ要素の順序はblue work、hashで決定する。timestampと目標時間の単位はミリ秒。途中の平均化でも整数除算するため、式の演算順序を変更したり、targetの平均をdifficultyの平均へ置き換えたりしない。Sampled側は通常の分母にsample rateも掛け、Crescendo直後で標本が不足するときにはselected parentのbitsを継承または目標時間比で補正する別経路を持つ。

根拠：[window.rs](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/consensus/src/processes/window.rs)、[difficulty.rs](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/consensus/src/processes/difficulty.rs)、[params.rs](https://github.com/kaspanet/rusty-kaspa/blob/fcd9c28f9b211b9872a0c90a8c94f79466ffb063/consensus/core/src/config/params.rs)。ヘッダー検証では、申告bitsへのPoW検査と、履歴から計算する期待bitsとの照合を分けて行う。[第11章](chapter-11.md)の検証順を参照する。DAAの数値ベクトルを公式計算器へ入力する実行時差分テストは今回未実施。

### 13.6.1 過去の情報だけで決まること

ノードごとに難易度が違ってしまうとコンセンサスが成立しない。したがって、候補ブロックに対して期待される難易度は、**プロトコルで認められた決定的な入力と計算手順**から導かれなければならない。

ノードのローカル時計、受信順、任意のピアの申告ハッシュレートをそのまま計算に使う設計は、ノード間不一致の原因になる。

### 13.6.2 Genesis・初期履歴・特殊条件

履歴が十分にない初期ブロック、特殊なネットワーク設定、ハードフォーク境界などでは、通常のウィンドウ計算と異なる扱いが必要になることがある。

**mainnet・testnet・devnetのパラメータを混同しないこと**。ブロック生成目標や適用ルールを論じる際は、ネットワーク種別とノードのリリースを必ず明記する。

## 13.7 タイムスタンプと信頼境界

ブロックヘッダーのタイムスタンプは、中央の時刻認証局が保証した値ではない。マイナーが提案し、ネットワークのコンセンサスルールで検証される値である。

### 13.7.1 なぜ時刻操作が問題になるか

DAAがブロック時刻に依存する場合、攻撃者が時刻を偏らせることで、観測上の生成ペースを実際より速く、または遅く見せようとする可能性がある。

この種のリスクは一般に**タイムスタンプ操作**や**time-warp系の問題**として議論される。ただし、具体的に成立する攻撃や緩和策は各プロトコルの検証条件次第である。

### 13.7.2 防御の考え方

- 受信した時刻を無条件に信用しない。
- 時刻に関する許容範囲や順序条件をコンセンサスルールで定義する。
- 単一ブロックの時刻だけで判断せず、履歴の統計的な情報を使う設計を検討する。
- 異常な入力でオーバーフローやゼロ除算が起きないようにする。
- 合意に関わる丸め・ソート・タイブレークを決定的にする。

これらは一般的な設計原則であり、**Kaspaがすべてをこの形で採用していると主張するものではない**。

## 13.8 ハッシュレート急変とネットワーク分断

### 13.8.1 ハッシュレートが急増した場合

高性能マイナーが多数参加すると、調整前は平均発見間隔が短くなる。DAAはその変化を観測し、ターゲットを厳しくする方向へ動く。

### 13.8.2 ハッシュレートが急減した場合

マイナーが離脱するとブロック発見が遅くなり、調整に必要な履歴の更新自体が遅れることがある。DAAの追従速度はネットワークの回復性に影響する。

### 13.8.3 ネットワーク分断が起きた場合

通信が分断されたとき、各側で観測するブロック集合は異なりうる。再接続後にはDAG構造や選択された過去の履歴が変化する可能性がある。

このためDAAは、**P2Pから到着した順番ではなく、コンセンサス上で定義された履歴**に基づく必要がある。DAAをP2Pの受信処理に直接埋め込むと、責務境界を誤りやすい。

## 13.9 セキュリティ・安全性・活性

DAAは単なる性能調整ではなく、ネットワークのセキュリティ条件にも影響する。

| リスク | 問題 | 調査・設計で確認すること |
|---|---|---|
| 難易度が低すぎる | ブロック生成が過剰に速くなり得る | ターゲットの上限、計算の境界条件 |
| 難易度が高すぎる | ブロック生成が長時間止まり得る | 急減時の応答性 |
| 時刻の偏り | 観測期間を誤る | 時刻検証、統計的処理 |
| DAG集合の誤定義 | 計算に使う仕事量が不適切になる | DAA windowの選択規則 |
| 整数計算の不一致 | ノード間で期待bitsが変わる | 整数型、丸め、境界値テスト |
| ネットワーク分断 | 観測できる履歴が変化する | 再接続時の再評価 |

**Safety（安全性）**は、ノードが不正な難易度のブロックを受理したり、同じ履歴から異なる期待難易度を計算したりしないことに関わる。

**Liveness（活性）**は、ハッシュレートの変化後も新しいブロックが継続的に生成・受理されることに関わる。

両者を混同しないこと。難易度調整が速いだけで安全性が保証されるわけではない。

## 13.10 Rustで学ぶ簡易DAA

ここでは、**ブロック生成間隔の平均を利用して難易度を更新する教育用モデル**を作る。これはKaspaの実装とは異なる。

### 13.10.1 モデルの前提

- 目標ブロック間隔は `10秒`。
- 観測した間隔の合計と期待時間の比で相対難易度を更新する。
- 一度の更新倍率は `0.25〜4.0` に制限する。この制限は教材独自であり、上記の公式target計算を再現していない。
- 整数ターゲット・コンパクト表現・BlockDAG固有のDAA windowは扱わない。
- 難易度は `f64` で表すが、**実際のコンセンサス実装では浮動小数点の非決定性に注意し、正確な整数演算を使うべき**である。

`cargo new daa-lab` でプロジェクトを作り、`src/main.rs` を次の内容に置き換える。

```rust
const TARGET_INTERVAL_SECS: f64 = 10.0;

/// 学習用: 観測間隔から新しい相対難易度を推定する。
/// Kaspaのコンセンサス実装ではない。
fn adjust_difficulty(
    current_difficulty: f64,
    observed_intervals_secs: &[f64],
) -> Result<f64, &'static str> {
    if !current_difficulty.is_finite() || current_difficulty <= 0.0 {
        return Err("current difficulty must be positive and finite");
    }
    if observed_intervals_secs.is_empty() {
        return Err("at least one interval is required");
    }
    if observed_intervals_secs
        .iter()
        .any(|&x| !x.is_finite() || x <= 0.0)
    {
        return Err("intervals must be positive and finite");
    }

    let observed_total: f64 = observed_intervals_secs.iter().sum();
    if !observed_total.is_finite() {
        return Err("observed total is too large");
    }
    let expected_total = TARGET_INTERVAL_SECS * observed_intervals_secs.len() as f64;

    // 観測が速い（observed_total < expected_total）なら難易度を上げる。
    let raw_ratio = expected_total / observed_total;
    let bounded_ratio = raw_ratio.clamp(0.25, 4.0);
    let next = current_difficulty * bounded_ratio;
    if !next.is_finite() {
        return Err("next difficulty is too large");
    }
    Ok(next)
}

fn main() {
    let current = 100.0;
    let fast = [5.0, 5.0, 5.0, 5.0];
    let slow = [20.0, 20.0, 20.0, 20.0];

    println!("fast: {:?}", adjust_difficulty(current, &fast));
    println!("slow: {:?}", adjust_difficulty(current, &slow));
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn faster_blocks_raise_difficulty() {
        let next = adjust_difficulty(100.0, &[5.0, 5.0]).unwrap();
        assert_eq!(next, 200.0);
    }

    #[test]
    fn slower_blocks_lower_difficulty() {
        let next = adjust_difficulty(100.0, &[20.0, 20.0]).unwrap();
        assert_eq!(next, 50.0);
    }

    #[test]
    fn target_rate_keeps_difficulty() {
        let next = adjust_difficulty(100.0, &[10.0, 10.0]).unwrap();
        assert_eq!(next, 100.0);
    }

    #[test]
    fn extreme_changes_are_bounded() {
        assert_eq!(adjust_difficulty(100.0, &[1.0]).unwrap(), 400.0);
        assert_eq!(adjust_difficulty(100.0, &[100.0]).unwrap(), 25.0);
    }

    #[test]
    fn invalid_inputs_are_rejected() {
        assert!(adjust_difficulty(100.0, &[]).is_err());
        assert!(adjust_difficulty(100.0, &[0.0]).is_err());
        assert!(adjust_difficulty(-1.0, &[10.0]).is_err());
        assert!(adjust_difficulty(100.0, &[f64::NAN]).is_err());

}
```


## 13.13 DDD・C4で責務を分ける

DAAを設計対象として見ると、役割の分離が理解しやすい。

```text
┌─────────────────────────────────────────────┐
│ P2P / Block Reception                       │
│   受信・転送・重複排除                        │
└───────────────────┬─────────────────────────┘
                    │ candidate block
                    ▼
┌─────────────────────────────────────────────┐
│ Consensus Validation                        │
│   ヘッダー・親・PoW・難易度の検証             │
│                                             │
│   ┌─────────────────────────────────────┐   │
│   │ Difficulty / DAA                     │   │
│   │ 決定的な履歴選択・期待targetの算出    │   │
│   └─────────────────────────────────────┘   │
└───────────────────┬─────────────────────────┘
                    │ validated result
                    ▼
┌─────────────────────────────────────────────┐
│ BlockDAG / Consensus State                  │
│   DAG・GHOSTDAG・Virtual State              │
└─────────────────────────────────────────────┘
```

**依存関係の考え方**：P2P層は「いつ受信したか」を知っているが、「そのブロックの正しい難易度」を独断で決めるべきではない。難易度はコンセンサス層が、検証済みの履歴と共通ルールから決定する。

### 13.13.1 DAAの不変条件

- 同じコンセンサス入力から、すべての正しいノードが同じ期待難易度を計算する。
- 候補ブロックが自分に都合のよい難易度を自由に選べない。
- 入力順序やローカルの受信時刻に依存して結果が変わらない。
- ターゲットが許容範囲を外れない。
- コンセンサス変更の適用境界が決定的である。

### 13.13.2 状態遷移として考える

```text
CandidateReceived
      │
      ▼
ParentsAvailable ── no ──> WaitingForParents
      │ yes
      ▼
ExpectedDifficultyComputed
      │
      ├── mismatch ──> Rejected
      │
      ▼
PoWVerified
      │
      ├── fail ──────> Rejected
      │
      ▼
FurtherConsensusValidation
```

これは学習用の状態モデルであり、実際のKaspaノードのステートマシンをそのまま示すものではない。

## 13.14 障害調査：難易度が想定と違うとき

ノードで「ブロックがなかなか増えない」「難易度表示が急変した」と感じた場合、まず**表示値とコンセンサスの問題を分ける**。

### 調査の順序

1. 対象ネットワーク（mainnet/testnet/devnet）を確認する。
2. ノードのバージョンと同期状態を確認する。
3. ブロック生成レートの観測期間を明示する。
4. 表示難易度がどの基準で計算された数値か確認する。
5. 同期遅延・ネットワーク分断・ピア数を確認する。
6. 必要に応じてブロックヘッダーの `bits` と検証ログを調べる。
7. 実装のDAA計算とテストベクトルを照合する。

**短い観測期間のブロック生成間隔が不規則なだけでは、DAAの不具合とはいえない。**

## 13.15 よくある誤解

**Q1. 難易度が高いほどブロック生成が速い？**  
いいえ。同じハッシュレートなら、難易度が高いほど平均発見時間は長くなる。

**Q2. ハッシュレートをノードが直接測定して難易度を決める？**  
通常はブロック履歴などから間接的に推定する。各マイナーの実際の試行回数を全ノードが直接観測できるわけではない。

**Q3. KaspaはBlockDAGだから難易度調整が不要？**  
いいえ。PoWの生成ペースを維持するために難易度調整は必要である。

**Q4. blue scoreとDAA Scoreは同じ？**\
同義として扱ってはいけない。どちらもコンセンサスに関わる指標だが、用途と計算規則を実装で区別する。

**Q5. Targetを満たすハッシュならブロックは必ず有効？**  
いいえ。難易度が正しいことに加え、親・ヘッダー・トランザクションなど、他のコンセンサス条件も満たす必要がある。

**Q6. 簡易RustモデルをそのままKaspaノードに使える？**  
いいえ。教育用モデルであり、BlockDAG固有の履歴選択や整数計算などを省略している。

## 13.16 理解度チェック

1. Targetが半分になると、成功確率と期待発見時間はどう変化するか。ハッシュレート一定の条件で説明せよ。
2. ブロック間隔が確率的にばらつくことは、DAA windowの設計にどう影響するか。
3. Bitcoinの2,016ブロック方式をKaspaにそのまま当てはめられないのはなぜか。
4. Selected-parent chainだけを数えると、BlockDAGで何を見落とす可能性があるか。
5. `bits` の値が不正でも、ヘッダーのハッシュがその値のTargetを満たせばよいか。
6. タイムスタンプが信頼できる時計でないことは、DAA設計にどう影響するか。
7. DAAをP2P受信時刻に依存させると、どの不変条件を破る可能性があるか。
8. `rusty-kaspa` のDAA実装を調べる際、最低限どの情報を固定して記録すべきか。

### 解答の方向性

1. 成功確率は概ね半分、期待発見時間は概ね2倍。
2. 単発のノイズを平均化する必要がある一方、窓が大きすぎると変化への追従が遅れる。
3. BlockDAGでは並行ブロックとコンセンサス上の履歴選択が関係するため。
4. 並行して採掘されたブロックの一部。
5. いいえ。期待される難易度と一致する必要がある。
6. 時刻の検証・選択・外れ値への耐性が重要になる。
7. 同じ履歴に対してノード間で同じ難易度を計算するという決定性。
8. コミット／タグ、ネットワーク、DAA windowの規則、bitsの変換、境界条件、テスト。

## 13.17 まとめ

本章の中心は、**難易度調整を「採掘速度を自動制御する仕組み」として理解しつつ、コンセンサスの決定性を守る処理として捉えること**である。

- PoWの成功は確率的であり、生成間隔には自然なばらつきがある。
- ハッシュレートが増えれば、同じターゲットでは平均生成間隔が短くなる。
- DAAは観測された履歴からターゲットを調整し、目標ペースに近づける。
- BlockDAGでは並行ブロックが存在するため、観測対象の選択自体が重要になる。
- DAAの計算は、すべての正しいノードで一致する**決定的なコンセンサス処理**でなければならない。
- Rustの簡略モデルは直感の理解に役立つが、実際のKaspaの仕様を置き換えるものではない。

次章 **Chapter 14 — Consensus Ordering & Virtual State（コンセンサス順序と仮想状態）** では、DAG上のブロックに決定的な順序を与え、UTXO状態を評価する仕組みを扱う。
