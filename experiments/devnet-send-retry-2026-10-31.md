# Devnet：送信応答喪失と再試行・重複計上

実施日：2026-10-31。環境、ノード、公式SDKアーカイブとSHA-256は `devnet-send-review-2026-10-31.md` と同じ。
鍵はメモリ内でランダム生成し、保存も出力もしていない。

## 実行と障害の作り方

```bash
KASPA_SDK_ROOT=<展開したSDKのルート> node experiments/devnet/send.cjs --retry-checks
```

`retry-transport.cjs` が127.0.0.1の空きポートでJSON wRPCの中継を起動する。転送先は127.0.0.1:18310固定。
送金の準備中はすべて転送し、送信直前に障害注入を有効化する。ノードのsubmitTransaction成功応答を1件だけ破棄し、以降の応答は転送する。送信クライアントには500msのアプリケーション側期限を設定する。

タイムアウトだけでは送信失敗と判断しない。失われた応答内容を復旧の根拠には使わず、送信前から保持するTX IDを使ってMempoolを照会する。

## 実測した結果

- 成功応答の破棄数：1件。ノード受理前のエラーや単なる通信不通を成功には数えていない。
- クライアントの500ms期限切れを確認。
- TX IDでMempoolの存在を確認し、送信済みとして復旧。
- 保存した同じ署名済みトランザクションを変更せず再送。ノードは重複として拒否した。
- 採掘再開後、virtual chainの受理ID・入力消費・宛先UTXOを確認。
- 宛先の同一スナップショットを2回処理すると、単純加算なら200000000 sompiになるところ、OutpointをキーにしたMapでは100000000 sompi（1 KAS）で一致。
- 一意な計上対象Outpointは1件。
- 手数料10000 sompi・お釣り49899990000 sompiも独立計算と観測値が一致。
- 終了コード0。マイナーとローカルプロキシは正常終了時に停止。

## 適用範囲

これは実ノードとの通信中に応答を選択的に落とす障害注入であり、ノード自身の障害や実ネットワーク分断を測定した結果ではない。復旧ではMempoolを照会したが、既にブロックへ入ったケースの検索経路は別途必要。

同一TXの再送は検証を目的として意図的に行った。実アプリでは照会で受理済みと分かったら不要な再送を避ける。未発見でも直ちに新しい送金を構築せず、同じ署名済みTXの保持・再照会・再送方針を定める。

重複処理は同一プロセス内で受取UTXOのスナップショットを2回与える教材試験。実際の通知の重複配信をネットワーク上で発生させた試験ではない。永続DB・複数ワーカー・再起動をまたぐ一意制約やトランザクション、再編成で取り消す台帳処理は未実装。異なるOutpointである同じTX内の複数出力は別の入金として扱う必要がある。
