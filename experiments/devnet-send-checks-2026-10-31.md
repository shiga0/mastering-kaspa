# Devnet送金：検算と異常系

実施日：2026-10-31。環境・公式SDKアーカイブの固定値は `devnet-send-review-2026-10-31.md` と同じ。今回も秘密鍵をメモリ内でランダム生成し、保存・出力していない。

## 実行

```bash
KASPA_SDK_ROOT=<展開したSDKのルート> node experiments/devnet/send.cjs --checks
```

採掘で成熟入力を準備した後、採掘を停止したまま異常系とMempoolを確認する。正常送金と競合送金は、同じ入力から異なる支払額で構築・署名する。競合送金の拒否を確認してから採掘を再開し、正常送金のvirtual受理とUTXO変化を確認する。

## 実測値（sompi）

| 項目 | 値 |
|---|---:|
| 入力合計 | 50000000000 |
| 出力合計 | 49999990000 |
| 入力合計−出力合計 | 10000 |
| SDKの手数料 | 10000 |
| 宛先への送金 | 100000000 |
| 期待するお釣り | 49899990000 |
| 送金元で観測した同じTX IDのお釣りUTXO合計 | 49899990000 |

金額は整数で比較した。入力−出力で独立に得た手数料とSDKのfeeAmountが一致し、入力＝送金＋お釣り＋手数料も成立した。これは算術上の保存と観測したお釣りの検算であり、ネットワークの必要mass手数料を別実装で再計算した試験ではない。

## 異常系の結果

| 試験 | 層 | 結果 |
|---|---|---|
| 選択した入力を超える金額を要求 | SDKのトランザクション生成 | 残高不足として拒否 |
| 正しく署名したトランザクションを複製し署名バイトを変更 | ノードへのsubmitTransaction | 検証エラーとして拒否。元の入力UTXOが残ることも確認 |
| 正常送金がMempoolにある間に同じ入力の別送金を送信 | ノードへの送信 | 競合として拒否 |
| 正常送金 | Mempool・virtual chain・UTXO | Mempool照会、virtual受理ID、入力消費、宛先UTXOを確認 |

通信切断・タイムアウトを期待する拒否に数えず、該当するエラー分類以外は試験失敗とする。公開結果は `devnet/send-checks-observed-2026-10-31.json`。TX IDは `ffafa3555c45afc30b24707b459c938e1aef5ba911ab3b2f69a41d7ab1bfbfef`。

## 試行時の修正

最初は不正署名用の複製でSDKの型変換に失敗し、ノードでの拒否確認まで進まなかった。正式なsafe JSON復元APIへ変更した。
次にMempool照会で失敗し、filterTransactionPool=falseを明示して解消した。これらの途中失敗を異常系PASSには含めない。
成功後の変更は、デバッグ用のエラーメッセージ出力の削除のみ。

## 未確認事項

手数料率/massの独立実装による再計算、ブロック包含の独立照会、送信タイムアウト後の再試行・二重計上防止、再編成、2ノード収束、強制終了シグナルの実測は未完了。3種類の拒否を検証したことを異常系全体の完了とは扱わない。
