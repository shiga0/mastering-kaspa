# Devnet：稼働中の通知と再照会・古い結果の拒否

実施日：2026-10-31。環境とSDKは `devnet-notifications-2026-10-31.md` と同じ。

## 方針

通知のadded/removedをこの実習では直接DBへ適用しない。通知は「状態が変わった可能性がある」というヒントとし、固定した1アドレスの完全なRPCスナップショットを再取得する。

照会開始ごとに単一プロセス内の世代番号を発行する。最新の開始済み照会の結果だけをコミットし、より古い結果や同一結果の再コミットを拒否する。照会中に通知が来た場合、dirtyフラグが立って再照会する。通知がなくても1秒間隔を目安に再照会し、再購読時には直ちに照会する。

世代番号はノードのDAA scoreではなく、アプリ側の要求順序である。ノードのreorgを検知・拒否する仕組みではない。最新要求が失敗した場合は古い結果を代用せず、次の照会で復旧する方針。

## 実行

```bash
KASPA_SDK_ROOT=<展開したSDKのルート> python3 experiments/devnet/live-reconciliation.py
python3 -m unittest discover -s experiments/devnet -p 'test_*.py'
```

購読を開始してから初期スナップショットを取る。最初の結果を意図的に保留し、採掘中の通知と新しいスナップショットを処理した後で古い結果のコミットを試す。
続いて購読を停止し、欠落分を追加採掘で作る。再購読後、新しい通知を待たずに完全照会し、DBの有効Outpointと金額の全行をRPC結果と比較する。

DBは一時領域だけに置き、実験後に削除。秘密鍵やシードは不要。公開JSONは集計と検査結果のみ。コンテナと購読子プロセスは終了時に停止する。

## 実測

- 実UTXO通知のヒントを160件受信。
- 採掘中のスナップショットを13回コミット。
- 意図的に遅らせた古い結果は拒否。
- 購読停止中にRPC状態とDBの差ができたことを確認。
- 再購読に成功し、新しい通知を待たずに照会して補完。
- 最終1186件の有効Outpointと金額がRPC結果の全行に一致。合計59300000000000 sompi。
- 終了コード0。公開結果は `devnet/live-reconciliation-observed-2026-10-31.json`。

SQLite単体テストは合計7件成功。従来4件に加え、古い結果による出力の復活防止、新要求が未完了でも旧結果を拒否すること、失敗時にコミット済み世代を進めず再試行できることを確認した。

## 限界

アプリ内の完了順序逆転は、実際に取得した古いスナップショットを保留して再現した。ネットワーク自体の順序を変更した試験ではない。今回のノード状態は採掘による追加中心で、競合支出やreorgのremoved通知は実測していない。

世代管理は単一プロセス・単一書き込み主体向け。世代番号はDBへ永続化せず、プロセスをまたぐ同時ワーカーには使えない。再起動する場合は古い処理が終了していることを前提に、再購読と完全照会から始める。すべての瞬間でDBが最新ノード状態と一致する保証ではなく、変更が落ち着いた後の収束を確認した。

このストアは現在UTXOの観測であり、成熟残高、売上、支払い確定台帳ではない。複数アドレスの一貫したスナップショット、RPC自体の整合性証明、reorgに伴う会計上の取り消し、Pruning後の復旧は未検証。SDK通知子プロセスには60秒の実験用期限があり、自動再接続を継続運用するサービスではない。
