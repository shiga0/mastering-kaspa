# 執筆・技術レビューの管理資料

本書の執筆者・メンテナー向けに、付録Hから移した管理形式・テンプレートをまとめます。
読者向けの参考文献・判定基準・変更履歴は [付録H](../src/appendices/appendix-h.md)、
投稿方法は [CONTRIBUTING](../CONTRIBUTING.md) を参照してください。

以下は管理方法の参考資料です。従来のチェックリストは2026-11-01のレビュー時点の記録であり、
未チェック欄を現在の必須作業へ追加するものではありません。現在の作業範囲は [ROADMAP](../ROADMAP.md) に従います。

## 変更履歴の設計

書籍の変更を「文章修正」と「技術的な意味の変更」に分ける。

| 変更種別 | 例 | 必要な確認 |
|---|---|---|
| Editorial | 誤字、見出し、表現 | 編集レビュー |
| Clarification | 用語・図解の改善 | 内容の整合性 |
| Technical correction | 誤った数式・コード修正 | 一次資料とテスト |
| Version update | Rust/Kaspaリリース更新 | 差分と互換性 |
| Protocol update | KIPの有効化・コンセンサス変更 | ネットワーク別確認 |
| Experiment update | 実測値・再現手順更新 | ログ・環境・証拠 |

## Gitによる変更履歴の追跡

```bash
# 書籍リポジトリで実行
git status --short
git log --oneline --decorate -n 15

# 特定章の履歴
git log --follow -- src/part-05-advanced/chapter-34.md

# 差分確認
git diff -- src/appendices/appendix-h.md

# 以下はレビュー後に必要な場合のコミット例（今回自動実行していない）
git add src/appendices/appendix-h.md
git commit -m "docs: add bibliography and review policy"
```

公開後はGitタグで書籍版を固定すると、読者が同じ内容を再参照しやすくなる。

## 執筆と技術レビューの分離

**執筆**では、概念を理解できるようにする。**技術レビュー**では、その説明が資料と実装に照らして正しいかを確認する。二つの作業を混ぜると、読みやすいが誤った説明が残りやすい。

推奨する流れ：

1. 章の目的と読者の前提知識を定義。
2. 一次資料を収集して版を固定。
3. 概念図と本文を作成。
4. 数式・コード・数値に出典IDを付ける。
5. コードを実行し、実験IDを付ける。
6. 別の視点でレビュー。
7. 修正履歴を残して公開。

## 長いコードの折りたたみ

コードは原則として20行以上を `<details class="code-details">` と `<summary>` で囲み、
閉じた状態にする。見出しは「UTXO最小モデルの実装を見る」など、内容が分かる名前にする。
HTMLタグとMarkdownのコードフェンスの間には空行を入れ、コード自体や本文同期用コメントは変更しない。

直後の説明と見比べる型・状態遷移・境界設計のコードは `open` 属性を付けて最初から表示する。
20行未満のコード、実行コマンド、短いログ、テキスト図は通常どおり表示する。
長い実行ログや補足の全体実装は行数だけで決めず、内容に応じて折りたたむ。
includeを使う例は展開後の行数で判断する。将来の追記時もこの基準で個別に確認する。

開閉はブラウザ標準の機能を使用し、追加プラグインは不要。
`theme/code-details.js` は印刷前に閉じたコードを展開し、印刷後に元の状態へ戻す。
印刷以外のPDF・EPUB変換では、変換先でもコード全文が含まれるか別途確認する。

## 理解度チェックの形式

全章・付録の理解度チェックは、質問一覧と解答例を一つの `<details class="quiz-answers">` にまとめ、初期状態では閉じる。
`<summary>` は「理解度チェックを見る」に統一する。枠を開くと番号付きの質問一覧と「解答例」が一緒に表示される。
解答だけの折りたたみは入れ子にせず、解答は質問と同じ番号・順序で一対一に対応させる。
既存の章・節番号とアンカーは維持し、基礎・応用の区分や発展課題・確認の観点も残す。

解答は本章の対象版・本文に基づく。設計・調査課題は一意の正解ではないため、
考え方の例や確認手順・判断基準を示す。未実施の実験結果や、未確認の最新動作を解答に書き足さない。
印刷時はコードと同じスクリプトで質問・解答を展開し、印刷後は元の開閉状態へ戻す。

## よくある誤解の形式

章・付録の「よくある誤解」は、`**1. 誤解または疑問の内容**` のような番号付きの太字見出しと、
空行を挟んだ説明段落に統一する。番号は各節内で1から始める。
節の見出しを残し、内容全体を初期状態で閉じた `<details class="misconception-details">` で囲む。
`<summary>` は「よくある誤解を見る」に統一する。印刷時はコード・解答と同じ処理で展開し、印刷後に元へ戻す。
表形式、Q/Aの接頭辞、説明前の矢印は使わず、主張・留保・根拠は維持する。
既存の小見出しを太字に変更する場合は、元のIDをアンカーとして残す。

## まとめの形式

各章・付録の「まとめ」（Part・本章・本書のまとめを含む）は、節の見出しを残し、
初期状態で閉じた `<details class="summary-details">` に本文を入れる。
`<summary>` は「まとめを見る」に統一する。要点のリストは箇条書きとし、説明段落・図・表の内容は維持する。
末尾の次章案内、区切り線やレビューの確認範囲は枠の外に置き、閉じた状態でも読めるようにする。
印刷時は他の折りたたみと同じ処理で全文を展開し、印刷後に元の状態へ戻す。

## 参考資料の形式

章・Argent・付録の参考資料一覧は、既存の節見出しを残し、
初期状態で閉じた `<details class="reference-details">` に入れる。
`<summary>` は「参考資料を見る」に統一する。参考資料は名前付きリンクの箇条書きとし、
著者・題名・版・コミット・説明・留保と元の順序、分類用の小見出しを維持する。
確認範囲・未確認事項・編集メモ・レビュー確認項目・次章案内は枠の外に残す。
付録Hの書誌表や出典管理の説明、本文中の一次資料を読む手順は、参考リンク一覧とは別に扱う。
印刷時は他の折りたたみと同じ処理で資料一覧も展開し、印刷後に元へ戻す。

## 実践課題・演習の形式

独立した実践課題・実践演習・演習・発展課題は、節見出しを残して内容を
`<details class="exercise-details">` に入れ、初期状態では閉じる。
開閉ラベルは種類に応じて「実践課題を見る」「演習を見る」「発展課題を見る」とする。
複数の課題を含む節では、課題名を小見出しに揃え、手順・成果物・合格条件・注意事項を維持する。
変更した小見出しの元のアンカーも残す。理解度チェック内の発展課題は既存の枠内に置き、
さらに折りたたむ入れ子にはしない。本文の実装手順そのものを扱う「実践」節は一括で閉じない。
印刷時は他の折りたたみと同じ処理で課題全文も展開し、印刷後に元へ戻す。

## レビュー記録と読者向けの注意

「目次順の本文レビュー」等の作業日・作業経緯は、章冒頭へ繰り返さず、
[技術レビューの進捗](../src/review-status.md)と既存の `experiments/` の記録に集約する。
共通の対象版・検証方針は[本書の対象バージョン](../src/baseline.md)へまとめる。

章・付録・Argentの末尾には、初期状態で閉じた `<details class="verification-details">` を置き、
「検証状況を見る」から対象版・章別のレビュー記録・詳細な確認範囲へ進めるようにする。
検証件数・未実施事項・確認日の記録は削除せず、編集整理を新しい実行結果やVerifiedへの更新として扱わない。
印刷時は検証状況も展開する。

教育用コードと実ノードの違い、利用できるネットワーク・対象版、鍵や資金を扱う際の前提など、
読者の判断に必要な注意は本文やコードの近くに残す。研究提案・実装・ネットワーク有効化も引き続き区別する。

## 章冒頭・注意・実習・次章案内

章タイトルの直後には、目次と同じPart名を `.chapter-part` で一度だけ表示する。
書名やPart名を引用ブロックへ重ねて書かない。対象読者・前提知識・章の位置づけは、
既に記載のある内容を使い、不要な前提を新たに追加しない。

学習目標を示す節は「この章で学ぶこと」、目標のリストは箇条書きに揃える。
節番号は変更せず、見出しを変更するときは旧IDも明示アンカーで維持する。
注意書きは `> **注意：**` または `> **重要：**` に揃え、常時表示する。
課題の合格基準・合格条件は「完了条件」、提出内容は「成果物」として区別する。

実習の同じ役割のラベルは「前提条件」「実行手順」「期待結果」「制限」に揃える。
新しい実習はこの順で説明する。既存の実習ではコードの依存関係や説明の対応を優先し、
形式だけのためにコードを並べ替えたり、未確認の期待結果を補ったりしない。

次章案内は `.chapter-next` の共通枠で本文末尾・検証状況の前に置く。
32章からArgent、36章から付録Aへ進む案内も維持する。枠は折りたたまず、印刷時には非表示にする。
まとめに続く説明文は残してよいが、独立した「Next:」等の案内を重複して置かない。

## 継続的なメンテナンス

Kaspaの実装・KIP・SDKは更新される。公開後も、少なくとも**新しい主要リリース時**に関連章を見直す。更新対象は「値の変更」だけではなく、用語、互換性、セキュリティ前提、RPC応答、テスト手順なども含む。

自動化できる部分：リンクチェック、Markdown lint、Rustテスト、mdBookビルド、参照タグの存在確認。自動化しにくい部分：論文の仮定、コンセンサスの意味、脅威モデル、実際のネットワーク有効化条件。

| [kaspanet/research](https://github.com/kaspanet/research) | `main` | 論文・研究仕様 |

GitHubのWatchはリポジトリ単位で、特定ブランチの全コミットを通知する設定ではない。[GitHubの通知設定](https://docs.github.com/en/subscriptions-and-notifications/get-started/configuring-notifications)を参照。

- まず`rusty-kaspa`で「Watch → Custom → Releases」を選び、新リリースの通知を受ける。
- KIPや開発中の技術は、本に関係するIssue・PRを個別にSubscribeする。リリース通知だけでは文書・開発途中の変更を拾えない。
- 新リリース時や本の改訂時に、本文で固定したコミットと更新候補の差分を比較し、影響する章・実習を確認する。毎コミットの追従は必須にしない。
- 対象版を更新する場合は、関連コード・実習を再確認し、[対象バージョン](../src/baseline.md)と参照コミット・確認記録を一緒に更新する。確認前は従来の基準版を維持する。

CIでは教材のビルド・テストや新版の検知を自動化できるが、新しい仕様と本文の意味が一致するかは別途確認する。新版通知の自動化は現時点では導入していない。
